## 2. 診断 — #1 と #6 は同じ1つの欠陥である

### 2.1 既にあるものが見えていない

`CardType = 'tower' | 'trap' | 'spell' | 'reactor' | 'ember' | 'levy'` は `domain/cards/card-definition.ts:11` に定義済みで、配置先の決定（`placementKindOf`）にも使われている。**プレゼンテーション層での使用は `HandArea.tsx:186`（魔力炉のクールダウンゲージの出し分け）の1箇所だけ**で、プレイヤーには一切見せていない。

このコンセプトは MTG を出発点にしており、マナのカード化・デッキ構築・同名上限を借りた。**カードタイプという語彙も内部には借りていたが、画面に出していなかった。**

#1 も同種である。守り手は HP・攻撃力・射程・攻撃間隔・対空可否・範囲・貫通の7属性を持つが、盤面に出ているのは HPバーとカード名だけである。

**これは反復2で直した欠陥と同じ形である。** 当時は「`TickEvent` が計算済みなのに描画されていない」だった。今回は「`CardType` が定義済みなのに表示されていない」。**欠陥を直すときに、その欠陥の「形」で他の領域も点検していれば先に見つかっていた。**

### 2.2 根本原因は「符号の非対称」である

`enemy-visual.ts` は敵を **「形 × サイズ × 色」の3重符号**で区別し、「グレースケールでも形とサイズだけで見分けられること」を要件として明文化している（S1 の教訓）。

**守り手側にはこの対応物が存在しない。**

`BoardGrid.tsx:147-157` の `occupantLabel` は、`cardId === 'beacon'` なら「篝」、それ以外の全 tower を「塔」と描く。**弓兵・弩砲・火砲台・投石機・徹甲弩・石壁・鍛冶場の7種が盤面上で区別できない。** 罠は2種がどちらも「罠」、燠は「燠」、炉は「炉」である。

敵には確立した符号規約があり、守り手には無い。これが #1 の正体である。

### 2.3 #1 は3回持ち越した項目である

「デザインの全面見直し」は反復1・2・3 と3回連続で後回しにしてきた。個々の反復では毎回「本反復の問いと独立している」という正しい判断だったが、他が解消されるにつれて相対的に前へ出て、今回**6件中の最初に**挙がった。

**「後回しにしてよい」は「ずっと後回しにしてよい」ではない。**

## 3. この反復の問い

> **置いたもの・手札が何であるか、見て分かるか。**

実プレイのヒアリングで、「わかりにくい」の中身は**4層すべて**であることが確認された。

| 層 | 内容 |
|---|---|
| 同一性 | どれを置いたか。弓兵なのか弩砲なのか投石機なのか |
| 能力 | 何ができるか。射程・対空可否・範囲/貫通 |
| 状態 | 今どうなっているか。攻撃しているか、あと何回で壊れるか |
| 質感 | 見た目が素っ気ない |

### 3.1 この反復は表現層に閉じる

**カードタイプは「見せるだけ」とし、ルール上の意味は持たせない。** タイプごとの制約や相互作用を新設すると、語彙の拡張（#4・#5）と一体になって反復が肥大する。

この決定には判定上の利点がある。**ルールが1行も変わらないため、行動が変われば原因は表現以外にない。** 自然実験として成立する。

### 3.2 この反復の難しさ

反復1〜3 は「配分の判断が生まれるか」のような**機能の問い**で、勝率や配置比率という数値で測れた。表現の問いは**正解が数値になりにくい**。判定項目の作り方そのものを設計する必要がある（§8）。

## 4. 符号体系 — 形 × サイズ × 文字

`enemy-visual.ts` の対称物として `presentation/unit-visual.ts` を新設する。**色の代わりに文字を使う**ため、新しい色トークンを1つも増やさずに済む（設計書 §9.4 の6トークン規約を守る）。

### 4.1 図と地の分離

敵マーカーは**塗りつぶしの小さな図形**でセル上を動く。守り手を同じ土俵に乗せると混同するため、守り手は**セルに敷く台座（プレート）**として描く。

| 軸 | 敵 | 守り手・設置物 |
|---|---|---|
| 位置 | セル上を移動 | セルに固定 |
| サイズ | セル辺の 3.5〜7.5%（盤面幅基準） | セル辺の 45〜85% |
| 塗り | 不透明 | 輪郭線＋半透明 |
| z 順序 | 上（3） | 下（0〜2） |

4点で図地が分かれるため、形が一部重複しても誤読しない。

### 4.2 軸1: 形 ＝ 役割（6分類）

`CardDefinition` から純粋関数 `roleOf` で導出する。**ドメインは変更しない**（`unit-visual.ts` 側で導出する）。

| 役割 | 台座の形 | 該当カード | 導出条件 |
|---|---|---|---|
| 攻撃塔 | 上向き五角形 | 弓兵・弩砲・火砲台・徹甲弩・投石機 | `tower && tower.damage > 0` |
| 支援塔 | 円 | 篝火・鍛冶場 | `tower && tower.aura` |
| 壁 | 横長の角丸長方形 | 石壁 | `tower && damage === 0 && !aura` |
| 罠 | 下向き三角 | 棘罠・落網 | `type === 'trap'` |
| 炉 | 六角形 | 魔力炉 | `type === 'reactor'` |
| 燠 | 四芒星 | 業火 | `type === 'ember'` |
| **呪文** | **菱形** | **時泥** | `type === 'spell'` |
| **徴発** | **上向き三角** | **徴発** | `type === 'levy'` |

**盤面に出るのは上の6分類、手札とデッキ構築ではさらに呪文と徴発を加えた8分類になる。** 時泥と徴発は盤面に残らないため、**プレイヤーが盤面で同時に見分ける形は6種のまま**であり、認知負荷の上限（5〜7）は守られる。手札は面積があり名前も併記されるため、8種でも読み負担は増えない。

**この形を手札とデッキ構築画面にもそのまま出す**ため、これが #6 のカードタイプ表示を兼ねる。

3条件は排他である（篝火・鍛冶場・石壁はいずれも `damage: 0`、石壁だけ `aura` を持たない。カードプール実測値）。順序依存を残さないため、実装でも排他な条件として書く。

**制約を1つ記録しておく。** `PlacedUnit` と `PlacedTrap` は `cardId` を持つが、**`PlacedReactor` と `PlacedEmber` は持たない**（`combat-state.ts:32-43`）。したがって炉と燠の台座は「炉カードは `reactor` の1種、燠カードは `ember-blast` の1種」という現在のカードプールの前提の上でのみ正しく描ける。これは `run-summary.ts:82-87` が撃破の帰属で抱えているのと**同じ制約**である。**2種類目の炉または燠を追加した瞬間、両方が静かに誤表示・誤帰属する。** そのときはドメインに `cardId` を持たせる変更とセットで直すこと。

clip-path の値:

| 形 | 値 |
|---|---|
| 上向き五角形 | `polygon(50% 0%, 100% 38%, 82% 100%, 18% 100%, 0% 38%)` |
| 円 | `border-radius: 50%`（clip-path を使わない。`enemy-visual.ts` と同じ方針） |
| 横長角丸長方形 | `border-radius: 4px`（clip-path を使わない） |
| 下向き三角 | `polygon(0% 0%, 100% 0%, 50% 100%)` |
| 六角形 | `polygon(25% 0%, 75% 0%, 100% 50%, 75% 100%, 25% 100%, 0% 50%)` |
| 四芒星 | `polygon(50% 0%, 61% 39%, 100% 50%, 61% 61%, 50% 100%, 39% 61%, 0% 50%, 39% 39%)` |
| 菱形（呪文・手札のみ） | `polygon(50% 0%, 100% 50%, 50% 100%, 0% 50%)` |
| 上向き三角（徴発・手札のみ） | `polygon(50% 0%, 100% 100%, 0% 100%)` |

敵の形（円・菱形・四角・六角形・上向き三角）と重複するのは円・六角形・三角の3つだが、罠の三角は**下向き**で鴉の上向き三角と反転しており、円と六角形は §4.1 の4軸で分離される。**菱形と上向き三角は手札にしか出ない**ため、盤面上で敵と競合しない。

### 4.3 軸2: サイズ ＝ コスト（0〜5）

台座の辺長をセル辺に対する割合で決める。

```
sizePct(cost) = 45 + 8 * cost
```

| コスト | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 辺長 | 45% | 53% | 61% | 69% | 77% | 85% |

**サイズは強さではなく投資額を表す。** マナを払った実感と一致し、盤面に「何にいくら払ったか」が残る。

**例外を明示する。** HP と攻撃力は逆相関のため（石壁はコスト1で HP60）、サイズと強さは一致しない。石壁が小さく見える問題は、壁だけ**横長プレート（幅90% × 高さ45%）**にして面積を稼ぐことで緩和する。この非対称は判定の反証条件に含める（§8.3）。

|---|---|---|---|---|

| `catapult` | 投石機 | 投 | 攻撃塔 | 5 |

盤面に出るのは上12種、手札には14種すべてが出る。現状の「塔 / 篝 / 炉 / 燠 / 罠」を置き換える。

### 4.5 形とサイズだけで14種が一意に決まる（不変条件）

グレースケール要件を、文字にすら依存しない形で満たす。

| 役割 | 含まれるカードのサイズ |
|---|---|
| 攻撃塔 | 53 / 61 / 69 / 77 / 85（5種すべて相異なる） |
| 支援塔 | 53（鍛冶場） / 61（篝火） |
| 罠 | 53（棘罠） / 61（落網） |
| 壁・炉・燠・呪文・徴発 | 各1種 |

**`(形, サイズ)` の組は14種すべてで重複しない。** 文字は同一性の最終確認に使う冗長な符号であり、形とサイズが読めれば文字なしでも識別できる。この不変条件を**テストで機械的に検証する**（§11）。

将来カードを増やすとき（#4）、この不変条件は自動的に破れうる。**テストが破れることで気づける**のが設計上の狙いである。

### 4.6 情報量の上限

反復2 の `MAX_CONCURRENT_EFFECTS` に倣い、**設置済みセルに常時描く印を3つまで**とする定数 `MAX_CELL_MARKS = 3` を置く。

内訳は台座の形・個体文字・状態バーの3つ。現状の経路セルには `LaneMark`（レーン識別印）と `CellArrow`（進行方向）があるため、**設置物が乗ったセルではこの2つを隠す**。設置物が乗るのは自分が置いた結果であり、そのマスのレーンと方向は配置時点で既に判断済みだからである。

## 5. 盤面 — 状態と能力

### 5.1 状態バーは1本だけ。意味は形が決める

現状 HPバーは守り手（`units`）にしか出ていない。罠の残回数・燠のクールダウン・炉の生成間隔は、別の表現を持つか、持っていない（燠だけ文字色と太字で ready を示している。`BoardGrid.tsx:153`）。

**同じ位置・同じ形のバーを1本だけ出し、意味は台座の形が決める**という規約にする。

| 台座の形 | バーが表すもの | 分子 / 分母（実在するフィールド） |
|---|---|---|
| 攻撃塔・支援塔・壁 | 残 HP | `PlacedUnit.hp` / `tower.hp` |
| 罠 | 残り発動回数 | `PlacedTrap.usesLeft` / `trap.uses` |
| 燠 | 再発動までの経過 | `1 - PlacedEmber.cooldownLeft / ember.cooldownTicks` |
| 炉 | 次のマナ生成までの進捗 | `1 - PlacedReactor.ticksToMana / reactor.intervalTicks` |

4種すべて既存の状態フィールドから計算できる。**ドメインへの追加は不要**である。

`MAX_CELL_MARKS = 3` を守ったまま、**これまで見えなかった罠・燠・炉の状態がすべて可視化される**。プレイヤーが覚えるルールは「バーは1本、意味は形」の1つだけである。

既存の `UnitHpBar.tsx` を状態バーへ汎用化する。バーの色は据え置き（残量で色を変えない。反復2の教訓「観察者が色を種別と誤読した」を維持）。

### 5.2 能力は要求時に開示する

カード**未選択時**のセルタップは、現在は**再点火可能な燠火があればそれを再点火し、それ以外では何も起きない**（`useAshenRampartGame.ts:303-317`）。ここに能力の開示を足す。

**衝突を避けるため優先順位を先に定義する。**

| # | 状況 | 動作 |
|---|---|---|
| 1 | 一時停止中 | 無反応（現状維持） |
| 2 | カード選択中 | **配置**（現状維持。明示的な意図を尊重する） |
| 3 | 未選択 ＋ 再点火可能な燠火（`cooldownLeft === 0`） | **再点火**（現状維持） |
| 4 | 未選択 ＋ 設置物あり（上に当たらない） | **能力表示を開く／同じマスの再タップで閉じる** |
| 5 | 未選択 ＋ 空マス | 能力表示を閉じる |

3 が 4 より優先されるため、**再点火可能な燠火だけは能力表示を開けない**。ただしクールダウン中の燠火はタップで能力表示が開くので、燠火の性能を確認する手段は残る。既存の操作を1つも壊さずに能力表示を差し込める。

- タップした設置物の**射程リングを輪郭だけで描く**（塗らない。敵とエフェクトを隠さない）
- 属性チップは**盤面の外**に出す（`EnemyLegend` の近く）。盤面自体は汚さない
- 再タップ、他所のタップ、カード選択のいずれでも閉じる
- **カード選択中は従来どおり配置が最優先**。能力表示は起動しない

チップに出す内容:

| 役割 | 内容 |
|---|---|
| 攻撃塔 | 攻撃力 / 射程 / 攻撃間隔 / 対空可否 / 単体・範囲・貫通 |
| 支援塔 | 強化内容（火力 +N / 射程 +N） / 効果範囲 |
| 壁 | HP / 攻撃0であること |
| 罠 | ダメージ / 残回数 / 地上化の有無 |
| 炉 | 生成量 / 間隔 |
| 燠 | ダメージ / 半径 / クールダウン |

**射程0のカードを例外として先に決めておく。** 篝火・鍛冶場・石壁は `tower.range` が 0 である（カードプール実測値）。

| 対象 | 描くもの |
|---|---|
| 攻撃塔（`range > 0`） | 射程リング（輪郭のみ） |
| 支援塔（`range 0` ＋ `aura`） | **隣接8マスの枠**（オーラの実効範囲。リングではない） |
| 壁（`range 0` ＋ `aura` なし） | 何も描かない。チップで「攻撃しない」と明示する |

リアルタイム中に止まって読む負担はあるが、**射程リングは一瞬で読める**ため実用上はそこが主役になる想定である。

### 5.3 質感 — 新色ゼロで担保する

| 対象 | 内容 | 時間 |
|---|---|---|
| 攻撃時 | 台座の脈動（既存 `shot` エフェクトに同期） | 150ms |
| 配置時 | ポップイン | 200ms |
| 常時 | 台座に `secondary` の透明度差による微細な陰影 | — |

すべて `prefers-reduced-motion: reduce` で無効化する。**動くのは「何かが起きた瞬間」だけ**とし、装飾のための装飾は足さない（設計規約「機能的な瞬間のみ・300ms 以内」）。

## 6. 手札とデッキ構築 — 同じ符号を3画面で一貫させる

盤面の台座と**同じ形のアイコン**を手札カードの左に置く。これが「持っていた札」と「置いたもの」を結ぶ唯一の線であり、案の中心である。

手札カードに出すものを固定する（ここにも上限を置く）。

| 要素 | 内容 |
|---|---|
| 形アイコン | 台座と同一の6形。役割を表す |
| 名前 | 既存 |
| コスト | 既存 |
| 主要数値（最大2つ） | 塔=`HP/攻撃`、罠=`ダメージ/回数`、炉=`生成量/間隔`、燠=`ダメージ/半径`、呪文=`倍率/持続`、徴発=`提示枚数`（1つだけ） |
| 属性バッジ 最大2 | `対空` / `範囲` / `貫通` のうち該当するもの |

**デッキ構築画面（`DeckBuilder.tsx`）にも同じ形アイコンを出す。** 既に `towerStatsTextOf`（HP/攻撃）と `weaknessTextOf`（効かない相手）があるため、形を足すだけで**デッキ構築 → 手札 → 盤面**の3画面が同じ符号で繋がる。

### 6.1 幅のトレードオフ

手札カードは現在 `min-width: 92px`（`HandArea.tsx:55`）。数値とバッジを足すと幅が要り、**最小360px幅では折り返しが増えて盤面が圧迫される**。

**実装時に最小幅360pxでの実表示を必ず確認する。** 収まらない場合の削る順序を先に決めておく（同一性 > 能力）。

1. 属性バッジを2つ→1つに減らす
2. 属性バッジを落とす
3. 主要数値を2つ→1つに減らす

形アイコン・名前・コストは削らない。

## 7. 作らないもの（YAGNI）

- **カードタイプにルール上の意味を持たせない**（§3.1）
- **カードを1枚も増やさない**（#4 は後続）
- **敵に向かうカードを作らない**（#5 は後続。新機構）
- **ドット絵・イラスト素材を用意しない**（形と文字で足りるかをまず測る）
- **新しい色トークンを増やさない**（`theme.ts` の6トークンのみ）
- **ホバーによるツールチップを作らない**（タッチ端末で機能しない。タップに統一する）
- **盤面の3D化・パララックス・パーティクルを入れない**

## 8. 計測と判定

### 8.1 方法論 — 行動を「対」で事前登録する

表現の問いは「分かったか」を直接測れない。代わりにこうする。

> **「分かっていれば起きるはずの行動」と、「分かっていなければ起きるはずの行動」を対にして事前登録する。**

片方だけだと、その行動が起きなかったときに「表現が効いた」のか「そもそもその行動をしない人だった」のかが区別できない。**両方が同じ向きに動いたときだけ**表現の効果と読む。

§3.1 のとおりルールを1行も変えないため、行動差の原因は表現以外にない。

### 8.2 baseline がないことを正直に扱う

判定項目の数値は3反復連続で未集計であり、比較対象がない。

- 反復4は**絶対値の予測を事前登録**する（外れたと言える形で先に書く）
- 同時に全数値を記録し、**反復5以降の baseline にする**

### 8.3 事前登録する6項目

| # | 項目 | 対の向き | 事前予測 |
|---|---|---|---|
| 1 | 一度も出さなかった札の種類数 | 分かっていれば**減る** | 3ラン平均で **3種以下** |
| 2 | 手札から手動で捨てた回数 | 分かっていなければ**増える** | ラン1 > ラン3 |
| 3 | 能力表示を開いた回数 | 分かっていなければ**増える** | ラン1 > ラン3。**0回なら主観で切り分ける**（足りていたのか、機能に気づかなかったのか） |
| 4 | 拒否理由 `target`（置けない場所をタップ）の回数 | 分かっていなければ**増える** | 3ラン合計で **5回以下** |
| 5 | 1セルに常時描く印の数 | 情報量の上限 | **3以下**（自動テストで担保） |
| 6 | 前回より面白くなったか | — | 自由記述 |

項目1・2 が対（同一性）、項目3・4 が対（能力）である。

反復3の7項目（レーン配分・ブロッカー位置・失った守り手・経路上外比率・鴉の撃破位置・コスト分布）も継続して記録する。**貫通(19/20) > 範囲(11/20) への軸の偏り**（反復3設計書 §10）は今回も観察を続ける。

### 8.4 反証条件（先に定義する）

| 条件 | 判定 |
|---|---|
| 「まだ何を置いたか分からない」が出る | **No** |
| 「盤面がごちゃごちゃした・見づらくなった」が出る | **No**（情報量が過大） |
| 「サイズが強さに見えて誤読した」が出る | **部分 No**（§4.3 の例外が失敗） |
| 項目1 が6種以上 | **No** |

### 8.5 出口条件

§8.4 の上2つが出ず、項目6 が Yes なら、次段階（#4・#5 の語彙拡張＝カード種類の追加と、敵に向かうカード）へ進む。

## 9. 集計を判定者へ届ける経路

### 9.1 なぜ3反復届かなかったか

「計測ログをコピー」ボタンは反復2から存在する（`AshenRampartGame.tsx:297`）。原因は2つあった。

1. **判定者がボタンの存在を知らなかった**（ヒアリングで確認）
2. **コピーされるのは生イベント列で、判定項目の集計値が入っていない。** 集計は `run-summary.ts` が画面用に計算しているだけで、ログには入らない。判定者は JSON を受け取っても自分で集計し直さねばならなかった

**知らなかっただけでなく、知っていても使いにくい構造だった。** 両方を潰す。

### 9.2 集計値をログに入れる（スキーマ v3）

決着時に `run_tally` イベントを1件記録する。ログスキーマの原則「記録する項目はすべて判定に使う」に合致する。

追加するイベント:

| イベント | 用途 |
|---|---|
| `card_discarded_manual` | 項目2（既存の `card_discarded_overflow` は溢れによる消失で、意味が異なる） |
| `inspect_opened` | 項目3 |
| `run_tally` | 項目1〜4 ＋ 反復3の7項目のスナップショット |

- `CURRENT_ITERATION` を 3 → **4** に更新する
- スキーマを **v3** に上げ、キーを `ashen-rampart:play-log-v3` にする
- **新キーのため、実プレイ前の localStorage 削除作業が不要になる**（v2 のデータと混ざらない）

### 9.3 ボタンの文言を変える

「計測ログをコピー」→ **「判定用の記録をコピー（3ラン分まとまっています）」**。

なぜ押すのか、何回押せばよいのかがボタン自身に書かれている状態にする。ボタンは集計の直上に置く。

「勝敗の理由を記録する」を入力するまで集計が開かない現在のゲートは**維持する**。反復2・3の判定は自由記述から実質的に成立しており（反復3判定記録 §1.2）、この入力は判定の主材料だからである。

## 10. 実プレイ手順

**この節が判定者に届かなければ §9 の実装は無意味になる。Issue にも転記する。**

1. **3ラン続けて遊ぶ。** 途中でリロードしてよい（ログは localStorage にラン横断で蓄積される）
2. **各ランの決着時に「勝敗の理由を記録する」へ一言書いて「記録する」を押す。** これが集計を開く鍵であり、判定の主材料でもある
3. **3ラン目の決着後に「判定用の記録をコピー」を1回だけ押す。** 3ラン分がまとめてクリップボードに入る
4. コピーした JSON を貼る
5. あわせて、遊んだ感想を自由に述べる（§8.4 の反証条件はここから読む）

**localStorage の削除作業は不要**（§9.2）。

## 11. テスト方針

| 対象 | 検証すること |
|---|---|
| `unit-visual.ts` | **全14種のカード**に符号が定義されている（`MISSING_WEAKNESS_IDS` と同じ網羅パターン）／`roleOf` の全8分岐／`sizePct(0)=45`・`sizePct(5)=85` |
| **符号の一意性** | **`(形, サイズ)` の組が14種で重複しない**（§4.5 の不変条件。色にも文字にも依存せず識別できることの担保） |
| `BoardGrid` | **設置済みセルの常時印が `MAX_CELL_MARKS` 以下**（判定項目5 の機械的担保）／設置物がある経路セルで `LaneMark` と `CellArrow` が消える |
| 状態バー | 形ごとに意味が切り替わる（塔=HP、罠=残回数、燠=CD、炉=進捗）／分母が 0 のときに破綻しない |
| `HandArea` / `DeckBuilder` | 形アイコン・数値2つ・バッジ最大2 が出る／**盤面の台座と同じ形が使われている** |
| 能力表示 | カード未選択時のタップで開く／再タップ・他所タップ・カード選択で閉じる／**カード選択中は配置を邪魔しない**／**射程0の3種**（篝火・鍛冶場・石壁）でリングを描かず、支援塔は隣接枠・壁は無描画になる |
| ログ | v3 スキーマ／`run_tally` に項目1〜4 が入る／`card_discarded_manual`・`inspect_opened` が記録される／v2 データを読んでも壊れない |
| アクセシビリティ | `aria-label` に役割名と個体名が入る（例: 「攻撃塔 弓兵 HP8」）／`prefers-reduced-motion` で動きが止まる |

**「手札と盤面で同じ形が使われている」はテストにする。** ここが崩れると案の中心（持っていた札と置いたものが繋がる）が壊れるため、言葉の約束では守れない。

## 14. 教訓の適用

### 14.1 前反復から引き継いだもの

- **判定は「言われなかったこと」で読む。** 前回の不満が今回挙がらなければ達成の証拠になる（§8.4 の反証条件はこの形で書かれている）
- **後回しの回数を数える。** #1 は3回持ち越して最上位の不満になった（§2.3）

### 14.2 本反復で新たに得たもの

- **欠陥を直したら、その欠陥の「形」で他の領域も点検する。** 反復2の「計算済みなのに描画されていない」を直したとき、同じ形で `CardType` を点検していれば #6 は先に見つかっていた（§2.1）
- **既にある機能が使われていないなら、原因は「無い」ではなく「届いていない」。** ログのコピーボタンは2反復前から存在していた。作る前に、なぜ既存のものが届かなかったかを問う（§9.1）
- **表現の問いは、行動を対にして事前登録することで反証可能にできる。** 片側だけでは「効いた」と「そもそもやらない」が区別できない（§8.1）
