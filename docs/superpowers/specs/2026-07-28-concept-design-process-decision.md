## 1. なぜ方針を変えるのか

### きっかけ

#183 の実例調査を終えた時点で、開発者（ユーザー）から次の判断が示された。

> この結果からこのまま進めていてもいいものができない気がしてきました。
> ゲームとしてどのゲームに近い形を目指すのか、自分たちのオリジナリティは何なのか、
> どのようなソフトを求めているのか。コンセプトが必要な気がしてきました。

### 調査結果がこの判断を支持する

#183 の調査は「S2 で観戦を演出すれば直る」とは示していない。示したのは次の事実である。

- 調査対象6本のうち、戦闘中にプレイヤーが何もできないのは **Mechabellum ただ1本**
- その1本ですら、戦闘フェーズ約90秒の上限・加速ボタン・加速投票・冒頭の情報開示という**3重の管理下**に置いている
- 灰燼の城壁は**この最難関の形式を、なぜそれを選ぶのかという理由なしに選んでいた**

### 根本原因＝当初のコンセプトが「面白さの仮説」になっていない

`2026-07-16-ashen-rampart-design.md` の「コンセプト」節に書かれているのは、**ジャンルの組み合わせと世界観**である。

> ハイブリッド型 / フェーズ分離型 / 中型ラン / 経路型TD（4本柱）

ここに「**なぜこれが面白いのか**」という仮説はどこにも無い。したがって「フェーズ分離型＝戦闘は観戦」は、面白さの仮説として選ばれたのではなく、**構成要素として列挙されていた**にすぎない。

これが、これまでの改修（空間パズル化 PR #171 / 可読性 S1 PR #180）がいずれも「機構は正しく動き CI は全緑だが手触りは変わらない」で終わった構造的な理由である。**判断の基準が無いところに改修を積んでも、良し悪しを判定できない。**

### 結論

S2（観戦の演出）に進むことは、**コンセプトの空白を埋めないまま対症療法を重ねること**になる。よって S2 の提案は保留し、先に「コンセプトをどう決めるか」の作法を整備する。

## 2. 決定事項

ブレインストーミングで以下を確定した（4問中3問回答済み、残りは次セッション）。

| # | 論点 | 決定 |
|---|---|---|
| 1 | 今回のリセット範囲 | **まずプロセスだけ整備する。** 灰燼の城壁の個別結論（続行/変更/破棄）は先送りし、その作法の最初の適用対象とする |
| 2 | 成果物の形 | **再利用可能なスキル。** `local/AI/` 配下に置き、`.claude/skills/` へ symlink（claym の規約「スキルは他プロジェクトでも再利用可能な形で書く」に従う） |
| 3 | 「コンセプトが決まった」の定義 | **反証可能な面白さの仮説。** 「誰が・どの瞬間に・何を感じるか」を1文で言い切り、**それが違っていると分かる条件**と、最小コストで確かめる**垂直スライス**の定義までを含む。言い切れなければコンセプト未定として先に進まない |
| 4 | プロセスの形 | **案C: 二段ゲート型**（下記） |

### 採用した案C: 二段ゲート型

**ゲート1「体験の同定」— 実例の中から指差す（帰納）**

漠然とした「こういう感じが欲しい」から始め、近い実例を3〜5本調べ、**その体験が具体的にどの瞬間に生じているかを実例の中で特定する**。ここでは自分の企画を一切書かない。出力は「◯◯というゲームの、この瞬間が欲しい」という**指差し**。

**ゲート2「仮説と反証」— 言い切る（演繹）**

指差した体験に自分のひねりを**1つだけ**加え、「誰が・どの瞬間に・何を感じるか」を1文で言い切る。同時に**反証条件**（これが観測されたら仮説は死ぬ）と、それを最小コストで確かめる**垂直スライス**を定義する。

各ゲートに Stop 条件を置き、**言い切れなければ次に進まない。**

### 案Cを選んだ理由と、退けた案

| 案 | 内容 | 判断 |
|---|---|---|
| **C 二段ゲート型** | 帰納 → 演繹の順序を構造で強制 | **採用。** 直接の敗因が「原理から演繹しただけで実例から帰納していなかった」ことなので、順序の強制が是正になる |
| A 実例先行型 | 実例調査 → 分解 → ひねり → 仮説の一直線 | 不採用。軽いが**オリジナリティの問いに答える工程が無く**、模倣に寄りやすい |
| B 仮説先行→敵対的検証型 | 先に1文を書き、それを殺しにいく | 不採用。速くオリジナリティは出るが、**最初の1文が知識の呪いで測定不能になる**。S1 で実際に起きた失敗（「予告を見て配置を変えたか」が測定不能だった）と同型 |

**重さへの対処**: ゲート1の調査本数を企画の規模で 3本 / 5本と可変にする程度で吸収する方針。

## 3. スキルに載せるべき教訓（これまでの実績から）

新スキルは以下を**構造として**含むこと。いずれも本リポジトリで実際に失敗して得たものである。

| 教訓 | 由来 |
|---|---|
| **実例から帰納する。原理からの演繹だけで設計しない** | #183（S1 レトロ Problem 7） |
| **要約ツールの出力を逐語引用として提示しない。典拠が自説を否定していないか確認する。反証を明示的に探す** | Epic #178 再構成時に MDA 原典の引用を捏造した事故 |
| **作業仮説には反証条件を書く。** 反証条件が無いと、同じ観測が「続行」とも「棄却」とも読めてしまう | S1 レトロ（「環①を繋いだが単調なまま」の非判別性） |
| **事前登録した項目は全部判定に使う。** 判定に使わない項目を混ぜると死角になる | S1（行動記録を CoS に含めず1項目も収集されなかった） |
| **CoS に必ずユーザー実プレイを含める。** AI 観察の数字だけで達成報告しない | S1 最大の Problem |
| **測定可能な言葉で書く（知識の呪いを避ける）** | S1 の成功条件が測定不能だった件 |
| **レイヤー分解は診断には有効だが、作業単位としては不適切** | Epic #178 再構成（L0〜L6 の降格） |
| **テスト全緑・CI 全緑は面白さの証拠にならない** | PR #171 / Falldown Shooter 連鎖崩壊の破棄 |
| **juice（演出）は意味ある決断の欠如を補償できない** | #183 の反証調査 + PR #171 の実績 |
| **No も正当な成果。** 期限を切り、損切り条件を先に定義する | Epic #178 のプロダクトゴール |
