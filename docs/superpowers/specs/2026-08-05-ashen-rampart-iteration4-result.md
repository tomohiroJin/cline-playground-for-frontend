## 4. 数値だけが明かしたこと

## 6. 最終レビューを敵対的検証にして分かったこと

最終の全体レビューは、**4名の独立した反証者がそれぞれ別の視点からブランチを否定しにいく**形で実施した（設計との整合／テストの空虚さ／既存機能の退行／判定の健全性）。

**設計の中核4主張はすべて反証を跳ね返した。** 一意性はカードプールの生データから独立に再計算して14/14を確認、状態バーの4種の意味はドメインの初期化・減算箇所まで追跡、`domain/` の変更ファイル数ゼロ、`MAX_CELL_MARKS` は抑制を外すと実際に落ちる本物のガードであることを確認。

**一方で8件の実欠陥が見つかった。**

### 6.1 最も重かったもの: `run_tally` が1 tick 古い集計を記録していた

決着した tick の `setTally` がまだ反映されていない状態で書き出され、正しい値が届いた次のレンダーではガードが**正しい方を捨てて**いた。

**勝ったランは最終 tick に必ず撃破が入るため、偶発ではなく毎回ずれる。** 実測で鴉の撃破数 13 → 12。

**画面のリザルトは正しく、貼り付けた JSON は正しくない**という最悪の形だった。しかも `rejected` / `unit-lost` / `defeat` は生イベントとしてログに出ていないため、**判定者が手で再導出も照合もできない。間違った数値が唯一の数値になる。**

**この反復が存在する理由の半分が、静かに壊れていた。**

### 6.2 次に重かったもの: 射程リングが半セル分過大だった

ドメインは `hypot(...) <= range` で判定するのに、描画は `range + 0.5` セルの円を描いていた。**届かないマスを「届く」と描いていた。**

`+1` の項は支援塔のオーラ（チェビシェフ距離1の3×3）にだけ正しく、それをユークリッドの射程に流用したのが原因である。

**このブランチで唯一、新しい表現がルールと違うことを述べている箇所であり、しかもこの反復が直すために存在する層（能力・射程）で起きていた。**

### 6.3 その他

- **デッキ構築からコスト表示が消えていた**（退行）。テストが行を `aria-label` で掴んでおり、読み上げ用ラベルにコストが残っていたため緑のまま通っていた
- 能力チップの「クリックで再点火」が、**再点火できない時にしか表示されない**状態だった

## 7. 次の反復への申し送り

### 7.1 次の問いの候補

自由記述と数値が同じ方向を指している。

> **手札を持ち続けるか手放すかの判断が生まれるか。そして、配備が終わった後にも判断が残るか。**

構成要素:

- **溢れによる消失に対価が無い**（§3.1）。23回対1回という比は、手札管理が判断になっていないことの直接の証拠
- **デッキを撃ち切って終わる**（§3.2）。`handRemaining` が5ラン全て空。先を読む意味が無い
- **守り手が壊れない**（§4.1）。建て終わると盤面が完成し、以降の判断が消える
- **コスト4・5 が使われない**（§3.3）。にもかかわらず出ると強すぎる

### 7.2 引き継ぐ観察項目

- **経路上／経路外の配置比率**（§4.2）。5ランで約75%が経路外へ寄っている。反復3の反証条件「二択が成立していない」に近づいている
- **貫通と範囲の軸**（§4.4）。デッキ選択の影響を分離しないと読めない。観察方法を変えるか指標を落とす
- **能力表示の使用回数**（§1.5）。操作案内を足したので、次回が初めての有効な測定になる

### 7.3 未検証のまま残したもの

- **最小幅360pxでの文字の見え方。** 文字を `clip-path` の外へ出したので切られなくなったが、代わりに最小の台座では形からはみ出す可能性がある。実機確認ができていない
- **手札の幅を削る手順（設計 §6.1）。** 360px で手札が1行1枚に折り返しており発動条件を満たしたが、実プレイ評「十分遊べる」により見送った。手順自体が実地で未検証のまま
- **オーラの実効値がチップに反映されない。** 鍛冶場の隣は射程 +0.6、篝火の隣は攻撃 +25% だが、チップは素の値を出す。設計書 §5.2 のチップ表が素の属性を列挙しているため今回はスコープ外とした

## 8. 教訓

### 8.1 前反復から引き継ぎ、今回も有効だったもの

- **判定は「言われなかったこと」で読む。** 2反復連続で、同一人物の正反対の発言が最も強い証拠になった
- **後回しの回数を数える。** #1 は3回持ち越して最上位の不満になった

### 8.2 今回新たに得たもの

**欠陥を直したら、その欠陥の「形」で他の領域も点検する。**
反復2で「計算済みなのに描画されていない」（`TickEvent`）を直したとき、同じ形で `CardType` を点検していれば #6 は1反復早く見つかっていた。

**既にある機能が使われていないなら、原因は「無い」ではなく「届いていない」。**
ログのコピーボタンは2反復前から存在していた。原因は「知らなかった」と「知っていても使いにくかった」の2つで、片方だけ潰しても届かなかった。

**そして、その教訓を書いた同じ反復で、同じ欠陥を出荷した。**
能力表示は5ラン全く発見されなかった。**教訓を文書に書くことと、次に作るものへ適用することは別の作業である。** 新機能を出すときは「これは画面のどこで自己紹介するか」を実装の完了条件に含める。

**表現の問いは、行動を対にして事前登録することで反証可能にできる。**
「分かっていれば減る行動」と「分かっていなければ増える行動」を対にした。項目1（0.67種）と項目4（0回）が同じ向きに出たことで、主観評価だけに依らない判定ができた。ただし項目2 は「減る余地が最初から無い」という形で測れず、**対の片側が床に張り付く可能性を事前に検討すべきだった。**

**「テストが緑」と「保証されている」は別物である。**
このブランチ1本で、名乗った保証を守っていないテストが**9回**見つかった（実装中のレビューで4回、最終の敵対的検証で5件）。パターンは反復する——同じ関数を自分自身と比べるトートロジー、複数要素が持つ文字列への文書全体クエリ、境界だけを見る検証、変更前から真だった条件、ドメインが produce しない値のフィクスチャ。

**最終レビューを敵対的にしたことが決定的だった。**
通常のコードレビューはコードの正しさを見る。だが**このブランチの弱点は「コードが正しくてもテストが守っていない」**という形で、そこは狙って否定しにいかないと出てこない。命題を明示し、「迷ったら否定に倒す」と指示し、視点を4つに分けたことで、**この反復が存在する理由の半分が壊れていたこと**を出荷前に検出できた。
