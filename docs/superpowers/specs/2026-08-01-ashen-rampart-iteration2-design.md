## 1. 前段の結果と、この反復が扱うもの

反復1 の実プレイ判定は「**ゲームとしては要約面白みが出てきました。ですが全体的に弱いしまだまだだということも同時に分かりました**」＝**継続**。

ただし次段階（マップ追加・ボス・物語）へは進まない。挙がった問題は新しいコンテンツを足しても解決しないため。

効いたもの: オンボーディングとカウントダウン（「焦る」の指摘が消えた）。
効かなかったもの: 徴発（機能していない）、魔力炉の枚数（構造的に事故る）。

## 2. この反復の問い

> **盤面で起きていることが、プレイヤーに見えるか。**

反復1 で「配分の問題が毎回同じ形にならないか」には手応えが出た。次に問うのは、**その配分の結果が読めるか**である。読めなければ、当たったのか外れたのかが分からず、配分の判断は学習に繋がらない。

## 3. 既存の表現規約（設計時に必ず参照する）

本反復のデザインレビューで、必須修正4件のうち3件が「**既存コードのコメントに書かれている規約を、設計時に参照していなかった**」ことに起因した。規約がコード中にしか無いと次も同じことが起きるため、ここに転記する。

### 3.1 配色（`presentation/theme.ts`）

> 60-30-10。**赤は危険専用に予約し、枠やパネルには使わない。** 前作は赤を主色に使ったため、リアルタイムで本当の危険を赤で伝えられなくなる問題を抱えていた。

|---|---|---|
| `dominant` | `#1a1614` | 背景・盤面の地（60%） |
| `secondary` | `#e8ded2` | テキスト・枠・パネル（30%） |
| `danger` | `#8b2635` | 危険専用の面（10%） |
| `dangerText` | `#e8737f` | 危険専用のテキスト（背景比 6.15:1） |

**新しい色を増やさない。** 敵側が既に5色（`#8a95a5` / `#f0a830` / `#7f8c8d` / `#9b59b6` / `#5dade2`）を占有しており、`#f0a830`（俊足）は `opportunity` とほぼ同一色相で既に飽和している。

### 3.2 符号化（`presentation/enemy-visual.ts`）

> 敵種を「形 × サイズ × 色」の3重符号で区別する。**色のみに依存すると色覚特性やコントラストで判別できなくなるため、グレースケールでも形とサイズだけで見分けられることを要件とする**（S1 の教訓）。

**新規に追加する視覚表現もこの要件に従う。** 情報を色だけに載せてはならない。

### 3.3 モーション

`styles/GlobalStyle.ts` の `prefers-reduced-motion` 対応は `main[role="main"] > *` のページフェードインのみで、**ゲーム内エフェクトはカバーされていない**。エフェクトを追加する側が自前で対応する。

## 4. 層1 — 盤面で起きていることを描く

### 4.1 中核の問題

`state.events` は毎 tick 丸ごと置き換わる（`stepTick` が `events: []` から作り直す）。しかも `shot` は `towerIndex`、`defeat` は `enemyId` という**参照しか持たない**。次の tick には撃破された敵は `enemies` から消えるため、**イベントを受け取ったその tick のうちに座標へ解決してスナップショットしないと、二度と描けない**。

必要なのは「イベントを描く」ではなく「**イベントを寿命付きのエフェクトに変換して保持する**」層である。

### 4.2 構成

```
domain/combat/step-tick.ts        TickEvent を発行（defeat に撃破源を追加）
        ↓ events
presentation/combat-effects.ts    【新規・純粋関数】
        advanceEffects(prev, state, map) → Effect[]
        ・イベントを座標へ解決（towerIndex → towers[i].pos, enemyId → positionOf）
        ・寿命 untilTick を付ける
        ・寿命切れと超過分を落とす
        ↓ Effect[]
presentation/BoardEffectLayer.tsx 【新規】1枚の <svg> を盤面に重ねる
```

`Effect` はセル座標系のまま保持する。SVG に `viewBox="0 0 9 7"` を与えれば、セル座標をそのまま `<line x1="3" y1="4" ...>` と書ける。`Frame` は `aspect-ratio` 固定のため歪みは出ない。

### 4.3 何を、どう、どれだけの間描くか

| イベント | 描画 | 寿命 | グレースケールでの弁別 |
|---|---|---|---|
| `shot` | 塔→敵の**細い実線**（`secondary`） | 3 tick | 細さ |
| `trap` | 罠セルの縁を `danger` で囲む | 3 tick | 位置 |
| `ember` | `secondary` の円（radius を半径に） | 5 tick | 形 |
| `defeat` | 撃破源→撃破位置の**太い線 + 終端に ✕** | 8 tick | 太さ + 形 |
| `leak` | 砦セルの `danger` 塗り + HUD ライフを同時に `dangerText` へ | 8 tick | 位置 + 連動 |
| `rejected` | **盤面直下**に日本語の理由 | 6 tick | テキスト |

塔の性格差は**線幅と破線パターン**で表す（範囲 = 太実線 / 単体 = 細実線 / 貫通 = 破線）。**塔ごとの色分けは行わない**（§3.1・§3.2）。

味方の攻撃（射撃・燠火）は `secondary`、脅威の顕在化（罠の発動・漏れ）は `danger` に統一する。**`opportunity` はエフェクトに使わない** — `BoardGrid` が既に「再点火可能な燠火」の意味で使っており、同じ色が「今爆発した」と「また使える」を同時に指してしまうため。

撃破の帰属を「撃破源セル → 撃破位置の線」で示すことで、色に依存せず幾何学的接続で伝わる。射撃線（細・3 tick）と撃破線（太・8 tick・✕ 終端）は太さと形で区別する。

### 4.4 ドメイン改修（1箇所のみ）

```ts
export type DefeatSource =
  | { kind: 'tower'; index: number }
  | { kind: 'trap'; index: number }
  | { kind: 'ember'; index: number };

// TickEvent
| { kind: 'defeat'; enemyId: number; source: DefeatSource }
```

`step-tick.ts` のダメージ適用は塔・罠・燠火の3経路に分かれているため、それぞれが「自分が削って 0 にした」と分かる位置で `defeat` を発行する。

**契約: 最後に削った者に帰属する**（オーバーキル分は問わない）。この契約をコード中のコメントに明示する。

### 4.5 制約の定数化

以下を1ファイルに集約する。**反証条件「情報量が過大」に当たったとき、値を動かすだけで次の反復が回るようにするため。**

- `MAX_CONCURRENT_EFFECTS` — 同時表示の上限。超過分は古いものから落とす
- 各イベントの寿命（tick）
- 線幅（細 / 太 / 破線パターン）

塔6基 × クールダウン8 tick では常時1〜3本の線が明滅する。ここに群れ22体が重なる局面があるため、上限は必須。

### 4.6 アクセシビリティ

- `prefers-reduced-motion: reduce` のとき、点滅を**静的表示に置換**する（同じ寿命だけ出しっぱなしにする）。**エフェクトを消してはならない** — 消すと reduced-motion のユーザーだけ判定項目1 が達成不能になる
- `role="status"` `aria-live="polite"` の要素を1つ置き、**撃破と漏れだけ**を日本語テキストで流す。射撃は毎 tick 発生するため除外する（高頻度更新は読み上げが詰まり、かえって情報が失われる）
- SVG は `pointer-events: none`。z 順序は **セル(0) < エフェクト(1) < 敵マーカー(2)**。敵マーカーの HP バー（S1 で絶対スケール化したもの）をエフェクトが覆ってはならない
- `stroke-width` は `vector-effect="non-scaling-stroke"` を使う。`viewBox` 座標系では `stroke-width: 1` がセル1個分の太さになり、盤面幅で見た目が変わってしまうため

## 5. 層2 — 操作が通らない

### 5.1 クールダウンを「盤面に置く札」だけに課す

現状の `applyPlayCard` は**カードを特定する前に**クールダウンを検査している。

```ts
// 現状（step-tick.ts:273）
if (draft.placeCooldown > 0) { rejected('cooldown'); return; }  // カード種別を知らないまま拒否
const cardId = draft.deck.hand[action.handIndex];
```

カード解決後に移し、`placementKindOf(card) !== 'none'` のときだけ検査・設定する。徴発・時泥はクールダウンを**消費も参照もしなくなる**。

これで #197 の「徴発が使えない・選択が出ない」は原理的に解消する。反復1 で徴発が機能しなかったのは、盤面に何も置かないカードが配置制約に縛られていたためで、バグというより**層の取り違え**だった。

### 5.2 拒否理由の表示

`presentation/card-text.ts` に日本語文言を置く。表示位置は**盤面直下**（`BoardWrapper` の内側）。

近接の法則により、フィードバックは原因の近くに置く。「置けない」は盤面をクリックしたときに起きるため視線は盤面にある。手札の上に出すと見落とされる。**手札溢れ通知（原因が手札）とは別枠にする。**

| 理由 | 表示文 |
|---|---|
| `cooldown` | 次の設置まで あと N.N 秒 |
| `mana` | マナが足りない（必要 N） |
| `target` | そこには置けない |
| `occupied` | すでに何かが置かれている |
| `pending` | 徴発の選択が先 |

`cooldown` のみ残り秒数を含める。「あと何秒か分からない」ことが不満の本体であるため。

### 5.3 能動的な捨て札

手札の各札に捨札操作を付ける。**コスト0・クールダウンなし**でいつでも切れる。

溢れた瞬間にモーダルで選択を迫る案は**採らない**。リアルタイムで敵が進軍している最中に選択を迫ると、選択の間もゲームが進んで理不尽になり、止めれば緊張感が消える。反復1 で効いたのがカウントダウン（＝準備の猶予を与える設計）だったことを踏まえ、**溢れる前に自分で整理できる**形にする。

ドメイン改修は `PlayerAction` に `{ kind: 'discard'; handIndex: number }` を1つ追加するのみ。`drawOne` の溢れ処理は現状のまま（コスト0札の保護を含む）。

**捨札はドローを早めない。** ドローは `DRAW_INTERVAL_TICKS = 40` の時間駆動であり、捨てても次のドローは早まらない。したがって「捨てて回す」戦術は成立せず、捨札の効果は**手札の枠を空けること**に限定される。これは意図した設計である（デッキを高速に掘る手段を新設すると、有限デッキという前提が緩む）。

## 6. 層3 — 構造的な窮屈さ

### 6.1 設置マスの規則化

現状は12マスが座標直書き。単に増やすと「置けるが射程が届かない」マスが生まれ、**死にマスを別の形で再生産する**。規則で定義する。

塔の射程は `火砲台 1.5 / 弓兵 1.6 / 徹甲弩 1.8 / 弩砲 2.2 / 投石機 3.0`。主力の下限が 1.5 であるため——

```
buildSlots = 経路から距離 1.5 以内の非経路セル
```

| 規則 | マス数 | 評価 |
|---|---|---|
| 現行（直書き） | 12 | 窮屈 |
| **距離 ≤ 1.5** | **22** | **どのマスからも主力2種が届く** |
| 距離 ≤ 2.0 | 33 | 弓兵・火砲台が届かないマスが出る |
| 距離 ≤ 2.5 | 36 | 同上、さらに悪化 |

**距離 1.5（22マス）を採用する。** 現行の約1.8倍。「増やしたのに置いても無駄だった」という新種の不満を作らず、かつ反証条件「どこでもよくなった」からも遠い（63マス中22マス＝35%）。

残る41マスは**「城壁の外」として背景を明確に変え**、置けないことを一目で示す。反復1 の「置き場所が少ない」は、置けるマスの絶対数だけでなく**置けそうに見えるのに置けない**ことへの不満でもあったため、こちらもセットで手当てする。

高台・滞留セルの位置は変更しない。

**現行12マスは新規則にすべて含まれる**（検算済み。漏れ0マス）。高台2マス `(3,4)` `(7,2)` も含まれる。したがって**マスは純増10のみで、既存の配置が不可能になることはない**。較正のやり直しは「選択肢が増えた方向」だけを見ればよく、退行の確認は不要。

### 6.2 魔力炉のデッキ内上限を撤廃する

`MAX_COPIES = 3` は全カード一律に効いており、コメントには「弓兵スパムを構造的に封じる」とある。目的は攻撃札の偏重防止であって、**マナ源を絞ることではなかった**。副作用として掛かっていた。

`MAX_COPIES` をカード定義の属性にし、魔力炉のみ上限なしとする。他は3枚のままで弓兵スパム防止を維持する。

`DeckBuilder` のバリデーション（`validateDeck`）と枚数表示も、一律の3ではなく**カードごとの上限**を参照するよう更新する。判定はドメイン側に置く既存の方針を維持する。

#### 支配戦略チェック（設計段階での検算）

| 制約 | 値 |
|---|---|
| 魔力炉の産出 | 1マナ / 60 tick |
| 配置クールダウン | 60 tick に1回 |
| 最高コストの札 | 3 |
| **最大消費レート** | **3マナ / 60 tick** |

**盤面の魔力炉は3〜4基で消費レートを完全に飽和させる。** 5基目以降のマナは使い道がない（配置クールダウンが律速するため）。上限を外しても「魔力炉を並べるほど強い」にはならず、構造的に自己制限がかかる。

この検算により、フィードバック #3 の正体が特定できた。**これは盤面に置ける枚数の問題ではなく、引ける確率の問題である。** 盤面の適正枚数は3〜4基で、上限3枚はそこだけ見れば妥当だった。壊れていたのは「20枚中3枚（15%）では、その3〜4基を置くタイミングまでに引けない」というデッキ内比率のほう。

同じ「3」という数字が、盤面制約としては正しく、デッキ構築制約としては誤っていた。ゆえに「上限を外す」は**並べ放題にするためではなく、確実に引くため**の手当てである。

#### 副作用と、その手当て

魔力炉を8枚入れると引く札の40%が魔力炉になり、盤面に4基置いた後の魔力炉は完全な死札になる。ここで §5.3 の能動的な捨て札が効く。**この2つの変更は同じ構造欠陥の表と裏である。**

### 8.1 リザルト画面の集計表示

### 8.3 反証条件（先に定義）

- 撃破・射撃を描画してなお「何が起きているか分からない」→ **描画の問題ではなく情報量そのものが過大**。§4.5 の定数を下げる方向へ
- 拒否理由を出してなお「置けない」が不満として残る → **クールダウン60tick そのものが長すぎる**。値を見直す
- 魔力炉の上限を外してなお事故る → マナ設計そのものを疑う（毎ターン自動供給への回帰も含めて検討）
- 置ける場所を増やして「どこでもよくなった」→ 空間の判断が消えた。希少性と選択肢の母数の均衡点を測り直す
- 3ラン中2ラン以上で「まだ弱い」が続く → **層1〜3 は原因ではなかった**。コンセプトの見直しへ

### 8.4 出口条件

6項目すべてを記録したうえで、**Yes** なら次段階（マップ追加・ボス・物語）へ。**No** ならどの反証条件に当たったかを記録して停止。

## 9. テスト方針

反復1 だけで「テストは緑、緑の理由が誤っていた」型の欠陥が4件出た。今回それが再発しやすい箇所は**エフェクトの寿命**である。

- `advanceEffects` は**ミューテーション検証を必須**とする（寿命を +1 して落ちることを確認）。「3 tick 後に消える」テストが、実は「そもそも生成されていない」ために緑になっていた、という形を防ぐ
- `BoardEffectLayer` は**「`<line>` が n 本ある」を直接数える**。S1 の「滞留セルで矢印が消える」を既存テスト7件が1件も検出できなかった教訓の直接適用。**「情報が存在する」テストと「レンダリングされる」テストは別物である**
- `defeat.source` は**塔・罠・燠火の3経路すべて**について、それぞれ単独で撃破が成立するテストを書く（1経路だけ緑で通る形を避ける）
- `balance.test.ts` は **「全要求充足デッキは勝てる」と「単一カードデッキは勝てない」の両方**を維持する。片側だけでは較正が厳しすぎても検出できない

## 10. バランス較正

層3 で設置マス（12→22）と魔力炉のデッキ内比率が変わるため、プリセット2種の勝率を再測定する。

**敵側の数値は動かさない**（実プレイ判定の直前に難度を動かさない方針の継続）。

あわせて据え置き中の「範囲攻撃なしでも 6/20 で勝てる」較正の緩さを、このタイミングで再検討する（反復1 の判定記録で「層3 の較正やり直し時に併せて再検討する」と記録した項目）。

`createDeck` のシャッフルが入力配列の宣言順に依存し、同一構成でも並べ替えで勝率が 6/20〜11/20 動く既知の性質があるため、較正の測定はプリセットの配列順を固定したうえで行う。

|---|---|---|

## 14. 教訓の適用

本設計は以下を明示的に適用している。

1. **一度診断した欠陥は、実装を書き直すと戻ってくる**（#197 教訓1）→ §3 で既存の表現規約を設計書に転記した。デザインレビューで出た必須修正4件のうち3件が、この転記の不在に起因していた
2. **元ネタから機構を借りるとき、その機構が成立している条件も一緒に借りる**（#197 教訓2）→ §6.2 で MTG の比率をそのまま輸入せず、本作の魔力炉が「土地」ではなく「マナ・アーティファクト」であることを踏まえて検算した
3. **支配戦略チェックは実装前に机上でできる** → §6.2 で実施し、その結果フィードバック #3 の正体（枚数ではなく確率の問題）が特定できた
4. **シミュレーションが測れるのは勝敗であって体験ではない**（#197 教訓3）→ §8.1 で判定項目を画面に出し、実プレイでしか得られない情報を確実に回収する
