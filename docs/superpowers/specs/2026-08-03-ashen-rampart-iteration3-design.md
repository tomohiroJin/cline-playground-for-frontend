## 2. 診断 — 5件は同じ1つの原因に帰着する

コードで裏取りした事実を先に置く。

| 事実 | 該当箇所 |
|---|---|
| `PLACE_COOLDOWN_TICKS = 60` は「盤面に置く札」**全部**に課される（反復2で除外したのは徴発・時泥だけ） | `step-tick.ts:339` |
| 攻撃塔5種のうち**4種がコスト3**に固まる。コスト2の攻撃塔は弓兵のみ | `card-pool.ts` |
| 徹甲弩の「最大HP40以上に2倍」が効く敵は重装のみ。**重装はラン全体で1体しか出ない** | `waves.ts:64` |
| 鴉13体は経路 index **5**（11セル中の中間）から湧く。入口側をカバーする配置は一切効かない | `waves.ts:70` |
| 次ウェーブ予告は「鴉13」のように**種類と数しか出さず、湧き位置を伝えない** | `wave-preview.ts:14` |
| 対空手段は弩砲・徹甲弩・落網の**3種のみ**。鴉13体 > ライフ12 なので全漏らしは必敗 | `card-pool.ts` / `combat-state.ts:124` |

### 2.1 個別に手当てしようとして、成立しないことが分かった

当初はこれらを較正の不備として個別に直す計画を立てた（クールダウンの限定・コスト帯の再配置・飛行の湧き位置変更）。設計の過程で**飛行に位置要求を持たせる案を検算したところ、成立しないことが分かった**。

入口 `(0,3)` から砦 `(8,1)` への直線は `y = 3 − x/4`。地上経路（S字）との**垂直距離は最大 0.75 セル**しかない。塔の射程は最短でも 1.5 なので、2つのレーンの間に置いた塔はどちらにも届く。**飛行専用ルートを作っても位置の判断は生まれない。**

これは反復1で「置ける場所を増やしても射程が届かなければ死にマスの再生産」と判定したのと同じ構造である。

### 2.2 根本原因

3つの発見——4種がコスト3に固まる／徹甲弩の特性が死んでいる／位置要求が成立しない——は、いずれも**タワーディフェンスの設計空間そのものが狭い**ことの現れである。

塔を区別する軸は（射程・ダメージ・攻撃間隔・範囲・対空可否）の5つしかない。そこに5種類を置けば必ず重なる。**コスト帯を組み替えても、狭い空間の中で駒を並べ替えているだけ**であり、次の反復で同じ不満が再発する見込みが高い。

反復1の判定記録には反証条件として「**層1〜3 は原因ではなかった → コンセプトの見直しへ**」を事前登録してある。本反復はそれに当たったものとして扱う。

## 3. この反復の問い

> **前線をどこに敷き、何を捨てるかの判断が生まれるか。**

守り手にHPを持たせ、地上の敵が前線で止まって殴り合う形にする。飛行はそれを飛び越える。設置マスの制約を外し、盤面63マスすべてに置けるようにする。

### 3.1 なぜこれが5件を解くのか

| 解けるもの | 理由 |
|---|---|
| #1 配分の判断 | 置いたものが壊れるので、補充の判断が**ラン中ずっと続く**。今は置いたら終わりなので、クールダウンを外しても判断が働くのは序盤だけだった（§4.2 の算術） |
| #3 カードが似ている | **HPという軸が1本増える**。「硬くて攻撃力が無い」「脆くて火力が高い」が作れる。今は全部「壊れない置物」なのでこの軸が存在しない |
| #4 飛行の理不尽さ | 湧き位置を入口に戻す。前方で迎え撃てるようになる |
| #5 対空の固定化 | 飛行が**ブロッカーを飛び越える**という形で属性要求を表現する。位置要求は盤面の形に依存しなくなる。加えて対空の標準解（弩砲）を1マナ安くする |
| — | 設置マス22という恣意的なリストが消え、制約が「置けるマス」から「**置いた場所の危険度**」に移る |

### 3.2 何を捨て、何が生き残るか

**捨てるもの**

- 設置マス22の規則生成（`buildSlotsNearPath` / `BUILD_SLOT_MAX_DISTANCE`。反復2 Task 9 で作ったばかり）
- `balance.test.ts` の較正資産（プリセット2種の勝率・不変条件の数値）
- 石壁の「40tick足止め」効果（クリーチャー化して壁になる）
- 徹甲弩の「最大HP40以上に2倍」（貫通に置き換える）

**生き残るもの**

- デッキ構築・マナ経済・魔力炉の上限撤廃（#2 で成功と評価された）
- エフェクト層（`combat-effects.ts` / `BoardEffectLayer.tsx`）。**殴り合いが加わるぶん価値が上がる**
- リザルトの2段階表示と `run-summary.ts` の集計基盤（項目は差し替える）
- オンボーディング・カウントダウン（反復1で「焦る」を解消した資産）
- 罠2種・燠火・時泥・徴発
- 高台・滞留セル

### 3.3 このプロジェクトは書き直しで物を失った前科がある

PoC の全面書き直しで `TickEvent` の描画が落ち、反復2でようやく拾い直した。判定記録には「**一度診断した欠陥は、実装を書き直すと戻ってくる**」と教訓が残っている。

**本反復では §3.2 の「生き残るもの」をそのままチェックリストとして扱う。** 実装計画の最終タスクで1項目ずつ目視確認する。

## 4. 戦闘モデル

### 4.1 経路の上か外かが役割を決める

盤面9×7＝63マスすべてに置ける。

| | 経路上（11セル） | 経路外（52セル） |
|---|---|---|
| 地上の敵 | **止める**（殴り合いになる） | 素通りされる |
| 敵からの攻撃 | **受ける**（HP 0 で消滅） | 受けない |
| 飛行 | 無視して通過する | 対空持ちだけが撃てる |
| 攻撃 | 射程内の敵を撃つ | 射程内の敵を撃つ |

**攻撃ロジックは現状の塔とまったく同じである。** 新規実装は「ブロック判定」と「敵の対守り手攻撃」の2つだけで、`step-tick.ts` の射撃・罠・燠火の3経路はそのまま残る。

**すべての守り手がブロックできる。** 石壁は壁の専門家であるだけで、弓兵を経路上に置いて時間を稼ぐこともできる。ここからHPという軸が効いてくる。

高台（火力ボーナス）と滞留セルはそのまま生きる。**滞留セルにブロッカーを置くと、遅くなった敵をさらに止める**という重なりが生まれ、経路上のどこで受けるかが判断になる。

**1セルに置けるのは守り手1体か罠1つのどちらか。** 経路セルでこの2つが競合するため、規則が要る。

### 4.2 なぜクールダウンの撤廃だけでは足りなかったか（算術）

フィードバック#1 への素直な対応は「魔力炉以外のクールダウンを外す」である。これは実施する（§5.1）。しかし**それだけでは判断が序盤にしか生まれない**。

マナ収入は魔力炉N基で `N/60` マナ/tick。消費はドローが40tickに1枚で、デッキ20枚のうち非魔力炉が `20−R` 枚だから `平均コスト × (20−R)/800` マナ/tick。均衡は——

```
R = 1200 × 平均コスト / (800 + 60 × 平均コスト)
```

平均コスト2.5 なら **R ≈ 3.2**。魔力炉3〜4枚で「引いた札を引いた端から置ける」状態になる。それ未満はマナ待ち、それ以上はマナが余って本命の札が減る。**積むほど強くも弱くもならない**という点では健全だが、裏を返せば**終盤はマナが余り、置く先も尽きる**。置いたものが壊れないからである。

守り手が壊れるようになると、この余ったマナに使い道が生まれ、**補充の判断がラン中ずっと続く**。#1 が求めていた「溜めて一気に／少しずつ」の選択が、序盤だけの話でなくなる。

なお反復2のプリセットは魔力炉8枚（40%）だが、これはクールダウンが律速だった前提の値なので較正で組み直す。

### 4.3 同時に殴れる数の上限（構造的な穴とその手当て）

**群れ22体が同時に1体のブロッカーを殴ると、石壁HP60 は 41tick で溶ける**（22体 × 1ダメージ / 15tick = 1.47 dps）。これでは壁が成立しない。

```
MAX_ATTACKERS_PER_BLOCKER = 3
```

1体のブロッカーを殴れるのは**先頭3体まで**。残りは後ろで待つ。これで石壁は約300tick 保つ。

**この上限は副次的にもう1つの問題を解く。** 待たされた敵が経路上に詰まるため、**範囲攻撃が本当に刺さるようになる**。現状は敵が一列に流れていくだけで、範囲攻撃は「たまたま重なったら得」でしかなかった（反復2で群れを8→22体・間隔3→1に増やしてなお、範囲なしデッキが 6/20 で勝てていた理由の一つ）。

### 4.4 ドメイン改修

```ts
// 守り手（PlacedTower を改名）
export interface PlacedUnit {
  cardId: string;
  pos: CellPos;
  hp: number;        // 追加
  maxHp: number;     // 追加
  cooldownLeft: number;
}

// 敵の仕様に攻撃を追加
export interface EnemySpec {
  // 既存: id, name, hp, speed, flying
  attack: number;             // 追加。飛行は 0（素通りするため）
  attackIntervalTicks: number; // 追加
}
```

`step-tick.ts` に加わる処理は2つ。

1. **ブロック判定** — 地上の敵は、**次に進入する経路セルに守り手がいれば、そのセルに進入せず**その場で止まる。既に自分がいるセルに守り手が後から置かれた場合も同様に止まる（置いた瞬間に足元を塞げる）
2. **敵の攻撃** — 止まっている敵は `attackIntervalTicks` ごとに守り手のHPを削る。同一ブロッカーへの攻撃者は先頭3体まで。HP 0 で守り手は消滅し、前進が再開する

**契約: 飛行はブロック判定を通らない。** 飛行の移動ロジックは現状のまま変えない。この契約をコード中のコメントに明示する。

### 4.5 用語

UI・ドメインとも「塔」から**「守り手」**へ改める（`PlacedTower` → `PlacedUnit`、`towers` → `units`）。攻撃しない石壁・魔力炉まで含めて1つの語で呼ぶ必要があるため。

`shot` イベントの `towerIndex` など、反復2で作ったイベント形状も追随して改名する。**エフェクト層の描画そのものは変えない**（§3.2 の「生き残るもの」）。

### 5.1 コスト帯を 0〜5 に広げる

現状は 0・1・2・3 の4帯に14種が詰まり、攻撃塔5種のうち4種がコスト3にあった。改訂後は各帯に役割が1つずつ対応する。魔力炉以外のカードから配置クールダウンを外すため（`card.type === 'reactor'` のときだけ検査する）、**コストが唯一の律速になる**。コスト5の投石機を置くには本当に溜める必要が出る。

### 5.2 HPと攻撃力の逆相関

```
石壁 60/0 → 魔力炉 20/0 → 火砲台 16/12 → 徹甲弩 14/14 → 弩砲 12/9 → 投石機 10/18 → 弓兵 8/4
```

前に出すほど硬いものが要り、後ろに置くほど火力に振れる。**置く場所と札の性格が結びつく**ため、「コスト違いの似たもの」という感覚が構造的に消える。

魔力炉をHP20で経路上に置いて時間を稼ぐ、という使い捨ても選べる。マナを捨てて時間を買う判断である。

### 5.3 対空の税は「+1マナ」に統一する

弓兵1（対空×）と弩砲2（対空○）は同じ単体攻撃の守り手で、差は1マナ。「対空を積むしかない」ではなく「**対空にいくら払うか**」という比較可能な判断になる。徹甲弩4 も対空できるが、それは高火力の副産物である。

### 5.4 徹甲弩を貫通にする

現状の「最大HP40以上に2倍」はラン中1体（重装）にしか効かず、実質的に存在しない特性だった。**守り手から標的へ引いた直線上にいる敵すべてに当たる**メカニクスに置き換える（標的より奥の敵にも当たる）。単体・範囲のどちらとも重ならない3つ目の軸になる。

反復2のエフェクト設計は「範囲=太実線 / 単体=細実線 / **貫通=破線**」と線種を定義済みだが、貫通する塔が存在しないため破線は一度も描かれていない。この実装で初めて使われる。

### 5.5 石壁を罠から守り手へ

「40tick足止め」より「HP60の壁」のほうが本モデルでは素直である。罠は棘罠・落網の2種に減る。

## 6. 飛行

| | 現状 | 変更後 |
|---|---|---|
| 出現位置 | 経路 index 5（中盤） | index 0（入口）＝他の敵と同じ |
| 進む距離 | 中盤以降のみ | 全長11セル |
| ブロック | （ブロックが存在しない） | **無視して通過する** |
| 攻撃 | （攻撃が存在しない） | しない（素通り） |
| 対処 | 弩砲(3)・徹甲弩(3)・落網(2) | 弩砲(**2**)・徹甲弩(4)・落網(2) |

**実装は `spawnPathIndex: 5 → 0` の1文字である。** 飛行レーンの描画も、罠の設置先の分岐も、移動ロジックの改修も要らない（§2.1 の検算により、専用ルートは位置要求を生まないと判明したため）。

位置要求は「飛行がブロッカーを飛び越える」という形で、盤面の形に依存せず成立する。前を厚くしても飛行は素通りするので、対空をどこに置くかの判断が残る。

副作用として**鴉が防衛線に晒される時間が倍以上になる**ため、13体は確実に緩くなる。較正でウェーブ4の構成を組み直す（「対空を無視したら負ける」という保証は数値を変えて維持する）。

## 8. 計測と判定

### 8.1 判定項目の検算

| # | 収集項目 | 取りうる範囲 | 何が分かるか |
|---|---|---|---|
| 1 | ブロッカーを置いた経路位置 | index 0〜10 | 前線をどこに敷いたか。ランごとに変わるか（変わらなければ唯一解） |
| 2 | 失った守り手の数と種類 | 0〜20体 | 0なら壊れなさすぎ、10以上なら消耗戦 |
| 3 | 経路上／経路外の配置比率 | 0〜1 | 0ならブロック未使用（旧TDのまま）、1なら射手が死んでいる |
| 4 | 鴉の撃破位置の平均進捗 | 0〜1 | 前方で迎え撃てたか。1.0 に近ければ砦手前でしか落とせていない |
| 5 | 使わなかったカード種 | 0〜14種 | 軸分けが効いたか |
| 6 | 使ったカードのコスト帯分布 | コスト0〜5 | 安い札と高い札の両方が使われたか |
| 7 | 前回より面白くなったか | Yes / No | 最終判定 |

項目1・3 が本反復の主軸である。項目5・6 は #3 への直接の応答、項目4 は #4 への直接の応答にあたる。

### 8.2 リザルト表示

反復2で作った**2段階表示**（勝敗の理由を記録してから集計を表示する。判定の汚染防止）をそのまま維持し、集計項目だけ §8.1 に差し替える。`run-summary.ts` は純粋関数のまま。

反復2で作った塔別撃破の集計は、守り手別の撃破として引き継ぐ。支援塔2種（篝火・鍛冶場）の貢献集計も維持する。

### 8.3 判定の事前登録

**実施**: 自分で組んだデッキで3ラン。**判定ランのデッキには篝火・鍛冶場・石壁を最低1枚ずつ入れる**（集計行が出ない設計のため。反復2 §8.3 と同じ理由）。

### 8.4 反証条件（先に定義）

- 守り手が3ラン合計で**2体未満**しか壊れない → 壊れにくくしすぎ。敵の攻撃力を上げる
- 1ランで**10体以上**壊れる → 消耗戦になった。HPを上げるかコストを下げる
- 経路上の配置比率が **0.1未満 または 0.9超** → 経路上と経路外の二択が成立していない。片方の役割が死んでいる
- 置いた位置がランごとに変わらない → 前線の位置に唯一解がある。滞留セル・高台の配置を見直す
- 3ラン中2ラン以上で「まだ弱い」が続く → **戦闘モデルを拡張してもなお足りない**。問題はコンセプトの内側ではなく外側（題材・演出・ボリューム）にある

### 8.5 出口条件

7項目すべてを記録したうえで、**Yes** なら次段階（マップ追加・ボス・物語）へ。**No** ならどの反証条件に当たったかを記録して停止。

## 9. バランス較正

較正資産は全面的にやり直しになる。**完了条件を数値の不変条件として `balance.test.ts` に固定する**（反復2の教訓「『再検討する』だけでは曖昧なまま流れる」の適用）。

| 不変条件 | 対照条件 | 閾値 |
|---|---|---|
| 全要求充足デッキ（壁・射手・対空・範囲を含む）の勝率 | — | **12/20 以上** |
| 対空を含まないデッキの勝率 | デッキ構成 | **4/20 未満** |
| **経路上に一切置かない戦略の勝率**（新設） | **戦略** | **4/20 未満** |
| 範囲攻撃を含まないデッキの勝率 | デッキ構成 | **6/20 未満** |

**「ブロックが必要か」はデッキ構成では検査できない。** すべての守り手がブロックできる以上、石壁を抜いたデッキでも弓兵を経路上に置けばブロックは成立してしまう。検査したいのは**行為のほう**なので、`run-simulation.ts` の `greedyStrategy` に「経路外にしか置かない」変種を1つ足し、その勝率を測る。これが緩いままだと、モデルを拡張したのに旧タワーディフェンスとして遊べてしまう。

デッキ構成側の除外は ID のハードコードではなく**スペック述語**で機械的に行う（対空 = `hitsFlying`、範囲 = `splashRadius > 0`）。

両側を同時に課すのは、片側だけでは較正が厳しすぎても緩すぎても検出できないためである（反復1で4回繰り返した欠陥への対策）。

`createDeck` のシャッフルが入力配列の宣言順に依存し、同一構成でも並べ替えで勝率が動く既知の性質があるため、較正の測定はプリセットの配列順を固定したうえで行う。

## 10. テスト方針

過去の反復で繰り返し出た「テストは緑、緑の理由が誤っていた」型の欠陥に対し、今回リスクが高いのは**ブロック判定**である。

- **ブロック判定は3つを別々にテストする**——「敵が止まる」「守り手のHPが削れる」「HP 0 で消滅し前進が再開する」。1つのテストで全部を通そうとすると、どれかがゼロのまま緑になる（反復2 §9 の支援塔2種と同じ構造）
- **`MAX_ATTACKERS_PER_BLOCKER` はミューテーション検証を必須とする**。上限を +1 して結果が変わることを確認する。「3体までしか殴らない」テストが、実は「そもそも殴っていない」ために緑になっていた形を防ぐ
- **飛行がブロッカーを無視することを、ブロッカーを置いた状態で直接検証する**。ブロッカーが無い盤面では自明に通ってしまう
- **貫通は「一直線上の2体以上に当たる」ことを直接数える**。1体に当たるだけでも緑になる形を避ける
- **経路上への配置が UI から到達可能であることを統合テストで担保する**。層ごとのテストが全部緑のまま UI から到達不能だった欠陥が過去に4件ある
- **エフェクト層に「守り手が殴られる」「守り手が消滅する」を追加し、要素数を直接数える**（反復2 §9 の `<line>` を数える方針の踏襲）

### 14.1 本反復で新たに得た教訓

**個別の較正不備が3つ同時に出たら、それは較正ではなく設計空間の問題を疑う。** 本設計は当初、5件のフィードバックを3つの根（配置の律速・カードの軸・対空の窮屈さ）に分けて個別に手当てする計画だった。しかし調査で出た3つの事実——4種がコスト3に固まる／徹甲弩の特性がラン中1体にしか効かない／飛行に位置要求を持たせると検算上成立しない——は、いずれも「塔を区別する軸が5つしかない」という同じ原因から出ていた。個別に直しても、次の反復で同じ形の不満が再発する見込みが高かった。**症状を数えるのではなく、症状が共有している空間の広さを見る。**
