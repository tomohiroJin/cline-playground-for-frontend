## 2. 診断 — 5件は同じ1つの原因に帰着する

コードで裏取りした事実を先に置く。

| 事実 | 該当箇所 |
|---|---|
| `PLACE_COOLDOWN_TICKS = 60` は「盤面に置く札」**全部**に課される（反復2で除外したのは徴発・時泥だけ） | `step-tick.ts:339` |
| 攻撃塔5種のうち**4種がコスト3**に固まる。コスト2の攻撃塔は弓兵のみ | `card-pool.ts` |
| 徹甲弩の「最大HP40以上に2倍」が効く敵は重装のみ。**重装はラン全体で1体しか出ない** | `waves.ts:64` |
| 鴉13体は経路 index **5**（11セル中の中間）から湧く。入口側をカバーする配置は一切効かない | `waves.ts:70` |
| 次ウェーブ予告は「鴉13」のように**種類と数しか出さず、湧き位置を伝えない** | `wave-preview.ts:14` |
| 対空手段は弩砲・徹甲弩・落網の**3種のみ**。鴉13体 > ライフ12 なので全漏らしは必敗 | `card-pool.ts` / `combat-state.ts:124` |

### 2.1 個別に手当てしようとして、成立しないことが分かった

当初はこれらを較正の不備として個別に直す計画を立てた（クールダウンの限定・コスト帯の再配置・飛行の湧き位置変更）。設計の過程で**飛行に位置要求を持たせる案を検算したところ、成立しないことが分かった**。

現行マップの入口 `(0,3)` から砦 `(8,1)` への直線は `y = 3 − x/4`。地上経路（S字）との**垂直距離は最大 0.75 セル**しかない。塔の射程は最短でも 1.5 なので、2つのレーンの間に置いた塔はどちらにも届く。**飛行専用ルートを作っても位置の判断は生まれない。**

これは反復1で「置ける場所を増やしても射程が届かなければ死にマスの再生産」と判定したのと同じ構造である。位置要求は**盤面の形そのもの**から来るものであり、レーンを1本増やす程度では作れない。§6 でステージの形ごと作り直すのはこのためである。

### 2.2 根本原因

3つの発見——4種がコスト3に固まる／徹甲弩の特性が死んでいる／位置要求が成立しない——は、いずれも**タワーディフェンスの設計空間そのものが狭い**ことの現れである。

塔を区別する軸は（射程・ダメージ・攻撃間隔・範囲・対空可否）の5つしかない。そこに5種類を置けば必ず重なる。**コスト帯を組み替えても、狭い空間の中で駒を並べ替えているだけ**であり、次の反復で同じ不満が再発する見込みが高い。

反復1の判定記録には反証条件として「**層1〜3 は原因ではなかった → コンセプトの見直しへ**」を事前登録してある。本反復はそれに当たったものとして扱う。

## 3. この反復の問い

> **前線をどこに敷き、何を捨てるか。**

守り手にHPを持たせ、地上の敵が前線で止まって殴り合う形にする。飛行はそれを飛び越える。設置マスの制約を外し、盤面のほぼ全マスに置けるようにする。そして**進軍路を2レーンに分ける**。

### 3.1 なぜこれが5件を解くのか

| 解けるもの | 理由 |
|---|---|
| #1 配分の判断 | 置いたものが壊れるので、補充の判断が続く。今は置いたら終わりなので、クールダウンを外しても判断が働くのは序盤だけだった（§5.2 の算術） |
| #3 カードが似ている | **HPという軸が1本増える**。「硬くて攻撃力が無い」「脆くて火力が高い」が作れる。今は全部「壊れない置物」なのでこの軸が存在しない |
| #4 飛行の理不尽さ | 湧き位置をレーンの入口に戻す。前方で迎え撃てるようになる |
| #5 対空の固定化 | 飛行が**ブロッカーを飛び越える**形で属性要求を表現する。加えて対空の標準解（弩砲）を1マナ安くする |
| 位置要求の復活 | 2レーンへの配分が空間の判断になる。§2.1 で成立しないと判定したものが、盤面の形を変えることで成立する |

### 3.2 何を捨て、何が生き残るか

**捨てるもの**

- 現行の平原マップ（S字1本の経路11セル）と設置マス22の規則生成（`buildSlotsNearPath` / `BUILD_SLOT_MAX_DISTANCE`。反復2 Task 9 で作ったばかり）
- `balance.test.ts` の較正資産（プリセット2種の勝率・不変条件の数値）
- 石壁の「40tick足止め」効果（クリーチャー化して壁になる）
- 徹甲弩の「最大HP40以上に2倍」（貫通に置き換える）

**生き残るもの**

- デッキ構築・マナ経済・魔力炉の上限撤廃（#2 で成功と評価された）
- エフェクト層（`combat-effects.ts` / `BoardEffectLayer.tsx`）。**殴り合いが加わるぶん価値が上がる**
- リザルトの2段階表示と `run-summary.ts` の集計基盤（項目は差し替える）
- オンボーディング・カウントダウン（反復1で「焦る」を解消した資産）
- 罠2種・燠火・時泥・徴発
- 高台・滞留セルという概念（位置は新マップに合わせて置き直す）

### 3.3 このプロジェクトは書き直しで物を失った前科がある

PoC の全面書き直しで `TickEvent` の描画が落ち、反復2でようやく拾い直した。判定記録には「**一度診断した欠陥は、実装を書き直すと戻ってくる**」と教訓が残っている。

**本反復では §3.2 の「生き残るもの」をそのままチェックリストとして扱う。** 実装計画の最終タスクで1項目ずつ目視確認する。

## 4. 戦闘モデル

### 4.1 経路の上か外かが役割を決める

盤面9×7＝63マスのうち**砦セルを除く62マス**に置ける。内訳は §5.2 の出発点の形で経路上20マス（2レーン計21マスから砦を除く）・経路外42マスとなる。

| | 経路上（20マス） | 経路外（42マス） |
|---|---|---|
| 地上の敵 | **止める**（殴り合いになる） | 素通りされる |
| 敵からの攻撃 | **受ける**（HP 0 で消滅） | 受けない |
| 飛行 | 無視して通過する | 対空持ちだけが撃てる |
| 攻撃 | 射程内の敵を撃つ | 射程内の敵を撃つ |

**攻撃ロジックは現状の塔とまったく同じである。** 新規実装は「ブロック判定」と「敵の対守り手攻撃」の2つだけで、`step-tick.ts` の射撃・罠・燠火の3経路はそのまま残る。

**すべての守り手がブロックできる**（魔力炉を除く。§7.5）。石壁は壁の専門家であるだけで、石壁を使い切った後に弓兵を経路上に出して時間を稼ぐこともできる。

**1セルに置けるのは守り手1体か罠1つのどちらか。** 経路セルでこの2つが競合するため規則が要る。

**砦セルには何も置けない。** 置けると2レーンの合流点を1体で塞げてしまい、分岐の意味が消える（§15 の致命的欠陥①と同じ構造）。

### 4.2 ドメイン改修

```ts
// 守り手（PlacedTower を改名）
export interface PlacedUnit {
  cardId: string;
  pos: CellPos;
  hp: number;        // 追加
  maxHp: number;     // 追加
  cooldownLeft: number;
}

// 敵の仕様に攻撃を追加
export interface EnemySpec {
  // 既存: id, name, hp, speed, flying
  attack: number;
  attackIntervalTicks: number;
}

// 敵はどのレーンを進むかを持つ
export interface ActiveEnemy {
  // 既存: id, enemyId, progress, hp, ...
  laneIndex: number;  // 追加
}
```

`step-tick.ts` に加わる処理は2つ。

1. **ブロック判定** — 地上の敵は、**次に進入する経路セルに守り手がいれば、そのセルに進入せず**その場で止まる。既に自分がいるセルに守り手が後から置かれた場合も同様に止まる（置いた瞬間に足元を塞げる）
2. **敵の攻撃** — 止まっている敵は `attackIntervalTicks` ごとに守り手のHPを削る。同一ブロッカーへの攻撃者は先頭3体まで（§4.4）。HP 0 で守り手は消滅し、前進が再開する

**契約: 飛行はブロック判定を通らない。** ただし落網で地上化している間は通る（§8.2）。この契約をコード中のコメントに明示する。

### 4.3 なぜクールダウンの撤廃だけでは足りなかったか（算術）

フィードバック#1 への素直な対応は「魔力炉以外のクールダウンを外す」である。これは実施する（§7.1）。しかし**それだけでは判断が序盤にしか生まれない**。

マナ収入は魔力炉N基で `N/60` マナ/tick。消費はドローが40tickに1枚で、デッキ20枚のうち非魔力炉が `20−R` 枚だから `平均コスト × (20−R)/800` マナ/tick。均衡は——

```
R = 1200 × 平均コスト / (800 + 60 × 平均コスト)
```

§7 の新プールにおける非魔力炉13種の平均コストは **2.08** なので **R ≈ 2.7**。魔力炉3枚前後で「引いた札を引いた端から置ける」状態になる。それ未満はマナ待ち、それ以上はマナが余って本命の札が減る。

**この式は定常状態のみを表す。** 魔力炉自身が60tickのクールダウンを持つため、R基の展開には `60R` tick かかる（3基なら180tick、8基なら480tick）。立ち上がりのあいだはマナが不足する側に振れる。

積むほど強くも弱くもならない点では健全だが、裏を返せば**終盤はマナが余り、置く先も尽きる**。置いたものが壊れないからである。守り手が壊れるようになると、この余ったマナに使い道が生まれる。

なお反復2のプリセットは魔力炉8枚（40%）だが、これはクールダウンが律速だった前提の値なので較正で組み直す。

### 4.4 同時に殴れる数の上限（構造的な穴とその手当て）

**群れ22体が同時に1体のブロッカーを殴ると、石壁HP60 は 41tick で溶ける**（22体 × 1ダメージ / 15tick = 1.47 dps）。これでは壁が成立しない。

```
MAX_ATTACKERS_PER_BLOCKER = 3
```

1体のブロッカーを殴れるのは**先頭3体まで**。残りは後ろで待つ。これで石壁は約300tick 保つ。

**この上限は副次的にもう1つの問題を解く。** 待たされた敵が経路上に詰まるため、**範囲攻撃が本当に刺さるようになる**。現状は敵が一列に流れていくだけで、範囲攻撃は「たまたま重なったら得」でしかなかった（反復2で群れを8→22体・間隔3→1に増やしてなお、範囲なしデッキが 6/20 で勝てていた理由の一つ）。

### 4.5 用語

UI・ドメインとも「塔」から**「守り手」**へ改める（`PlacedTower` → `PlacedUnit`、`towers` → `units`）。攻撃しない石壁まで含めて1つの語で呼ぶ必要があるため。

**魔力炉は `reactors` 配列のまま統合しない**（§7.5 により経路外専用・HPなしとするため）。`shot` イベントの `towerIndex` など反復2で作ったイベント形状は追随して改名するが、**エフェクト層の描画そのものは変えない**（§3.2 の「生き残るもの」）。

## 5. ステージ — 2レーンへの分岐

### 5.1 なぜ分岐が要るか

**現行の経路は1マス幅の11セル列で、迂回路がない。** ブロックを導入すると、経路上に守り手を1体置けば地上の敵が全員そこで止まる。石壁はコスト1・HP60 で1枚あたり133〜300tick 保つため、**壁を置き続けて対空だけ用意する**のが支配戦略になる。PvZ が5レーンを持つのは偶然ではなく、**単一レーンでブロックを導入すると必ずこうなる**。

**分岐点を1つ作るだけでは足りない。** 入口を共有すると、その共有セルに壁を置けば両方が止まる。**共有してよいのは砦セルだけ**であり、そこには何も置けないようにする（§4.1）。

### 5.2 形

```
入口A (0,2) ── 北レーン（10セル・滞留なし） ──┐
                                              ├── 砦 (8,3)
入口B (0,4) ── 南レーン（12セル・滞留2つ） ──┘
```

| | 北レーン | 南レーン |
|---|---|---|
| セル数 | 10 | 12 |
| 滞留セル | なし | 2つ |
| 性格 | 速く着く。処理が間に合わない | 時間を稼げる。手数を割きにくい |

**レーンは非対称にする。** 対称だと「半分ずつ」が自明解になり、配分が判断にならない。ウェーブごとにどちらへ何を流すかを変えることで、毎回同じ形にならないようにする。

**中央列 `y=3` は経路外のまま、両レーンの射程内に入る。** 中央に射手を集めれば両方を撃てるが、経路外なのでブロックはできない。壁は各レーンに別々に要る。これが「どちらをどれだけ厚くするか」という判断の中身である。

高台（火力ボーナス）は中央列に2マス置く。両レーンに届く希少な枠として奪い合いになる。滞留セルは南レーンにのみ置く。

**具体的なセル列は較正で調整する。** 上記は出発点であり、固定するのは以下の性質である。

- 2つの入口を持ち、**砦セル以外を共有しない**
- 2レーンは**非対称**（長さと滞留セル）
- **経路外に、両レーンへ届く列が存在する**

### 5.3 ドメイン改修

`StageMap` の `path: CellPos[]` を `lanes: CellPos[][]` に変える。`WaveEntry` は `spawnPathIndex` を捨て、**どのレーンに出すか**を持つ。敵は `laneIndex` を持ち、位置解決はレーン配列を引く。

`positionOf` の「経路配列上の進捗」というモデルはそのまま使える。参照する配列がレーンごとに分かれるだけである。

## 6. 飛行

| | 現状 | 変更後 |
|---|---|---|
| 出現位置 | 経路 index 5（中盤） | index 0（レーンの入口）＝他の敵と同じ |
| ブロック | （ブロックが存在しない） | **無視して通過する**（地上化中を除く） |
| 攻撃 | （攻撃が存在しない） | 地上化している間のみ行う（§8.2） |
| 対処 | 弩砲(3)・徹甲弩(3)・落網(2) | 弩砲(**2**)・徹甲弩(4)・落網(2) |

位置要求は「飛行がブロッカーを飛び越える」という形で成立する。前を厚くしても飛行は素通りするので、対空をどこに置くかの判断が残る。

**副作用として、鴉が防衛線に晒される時間が倍以上になる。** 現状の「鴉13体 > ライフ12 だから全漏らしは必敗」という体数の算術は、そのままでは緩くなる。

**保証の形式を先に決める。** 較正では次を満たす数を求める。

> 対空手段を1枚も含まないデッキでは、**飛行の漏れだけでライフが0を下回る**（飛行の体数 > `LIFE_INITIAL`）

体数を増やすか、飛行の出現を複数ウェーブに分けるかは較正で決めるが、**「体数 > ライフ」という形式は維持する**。加えて `balance.test.ts` の飛行単体ウェーブによる直接検証（反復2で導入済み）も維持する。

| 落網 | 2 | — | — | — | — | — | 飛行を120tick 地に落とす |
| 業火 | 2 | — | — | — | — | — | 半径2に8ダメージ、300tickで再点火 |
| 時泥 | 2 | — | — | — | — | — | 200tick すべての敵を40%減速 |
| 徴発 | 1 | — | — | — | — | — | 山札の上3枚から1枚 |

### 7.1 コスト帯を 0〜5 に広げる

現状は 0・1・2・3 の4帯に14種が詰まり、攻撃塔5種のうち4種がコスト3にあった。改訂後は各帯に役割が1つずつ対応する。魔力炉以外のカードから配置クールダウンを外すため（`card.type === 'reactor'` のときだけ検査する）、**コストが唯一の律速になる**。コスト5の投石機を置くには本当に溜める必要が出る。

### 7.2 HPと攻撃力の逆相関

```
石壁 60/0 → 火砲台 16/12 → 徹甲弩 14/14 → 弩砲 12/9 → 投石機 10/18 → 弓兵 8/4
```

前に出すほど硬いものが要り、後ろに置くほど火力に振れる。**置く場所と札の性格が結びつく**ため、「コスト違いの似たもの」という感覚が構造的に消える。

**石壁のデッキ内上限は3枚（`MAX_COPIES`）のまま据え置く。** これが本反復で最も重要な希少性である。壁を3枚使い切った後、2レーンを支えるには**石壁以外を経路上に出すしかない**。ここで初めて「弓兵を壁として捨てるか、後方で撃たせ続けるか」という判断が生まれる。上限を外すと壁が無限になり、§15 の致命的欠陥①が形を変えて戻る。

### 7.3 対空の税は「+1マナ」に統一する

弓兵1（対空×）と弩砲2（対空○）は同じ単体攻撃の守り手で、差は1マナ。「対空を積むしかない」ではなく「**対空にいくら払うか**」という比較可能な判断になる。徹甲弩4 も対空できるが、それは高火力の副産物である。

### 7.4 徹甲弩を貫通にする

現状の「最大HP40以上に2倍」はラン中1体（重装）にしか効かず、実質的に存在しない特性だった。**守り手から標的へ引いた直線上にいる敵すべてに当たる**メカニクスに置き換える（標的より奥の敵にも当たる）。単体・範囲のどちらとも重ならない3つ目の軸になる。

反復2のエフェクト設計は「範囲=太実線 / 単体=細実線 / **貫通=破線**」と線種を定義済みだが、貫通する塔が存在しないため破線は一度も描かれていない。この実装で初めて使われる。

### 7.5 魔力炉は経路外専用にする

魔力炉は**コスト0・デッキ内上限なし**である。これに壁の役割を与えると、**無限に湧く無料の盾**になり、石壁の希少性（§7.2）も壁のコストも意味を失う。

したがって魔力炉は**経路上に置けない**。攻撃を受けないため HP も持たず、`reactors` 配列のまま `units` に統合しない。設計の簡略化としても効く。

### 7.6 石壁を罠から守り手へ

「40tick足止め」より「HP60の壁」のほうが本モデルでは素直である。罠は棘罠・落網の2種に減る。

### 7.7 配置先種別の見直し

`placementKindOf` の `'slot' | 'path' | 'none'` は、設置マスの概念が消えることで意味を失う。次に改める。

| 種別 | 置ける場所 |
|---|---|
| `'unit'` | 砦セルを除く全マス |
| `'reactor'` | 経路外のみ（§7.5） |
| `'path'` | 経路セルのみ（罠・燠火） |
| `'none'` | 配置しない（時泥・徴発） |

## 8. 敵

### 8.1 数値

`EnemySpec` に攻撃を追加する。

| 敵 | HP | 速度 | 攻撃 | 間隔 | 飛行 |
|---|---|---|---|---|---|
| 雑兵 | 20 | 0.1 | 3 | 20 | — |
| 俊足 | 12 | 0.18 | 2 | 12 | — |
| 群れ | 8 | 0.12 | 1 | 15 | — |
| 重装 | 60 | 0.06 | 10 | 30 | — |
| 鴉 | 16 | 0.14 | 2 | 20 | ○ |

**敵の種類は増やさない。** モデル・カード・ステージを同時に動かすため、敵側まで動かすと較正が四重に揺れる。ウェーブの構成（数・タイミング・レーン配分）は較正で組み直すが、種類は5種のまま据え置く。

### 8.2 地上化した飛行の扱い

落網で地に落ちた飛行は、**その間だけブロックの対象になる**（止まる・殴られる・殴る）。

**鴉に攻撃力2を与えるのはこのためである。** 攻撃0のままだと、地上化した鴉がブロッカーの前で止まり、壁を壊せないまま120tick 膠着する。落網が「足止め」として機能してしまい、「落として叩く」という意図と食い違う。攻撃を持たせることで、地上化は**守り手のHPと引き換えに時間を買う**取引になる。

地上化が解けた鴉は、その位置からレーン上の進行を再開する（ブロックは再び無視する）。

## 9. 計測と判定

### 9.1 判定項目の検算

反復2 §8.1 で新設した手続きを全項目に通した。

> **この数値の取りうる範囲は何か。その範囲は、仮説を支持する側と否定する側の両方を含むか。**

| # | 収集項目 | 取りうる範囲 | 何が分かるか |
|---|---|---|---|
| 1 | **2レーンへの配置数の配分** | 0:N 〜 N:0 | どちらをどれだけ厚くしたか。ランごとに変わるか（変わらなければ唯一解） |
| 2 | ブロッカーを置いたレーン内位置 | 各レーンの index | 前線を入口寄りに敷いたか砦寄りか |
| 3 | 失った守り手の数と種類 | 0〜20体 | 0なら壊れなさすぎ、10以上なら消耗戦。**石壁以外を失っていれば §7.2 の判断が働いた証拠** |
| 4 | 経路上／経路外の配置比率 | 0〜1 | 0ならブロック未使用（旧TDのまま）、1なら射手が死んでいる |
| 5 | 鴉の撃破位置の平均進捗 | 0〜1 | 前方で迎え撃てたか。1.0 に近ければ砦手前でしか落とせていない |
| 6 | 使わなかったカード種 / 使ったコスト帯の分布 | 0〜14種 / コスト0〜5 | 軸分けが効いたか。安い札と高い札の両方が使われたか |
| 7 | 前回より面白くなったか | Yes / No | 最終判定 |

項目1が本反復の主軸である。項目3の「種類」は §7.2 の希少性が効いたかを直接測る。項目6は #3 への、項目5は #4 への直接の応答にあたる。

### 9.2 リザルト表示

反復2で作った**2段階表示**（勝敗の理由を記録してから集計を表示する。判定の汚染防止）をそのまま維持し、集計項目だけ §9.1 に差し替える。`run-summary.ts` は純粋関数のまま。

反復2で作った塔別撃破の集計は、守り手別の撃破として引き継ぐ。支援2種（篝火・鍛冶場）の貢献集計も維持する。

### 9.3 判定の事前登録

**実施**: 自分で組んだデッキで3ラン。**判定ランのデッキには篝火・鍛冶場・石壁を最低1枚ずつ入れる**（集計行が出ない設計のため。反復2 §8.3 と同じ理由）。

### 9.4 反証条件（先に定義）

- **1ランあたりの守り手の損失が2体未満** → 壊れにくくしすぎ。敵の攻撃力を上げる
- **1ランで10体以上**壊れる → 消耗戦になった。HPを上げるかコストを下げる
- **失った守り手が石壁だけ** → §7.2 が狙った「石壁以外を壁にする判断」が働いていない。石壁の上限をさらに絞る
- 経路上の配置比率が **0.1未満 または 0.9超** → 経路上と経路外の二択が成立していない
- **2レーンへの配分が毎回ほぼ同じ** → 非対称が効いていない。レーンの差を広げる
- 3ラン中2ラン以上で「まだ弱い」が続く → **戦闘モデルを拡張してもなお足りない**。問題はコンセプトの内側ではなく外側（題材・演出・ボリューム）にある

## 10. バランス較正

較正資産は全面的にやり直しになる。**完了条件を数値の不変条件として `balance.test.ts` に固定する**（反復2の教訓「『再検討する』だけでは曖昧なまま流れる」の適用）。

| 不変条件 | 対照条件の種類 | 閾値 |
|---|---|---|
| 全要求充足デッキ（壁・射手・対空・範囲を含む）の勝率 | — | **12/20 以上** |
| 対空を含まないデッキの勝率 | デッキ構成 | **4/20 未満** |
| **範囲攻撃も貫通も含まない**デッキの勝率 | デッキ構成 | **4/20 未満** |
| **経路上に一切置かない戦略の勝率**（新設） | 戦略 | **4/20 未満** |
| **壁と対空だけを置く戦略の勝率**（新設） | 戦略 | **10/20 未満** |

#### 「範囲攻撃なし」単独では拘束にならない（較正で判明・当初案からの変更）

初稿は「範囲攻撃を含まないデッキ < 6/20」を課していたが、**実測10/20 で成立しなかった。** 群れを22→30 に増やしても南北レーンに分けても 8〜11/20 から動かない。

原因は数値ではなく構造である。**1マス幅のレーンでブロックされた敵は同一座標に縦積みになるため、貫通が範囲攻撃の代わりになる。** 攻撃札の枚数を完全に揃えて3枚だけ入れ替えた測定が、拘束の所在を示している。

| 攻撃札9枚のうち3枚が | 勝率 |
|---|---|
| 火砲台（範囲） | 11/20 |
| 徹甲弩（貫通） | **19/20** |
| 棘罠（どちらでもない） | **0/20** |

拘束されているのは「範囲攻撃を持つこと」ではなく「**群れをまとめて削る手段を持つこと**」だった。したがって不変条件をその形に置き直す。**緩めたのではなく、別の軸で締め直している**（新条件の実測は 0/20）。範囲単独の寄与は相対差のラチェット（全要求充足 − 範囲なし ≥ 3）で監視する。貫通側にも同じラチェットを置く。

**この測定は §7 の想定を1つ崩している。** 設計は「単体・範囲・貫通」を対等な3軸として置いたが、実態は **貫通 > 範囲**（19 vs 11）である。ブロックの導入で敵が縦に詰まることが、`MAX_ATTACKERS_PER_BLOCKER`（§4.4）が狙った「範囲攻撃が刺さるようになる」より先に「貫通が刺さるようになる」を実現してしまった。**実プレイ判定の申し送りとし、本反復では調整しない**（敵側・カード側を判定直前に動かさない方針の継続）。判定で「徹甲弩ばかり使う」が観測されたら、次の反復で貫通の当たり幅かコストを見直す。

**両方向の対照条件を置く。** 「経路上に置かない戦略」だけでは、ブロックが**強すぎる**方向を検出できない。壁で止めて対空だけ処理する戦略が勝ちすぎないことを同時に課す。片側だけでは較正が厳しすぎても緩すぎても検出できない（反復1で4回繰り返した欠陥への対策）。

**「ブロックが必要か」はデッキ構成では検査できない。** すべての守り手がブロックできる以上、石壁を抜いたデッキでも弓兵を経路上に置けばブロックは成立してしまう。検査したいのは**行為のほう**なので、`run-simulation.ts` の `greedyStrategy` に戦略変種を2つ足して測る。

デッキ構成側の除外は ID のハードコードではなく**スペック述語**で機械的に行う（対空 = `hitsFlying`、範囲 = `splashRadius > 0`）。

`createDeck` のシャッフルが入力配列の宣言順に依存し、同一構成でも並べ替えで勝率が動く既知の性質があるため、較正の測定はプリセットの配列順を固定したうえで行う。

## 11. エフェクト層への追加

反復2 §12 は「情報量過大」を筆頭リスクに挙げている。新種を無指定で足さない。

| 新エフェクト | 描画 | 寿命 | 破棄優先度 | `aria-live` |
|---|---|---|---|---|
| `unit-damaged`（守り手が殴られる） | 守り手セルの縁を `dangerText` で点滅 | 3 tick | **最低**（`shot` と同格） | 流さない（高頻度） |
| `unit-lost`（守り手が消滅する） | 守り手セルに `danger` の ✕ | 8 tick | **`leak` の次** | **流す** |

破棄優先度は次に改める。

```
leak > unit-lost > defeat > trap / ember > shot / unit-damaged
```

`aria-live` の基準は反復2 §4.6 のまま——**頻度が低く、かつ取り返しがつかない出来事**を流す。`unit-lost` はこれに該当し、`unit-damaged` は該当しない（要素名ではなく性質で判定している）。

**`danger` の用途を「漏れ専用」から「脅威の実害」へ一般化する。** 反復2 §4.3 は `danger` を漏れ専用と書いたが、その趣旨は「罠のような味方の資産に赤を使わない」ことにあった。守り手の消滅は脅威が与えた実害であり、規約の**趣旨のほうに該当する**。文言ではなく性質で判定した結果として、ここで用途を広げる。罠・味方の行動には引き続き `secondary` を使い、`opportunity` はエフェクトに使わない（反復2 §4.3 のまま）。

`MAX_CONCURRENT_EFFECTS` は据え置きで開始し、反証条件に当たったら下げる。

## 12. テスト方針

過去の反復で繰り返し出た「テストは緑、緑の理由が誤っていた」型の欠陥に対し、今回リスクが高いのは**ブロック判定**である。

- **ブロック判定は3つを別々にテストする**——「敵が止まる」「守り手のHPが削れる」「HP 0 で消滅し前進が再開する」。1つのテストで全部を通そうとすると、どれかがゼロのまま緑になる（反復2 §9 の支援塔2種と同じ構造）
- **`MAX_ATTACKERS_PER_BLOCKER` はミューテーション検証を必須とする**。上限を +1 して結果が変わることを確認する。「3体までしか殴らない」テストが、実は「そもそも殴っていない」ために緑になっていた形を防ぐ
- **レーンの独立をテストする**——片方のレーンを壁で塞いでも、**もう片方の敵が砦に到達すること**を直接検証する。これが緑にならなければ分岐が形骸化している（§15 の致命的欠陥①の再発検知）
- **飛行がブロッカーを無視することを、ブロッカーを置いた状態で直接検証する**。ブロッカーが無い盤面では自明に通ってしまう。地上化中はブロックされることも別に検証する
- **貫通は「一直線上の2体以上に当たる」ことを直接数える**。1体に当たるだけでも緑になる形を避ける
- **経路上への配置が UI から到達可能であることを統合テストで担保する**。層ごとのテストが全部緑のまま UI から到達不能だった欠陥が過去に4件ある
- **砦セルに置けないことをテストする**。置けてしまうと分岐が無意味になる
- **エフェクト層の新種2つは要素数を直接数える**（反復2 §9 の `<line>` を数える方針の踏襲）

### 14.1 「自由配置」の実態を正直に書く

射程は 1.5〜3.0 なので、**射手は経路の近くに置かなければ何もしない**。設置マスの規則（反復2の「経路から距離1.5以内＝22マス」）を撤廃しても、実効的に意味のある配置先は経路の近傍に留まる。

**変わるのは2点だけである。**

1. **経路上にも置けるようになる**（＝ブロックできる）
2. **中央列が両レーンに届く**という新しい空間の意味が生まれる（§5.2）

危険度は「経路上か外か」の**二値**であって連続的な勾配ではない。「制約が置いた場所の危険度に移る」という言い方は実態より強いので採らない。

## 15. 初稿の敵対的検証で検出した13件

初稿（単一経路・魔力炉を壁として使う案）に対する敵対的検証で、以下を検出して本稿に反映した。

### 致命的

**① 壁1枚で地上が完全に止まる（支配戦略）** — 経路が1マス幅の単一列であるため、守り手を1体置けば地上の敵が全員止まる。石壁コスト1・HP60 は1枚で133〜300tick 保ち、魔力炉はコスト0・上限なしで無限の盾になる。**壁を置き続けて対空だけ用意する**のが最適解になり、地上からのライフ損失がほぼ消える。初稿の反証条件（配置比率0.9超）でも較正（経路外のみ戦略）でも検出できなかった。→ **§5 の2レーン分岐**、**§7.5 の魔力炉の経路外専用化**、**§4.1 の砦セル配置禁止**で対応。

### 高

**② ブロッカーの選択が自明** — 同コスト1で石壁HP60 対 弓兵HP8 では、経路上に弓兵を置く理由がない。「殴られながら撃つ」中間の選択が一度も成立せず、盤面が「経路上=石壁／経路外=それ以外」に二分される。→ **§7.2** で石壁の上限3枚を希少性の中核と位置づけ、使い切った後の判断として明示。**§9.1 項目3** で「失った守り手の種類」を測り、**§9.4** に「石壁だけを失っていたら失敗」を反証条件として追加。

**④ 「壊れにくくする」と「判断が続く」が両立していない** — 転換の根拠を「補充の判断がラン中ずっと続く」に置きながら、採用したのは「壊れにくくする」方針で、反証条件も「3ラン合計で2体未満」と低かった。→ 2レーンで壁の需要が倍になること、石壁が3枚しかないことで消耗が実質的に増える。**§9.4** の反証条件を「**1ランあたり**2体未満」に厳しくした。

### 17.1 本反復で新たに得た教訓

**個別の較正不備が3つ同時に出たら、それは較正ではなく設計空間の問題を疑う。** 本設計は当初、5件のフィードバックを3つの根に分けて個別に手当てする計画だった。しかし調査で出た3つの事実——4種がコスト3に固まる／徹甲弩の特性がラン中1体にしか効かない／飛行に位置要求を持たせると検算上成立しない——は、いずれも「塔を区別する軸が5つしかない」という同じ原因から出ていた。**症状を数えるのではなく、症状が共有している空間の広さを見る。**

**機構を借りるときは、その機構が前提としている地形も借りる。** 初稿はブロックという機構を MTG / PvZ から借りながら、**単一レーンの経路という地形はタワーディフェンスのまま**にした。結果、壁1枚で全部止まる支配戦略が生まれた（§15 ①）。PvZ が5レーンを持つのも、MTG で複数のクリーチャーが同時に攻撃できるのも、ブロックという機構が「守り手が足りない状況」を前提にしているからである。**1つの入口しかない地形では、ブロックは常に足りる。** これは反復1の教訓「元ネタから機構を借りるとき、その機構が成立している条件も一緒に借りる」（MTG の土地に枚数制限が無いこと）と同じ形の失敗が、別の機構で再発したものである。
