## 1. コンセプトと判定基準

### コンセプト文（計画の憲法）

> 『灰燼の城壁』は、毎ウェーブの敵予告という「問い」に対し、塔・罠・カードの配置で「解答」を提出し、決定的な自動戦闘という「採点」で読みの当否を答え合わせする、タワーディフェンス版の完全情報パズル・ローグライトである。

### 面白さの仮説（1文・反証可能）

> プレイヤーは予告を読んで「この配置なら守り切れる」という防衛仮説を立て、戦闘でその当否を答え合わせして、読み勝ちの有能感を得る。

実例上の根拠: Into the Breach（完全テレグラフ→実行＝答え合わせ）／Mechabellum（予測→観戦→返し手、因果が legible）／Balatro・Luck be a Landlord（順次可視化される因果）。反証例: The Bazaar・Loop Hero・Backpack Battles（因果不可視・受動観戦は「作業」に堕ちる）。詳細は企画書参照。

### 事前登録する判定項目（すべて最終判定に使う）

| # | 項目 | 記録方法 | 暫定閾値（反復0で較正） |
|---|---|---|---|
| 1 | 予告表示後の配置・カード操作の回数と内訳（ウェーブ平均） | 行動ログ（機械記録）。**「予告を見て変えたか」の直接測定は不可能なため、反復間比較による代理指標であることを明記** | 成功: 反復2前後で行動が有意に変化。反証: 変化なし（暫定: 平均1.0回以上/0.5回未満） |
| 2 | 戦闘を早送り・スキップせず最後まで見たウェーブの割合 | 行動ログ（機械記録） | 成功: 過半。反証: 半数未満 |
| 3 | ラン終了時に勝敗の理由を自分の言葉で1文で書けたか | ゲーム内の任意入力欄（書けなかった事実も記録） | 成功: 3ラン中2ラン以上で記述 |
| 4 | 実プレイ後の主観評（「単調」からの変化） | レトロで Keep/Problem 形式 | 成功: 「単調」評の変化 |

- 閾値は**反復0のベースライン計測後に較正して確定**し、以後動かさない。確定値は新 Epic にコメントで記録する
- **中間反復（1〜2）では棄却判断をしない**。観察記録のみ行い、最終判定は反復3完了後に全項目で行う。ただし中間の「明確に良くなった/悪くなった」兆候は記録し、反復の順序変更の材料にできる

### 反証時の次の一手（事前定義）

最終判定で反証条件が成立した場合、次の順で検討する:
(a) 戦闘中1回介入の導入 → (b) 案C（分岐リスク賭博）への軸足移動 → (c) フェーズ分離自体の再検討

## 2. 反復構造（E2E ブラッシュアップ 4反復）

各反復は「1ラン通しで遊べる状態」を壊さず、体験全体に1つのブラッシュアップを加えて実プレイで確かめる。

1反復のサイクル: 反復 Issue に事前登録 → 実装（TDD）→ `npm run ci` → PR・CI 全緑・マージ → **ユーザー実プレイ3ラン**（ログ自動記録＋勝敗理由1文）→ ログ集計とレトロ（事前登録項目の全判定）→ Issue に結果コメント → 次反復へ。

### 反復0「ベースライン計測」

- 入れるもの: ①行動ログ基盤（節3）②戦闘の早送り（2x/4x）とスキップ。体験の変更はこの2点のみ
- 実プレイ: 現状のゲームを3ラン計測し、**改修前の数値を確定・閾値を較正**
- 出口条件: ベースライン数値の記録と閾値の確定
- 意図: S1 の教訓「実装前ベースライン観察が最大の当たり」の制度化。早送りは判定項目2の**計測装置**として必須

### 反復1「採点を見せる」（因果可視化）

- 入れるもの: `TickEvent`（shot/trap/defeat/leak）の描画 — 射撃線・被弾・撃破・漏れ地点
- 検証する問い: 判定項目3（勝敗理由の言語化）が Yes に変わるか
- 意図: 帰納した3条件のうち「観戦中の因果可視化」を単独検証

### 反復2「問いを立てる」（予告の拡張）

- 入れるもの: 次ウェーブ予告を「敵種×数×到達順×経路」の具体情報に拡張
- 検証する問い: 判定項目1（配置行動）がベースラインから動くか
- 意図: 3条件のうち「観戦前の賭け」を検証。因果可視化が先にあることで「外した理由が分かる→次は読める」の循環が成立する順序

### 反復3「答え合わせを閉じる」（リザルト）

- 入れるもの: ウェーブ/ラン終了時のリザルト（塔別撃破数・漏れ地点・砦ライフ増減）。撃破帰属のドメイン小改修を含む
- 検証する問い: 全項目での**最終判定**。成功なら「面白くなりうるか」に Yes、反証成立なら次の一手へ
- 意図: 問い→解答→採点→講評のループを完全に閉じる

### 順序の根拠と損切り

- 反復1が2より先: 因果が読めない状態で予告だけ増やしても、外れた理由が分からず賭けが成立しない
- 反復は最大4。全反復消化後に Yes/No を必ず出す（**No も正当な成果**）
- 途中で明確な悪化（例: 可視化で観戦がうるさくなり非スキップ率低下）が出た場合のみ、その要素を戻して次へ進む

## 3. 計測基盤の設計（行動ログ）

目的: 判定項目1・2を機械記録にし、一人プレイテストの記憶バイアス・確証バイアスを構造的に排除する。

### アーキテクチャ（feature 内で完結）

- `features/ashen-rampart/application/ports/play-log-port.ts` — `record(event)` / `exportRuns()` のインターフェース
- `features/ashen-rampart/infrastructure/play-log/local-storage-play-log.ts` — localStorage 実装（キー `ashen-rampart:play-log`、ラン ID 単位で追記）
- 記録呼び出しはプレゼンテーション層のフックから。**シミュレーション純粋関数には手を入れない**

### 記録イベント（スキーマ v1）

| イベント | 属性 | 使う判定項目 |
|---|---|---|
| `run_started` | runId, 反復番号（実装バージョンをログに刻む） | 全体 |
| `prep_action` | wave, 種別（配置/撤去/カード使用）, 対象, フェーズ開始からの経過秒 | 1 |
| `wave_started` | wave, 配置済み塔数 | — |
| `battle_speed` | wave, 変更後速度（1x/2x/4x/skip）, 発生時刻 | 2 |
| `wave_ended` | wave, 所要秒, 漏れ数, 砦ライフ増減 | 補助 |
| `run_ended` | 勝敗, 総所要秒, 勝敗理由の1文（任意入力・未記入も記録） | 3 |

### エクスポートと集計

- リザルト画面に開発用「計測ログをコピー」ボタン（JSON をクリップボードへ）
- 集計は毎反復のレトロで AI が JSON を読んで事前登録項目に沿って算出し、生データも Issue に残す

### やらないこと（YAGNI）

サーバー送信／グラフ UI／他ゲームへの汎用化／スキーマの後方互換維持（v1 で反復0〜3を走り切る。変更が要る場合は版数を上げ、混在集計はしない）

### テスト

ポートのモックで「準備フェーズの操作が prep_action として記録される」等をユニットテストで保証。localStorage アダプタは既存 `infrastructure/storage/` のテストパターンに倣う。

## 4. 実装方針

共通: 反復ごとに `feature/ashen-rampart-e2e-<n>` ブランチ → TDD → `npm run ci` → PR → CI 全緑 → マージ → 実プレイ計測。`simulateWave` の決定性（同入力→同 tick 列）は全反復の不変条件。

### 反復0

- 戦闘は事前計算済み tick 列の**再生**のため、早送りは再生間隔の変更のみ（ドメイン変更ゼロ）。スキップは最終 tick へのジャンプ＋結果表示
- ログ基盤は節3の通り

### 反復1

- `simulate-wave.ts` の `TickEvent` を再生時に描画。射撃線は盤面グリッド上の SVG オーバーレイ、被弾・撃破はマーカーの状態変化。**新規 Canvas 層は導入しない**（tick 駆動の離散描画で足りる。air-hockey の教訓を回避）
- `shot.towerIndex` は fix `6f53d328` で `board.towers` と 1:1 保証済み。この契約を前提にする
- テストは S1 の教訓を適用: **「イベントが存在する」テストと「レンダリングされる」テストを分ける**。「shot イベントを含む tick を再生したとき射撃線要素が DOM に現れる」まで検証する

### 反復2

- ウェーブ定義は決定的な事前データ。`WavePreview` に「敵種×数×到達順×経路」を流す。ドメインには純粋な読み取り関数の追加のみ
- 表現は PR #180 の方針を踏襲: 絵文字に意味を託さず、凡例と日本語ラベルで索引を付ける

### 反復3

- 唯一のドメイン改修: `defeat` イベントに撃破源 `source: { kind: 'tower' | 'trap'; index }` を追加し、`kill()` の呼び出し元から源を渡す。帰属の正しさは新規テスト＋ミューテーション検証（源を故意に壊して落ちることを確認）で保証
- 集計は `domain/combat/summarize-battle.ts`（tick 列 → 塔別撃破数・漏れ地点の**純粋関数**）とし、プレゼンテーションから直接 import（純粋関数のため規約上許可）

### E2E（Playwright）と性能

- 反復2完了時点で「予告を読む→配置→戦闘→リザルト」のユーザーストーリー E2E を1本追加（毎反復の書き換えはしない）。E2E はローカル実行不可のため CI で確認
- 4x 再生時は tick 進行が最速 60ms 間隔程度。射撃線は表示中イベントの差分更新とする（React の key 設計で対応。計測して問題なければ単純実装のままで可）

## 制約・既存資産の扱い（企画書から確定）

- 決定的自動戦闘シミュレーション＝温存・中核化（採点の土台）
- 空間パズル機構（射程希少化・高台・滞留・かがり火）＝温存（仮説の変数）
- 可読性改善（PR #180）＝強化・拡張（因果可視化は本計画の心臓部）
- フェーズ分離・4カードタイプ・マナ・デッキ＝温存
- 純粋観戦＝**条件付き温存**（答え合わせが成立すれば維持、反証なら介入機構を検討）
- 演出（juice）単独の追加は禁止。すべての可視化要素は「これによってプレイヤーの次の配置が変わるか」を問い、変わらない要素は実装しない
