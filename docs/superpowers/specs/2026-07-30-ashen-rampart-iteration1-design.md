# 灰燼の城壁 反復1 設計書 — ランごとに違う配分の問題になるか

> 2026-07-30 策定。Issue #194。前段は PoC（Issue #192 / PR #193）で仮説 **Yes** 判定。
> 既存設計書: `2026-07-29-ashen-rampart-realtime-deck-poc-design.md`（本書はその差分）

## 1. 前段の結果と、この反復が扱うもの

PoC の実プレイ3ランで、仮説「プレイヤーは有限の札を今切るか温存するかで配分し、切り時の判断が当たった／外れたことを実感して面白がる」は **Yes** と判定された。

> 良い点: 確実にゲームは面白くなった／緊張感とリアルタイム性が素晴らしい／**カード運も重要だけどデッキ配分も重要ということを知る、いい感じ**

同時に挙がった3つの問題を本反復で扱う。

| # | 指摘 | 本書での扱い |
|---|---|---|
| 1 | 毎回同じカードだと、クリア不可の場合に何もランダム性がない | §3 シード可変化 ＋ §2 の「徴発」 |
| 2 | 何の説明もカウントダウンもなしだと焦る | §4 オンボーディング |
| 3 | デッキ配分も重要だと分かるが、カードデッキが悪い気がする | §2 カード拡張 ＋ §5 デッキ構築 UI |

## 2. この反復の問い

> **ランごとに違う配分の問題を出せるか。**

「配分が面白い」ことは判定済みなので、次に問うのは**その配分が毎回同じ形にならないか**である。同じ問題が繰り返されるなら、配分は一度学習した時点で作業になる。

### 2.1 なぜカードデッキが悪く感じたのか（構造的原因）

PoC のカードは8種、同名上限3枚、デッキ20枚。**8 × 3 = 24 枚が上限なので、20枚デッキは4枚落とすだけ**になる。これは既存設計書 §5.1 に「既知の限界」として明記した意図的な妥協だった。

さらに深い原因がある。**カウンター要求に対する答えが1枚しかない要求が2つある。**

| カウンター要求 | PoC での答え | 帰結 |
|---|---|---|
| 飛行（鴉） | **弩砲のみ** | 必ず積む。選択の余地なし |
| 群れ（範囲要求） | **火砲台のみ** | 同上 |
| 重装（単体高火力） | 弓兵・弩砲 | 兼用可 |
| 俊足（テンポ） | 時泥・前方配置 | 2つある |

必須枠が2つある状態でデッキ20枚を組むと、自由に選べる枠がさらに減る。**カードを増やすだけでは必須枠は消えない。必須になっている要求に「別の答え」を作ることでしか消えない。**

## 3. カードを14種に拡張する（＋6）

### 3.1 設計原則

**必須枠になっている要求に「別の答え」を作る。単に強いカードを足さない。**

既存設計書 §7 の原則「最高効率のカードには必ず効かない相手を作る」は維持する。追加カードもすべて「効かない相手」を持つ。

### 3.2 追加する6種

| カード | ID | コスト | 種別 | 効果 | 何の別解か |
|---|---|---|---|---|---|
| 落網 | `snare-net` | 2 | 罠 | 踏んだ**飛行**敵を 120 tick のあいだ地上化する（地上化中は地上専用の塔・罠が当たる）。ダメージなし・3体まで | **飛行**（弩砲の代替） |
| 投石機 | `catapult` | 3 | 塔 | 範囲2・8 dmg / 24 tick、射程 3.0。地上のみ | **群れ**（火砲台の代替） |
| 徹甲弩 | `piercer` | 3 | 塔 | 単体 7 dmg / 10 tick、射程 1.8、飛行可。**最大HP 40 以上の敵には 2 倍** | **重装**（弓兵物量の代替） |
| 石壁 | `stone-wall` | 1 | 罠 | 踏んだ地上敵を 40 tick 足止め。ダメージなし・3体まで | **テンポ**（時泥の代替） |
| 鍛冶場 | `forge` | 2 | 設置 | 隣接8近傍の塔の**射程 +0.6**。攻撃しない | 篝火（火力+25%）と対 |
| 徴発 | `levy` | 1 | 即時 | **山札の上から3枚を見て1枚を手札に加え、残り2枚を墓地へ** | 引き運への対抗 |

### 3.3 各カードの「効かない相手」

原則を全14種に通すための確認表（既存8種は前設計書 §7 の表を継承）。

| カード | 効かない相手・制約 |
|---|---|
| 落網 | 地上敵には無意味・ダメージゼロ・使い切り |
| 投石機 | 飛行・単体高HP。DPS/マナ **0.111** で最低 |
| 徹甲弩 | 低HP敵に非効率。DPS/マナ 0.233（雑兵相手なら弓兵 0.375 に劣る） |
| 石壁 | ダメージゼロ・地上のみ・使い切り |
| 鍛冶場 | 単体では0ダメージ |
| 徴発 | 盤面に何も残らない・山札が2枚以下だと効果が薄い |

**弩砲の記述を訂正（実装中に発見）**: 前設計書 §7 は弩砲を「効かない相手なし。代わりに DPS/マナ が最低クラス」と書いていたが、**これは PoC 時点ですでに誤り**だった（当時も 弓兵0.375 > 弩砲0.277 > 火砲台0.223 で、最低は火砲台）。14種になった今は 弩砲0.278 が5種中2位で、最低は投石機0.111。

「汎用性の代償として効率を犠牲にする」という原則の意図は正しいが、**弩砲ではその犠牲が数値として実現していない**。実害はコスト3・単体攻撃・同名3枚上限、および Task 9 の四不変条件で抑えられていると判断し、**数値は変えず文言のみ実態に合わせる**（ユーザー裁定）。実プレイで弩砲が強すぎると感じられた場合は次の反復で数値を見直す。

### 3.4 支配戦略チェック（設計段階での検算）

DPS/マナ（塔のみ、基礎値）:

| 塔 | DPS | /マナ | 適用範囲 |
|---|---|---|---|
| 弓兵の塔 | 0.750 | **0.375** | 地上のみ |
| 弩砲 | 0.833 | 0.278 | 制限なし |
| 徹甲弩 | 0.700（HP40+ は 1.400） | 0.233（同 **0.467**） | 制限なし。低HP敵に非効率 |
| 火砲台 | 0.667 | 0.222 | 地上のみ・範囲1 |
| 投石機 | 0.333 | 0.111 | 地上のみ・範囲2・射程3.0 |

弓兵は単体効率で依然最高だが飛行に当たらない。徹甲弩は重装相手だけ弓兵を上回るが雑兵相手では劣る。**効率の順位が敵によって入れ替わる**ため、単一の最適解が存在しない。

**必須枠の解消**:
- 飛行への答え: 弩砲 / 落網 / 徹甲弩 の **3つ**
- 群れへの答え: 火砲台 / 投石機 の **2つ**

### 3.5 新しい機構（実装が必要なもの）

追加6種のうち4種は既存の仕組みで表現できるが、2種は新しい状態が要る。

| 機構 | 内容 | 影響範囲 |
|---|---|---|
| **地上化**（落網） | `ActiveEnemy` に `groundedUntilTick: number` を追加。飛行判定を `spec.flying && tick > groundedUntilTick` に変える | `combat-state.ts` / `step-tick.ts` の全飛行判定箇所（射撃・範囲・罠・業火） |
| **足止め**（石壁） | `ActiveEnemy` に `stunnedUntilTick: number` を追加。`moveEnemies` で移動量をゼロにする | `combat-state.ts` / `step-tick.ts` の `moveEnemies` |
| **射程加算**（鍛冶場） | `TowerSpec.aura` を `{ towerDamageBonus?: number; towerRangeBonus?: number }` に拡張。射程算出を `effectiveRange` に集約 | `card-definition.ts` / `step-tick.ts`（`effectiveDamage` と同じ形で `effectiveRange` を新設） |
| **選択ドロー**（徴発） | 山札の上3枚を提示し1枚を選ばせる。**リアルタイムを止めない**ため、選択待ちの間もゲームは進む | `deck.ts` に `peekTop(deck, n)` / `takeFromPeek(deck, index)`。UI に選択オーバーレイ |

> **徴発の選択待ちについて**: 選択中にゲームを止めると「実質的な一時停止でマナを稼げる」抜け道になり、リアルタイム性の設計が崩れる。止めない。選択しないまま次の tick が進むのは許容し、選ぶまで盤面上部に選択肢が出続ける。**選択を放置している間も敵は進む**ため、これ自体がテンポの判断になる。

> **徴発と手札上限の関係（実装中に訂正）**: 当初「徴発を出した時点で徴発自身が墓地へ移るため手札に空きがあり、選んだ札は上限で溢れない」と書いたが、これは**選択が即座に行われる場合にしか成立しない**。「選択中もゲームを止めない」という設計により、選択を保留しているあいだも通常ドローが動いて空いた枠が埋まるためである。
>
> したがって**選択時に手札が上限に達していたら、選んだ札も墓地へ送る**。既存の「出さないと引けない」原則（手札溢れ）と一貫し、かつ**選択を放置すると損をする**のでテンポの判断が強まる。手札は必ず上限で頭打ちになり、手札 UI がレイアウトを前提にできる。
>
> 山札が3枚未満の場合は、残っている枚数だけを提示する（0枚なら効果なしで墓地へ）。

## 4. シード可変化

| 項目 | 内容 |
|---|---|
| 既定 | **毎ラン新しいシード**（`Date.now()` 由来） |
| 表示 | 現在のシードを画面に常時表示（再現できることが分かる形で） |
| 固定 | デッキ構築画面のシード入力欄に値がある場合のみ、そのシードで開始。空欄なら毎回ランダム |
| ログ | `run_started.seed` に実際に使った値を記録（既存のまま） |

PoC ではシード既定値が `1` に固定されており、明示的に変えない限り毎ラン同じドロー順になっていた。これは判定手順（同一シード2ラン＋別シード1ラン）を成立させるために可変にした仕様の副作用で、**計測のための仕様が遊びを壊していた**。判定が終わったので既定を可変にする。

固定機能は残す。反証条件の検証と、バグ再現のために必要。

## 5. オンボーディングとカウントダウン

リアルタイムの緊張感は良い点として評価されているため、**それを殺さない範囲**に留める。

### 5.1 開始前オーバーレイ

ラン開始前に静止した状態で表示する。内容:

- 目的: 砦を守る（敵を通すとライフが減り、0で敗北）
- 操作: カードを選んで盤面に置く／燠火はクリックで再点火／スペースで一時停止（閲覧のみ・配置不可）
- 第1ウェーブの予告

「開始」ボタンで進む。2回目以降のランではスキップできる（`localStorage` に既読フラグ）。

### 5.2 カウントダウン

開始ボタン後、盤面が見える状態で **3 → 2 → 1**（各 30 tick）。

- この間、**敵は出現しない**
- この間、**配置は可能**（初手を置く猶予）

> カウントダウン中に配置を許すのが要点である。禁止すると「見ているだけの3秒」になりリアルタイム性の良さを削る。許せば「最初の1枚をどこに置くか」を落ち着いて決める猶予になり、焦りだけが減る。

実装上は `CombatState` に `countdownLeft: number` を持ち、`stepTick` は `countdownLeft > 0` の間、出現とウェーブ進行だけを止める（配置・マナ生成・ドローは動く）。

> **較正への影響（見落としやすい）**: カウントダウンは 90 tick あり、その間もマナ生成とドローが動く。つまりプレイヤーは**敵が出る前に約2回のドローと数マナを得る**。これは実質的な難度低下であり、§8 のバランス較正に影響する。カウントダウンを入れたあとで較正テストが通ることを必ず確認し、緩くなっていれば敵数で調整する。
>
> 代替案として「カウントダウン中はマナ生成とドローも止める」も検討したが、それだと初手を置くマナが増えないため猶予の意味が薄い。**動かす方を採り、較正で吸収する。**

## 6. デッキ構築 UI（ブリーフィング）

| 項目 | 内容 |
|---|---|
| 導線 | ラン開始前。オーバーレイ（§5.1）の前段 |
| ルール | 14種から **20枚ちょうど**、同名 **3枚まで**（既存の `DECK_SIZE` / `MAX_COPIES`） |
| カード表示 | 名前・コスト・効果・**効かない相手**・選択枚数（＋/−） |
| 全体表示 | 合計枚数（20/20）・コスト曲線（コスト別の枚数） |
| 補助 | 既存2プリセットを「たたき台として読み込む」ボタン |
| 検証 | 20枚ちょうどでないと開始できない |
| ログ | `run_started` にデッキ構成を記録 |

**検証はドメインに置く**: `domain/cards/deck-builder.ts` に `validateDeck(cards): DeckValidation` を新設し、UI と CI の両方から使う。UI 側でだけ検証すると、テストが通るのに UI で組めないデッキが生まれる。

### 6.1 「効かない相手」を UI に出す理由

14種から20枚を選ぶ画面は読む量が多く、**情報量が過大だと選べなくなる**。§3.3 の「効かない相手」を各カードに明示することで、「何のために積むか」の手がかりを与える。これは §3.1 の設計原則をプレイヤーに開示することでもある。

コスト曲線を出すのは、既存設計書 §4.2 の検算（魔力炉の数と平均コストが釣り合う必要がある）をプレイヤーが自力で行えるようにするため。

## 7. 判定の事前登録

**記録する項目はすべて判定に使う。判定に使わない項目は記録しない。**

**実施**: 自分で組んだデッキで3ラン。**シードは毎ラン変わる**ため、ラン間比較は「同じ問題への対応」ではなく「違う問題への対応」を見る。

| # | 収集項目 | 何が分かるか |
|---|---|---|
| 1 | **ランごとに配置構成が変わったか**（`card_played` の種別と座標） | シードが変われば違う配分の問題になっているか。毎回同じ塔ばかりなら、カードを増やしても選択が潰れている |
| 2 | **使われなかったカード種**（デッキ構成 − 墓地の内訳 − `run_ended.handRemaining`） | 増やしたカードのうち一度も選ばれないものがあるか。あるなら役割が無い |
| 3 | **「クリア不可の引き」が起きたか**（`run_note`） | シード可変化で理不尽が減ったか、逆に増えたか |
| 4 | **徴発を使ったか、使って引きが改善したか**（`card_played` と直後の `card_drawn`） | 引き運への対抗手段が機能しているか |
| 5 | **開始時に焦ったか**（主観） | オンボーディングとカウントダウンが効いたか |
| 6 | **主観判定** — 前回より面白くなったか Yes/No | 最終判定 |

### 反証条件（先に定義）

- 3ラン中2ラン以上で配置構成がほぼ同じ → **カードを増やしても配分の幅が広がっていない**。カード設計が「別の答え」になっていない。増やす方向を見直す
- 増やした6種の半分以上が一度も使われない → 役割が無いカードを足しただけ。コスト効率か適用範囲の設計をやり直す
- 「クリア不可の引き」が3ラン中2ラン以上 → シード可変化がむしろ理不尽を増やした。マリガンや初手保証を検討（既存設計書 §12.2 の引き受けたリスクの見直し）
- デッキ構築に時間がかかりすぎて億劫になる → 情報量が過大。プリセット読み込みを既定にするなど導線を見直す
- カウントダウンを入れても焦る → 情報量そのものが過大。既存設計書 §9.1 のグループ化を見直す

### 出口条件

6項目すべてを記録したうえで、**Yes** なら次段階（マップ追加・ボス・物語）へ。**No** ならどの反証条件に当たったかを記録して停止する。

## 8. バランス較正

カードが8種→14種になり、`domain/combat/balance.test.ts` の前提が変わる。

**必須**: 支配戦略の回帰テストを**新カードにも拡張する**。前コンセプトを殺したのは「最効率カードに効かない相手がいない」ことであり、カードを増やす作業はその欠陥を再導入する最大の機会である。

- 単一種類に偏ったデッキ（魔力炉3＋各カード17）で勝てないことを、**新カード6種すべてについて**検証する
- `cardsPlayed > 5` の前提アサートを添え、マナ枯渇で自明に負けたのではないことを保証する（PoC で実際にこの穴があった）
- 難度の較正が崩れたら、テストを緩めず敵数で再較正する。3箇所（`waves.ts` / `waves.test.ts` / `balance.test.ts`）を同時更新する

### 8.1 較正結果（Task 9 実施・Task 14 反映）

`COUNTDOWN_TICKS`（90tick の開始猶予）を追加した結果、「素直な戦略でも全敗ではない」が
全滅（survived=0）になったため、実際に `waves.ts` を調整した。

- **敵の総HP**: 728（`balance.test.ts` の `較正の基準値` で固定値として検証）
- **敵の総体数**: 51（雑兵計13・俊足2・群れ22・重装1・鴉13）
- **LIFE_INITIAL**: 10 → **12**（カウントダウン追加後の全滅を解消するため）
- **鴉**: 10 → **13**（`LIFE_INITIAL`(12) を上回る数にし、「対空を無視すると必ず負ける」を漏れなく保証）
- **群れ**: 8 → **22**、`spawnIntervalTicks` 3 → **1**（密な同時侵入にし、「範囲攻撃を無視すると必ず負ける」を保証。旧8体では単体攻撃のみの合法デッキでも life9残しで楽勝できていた）
- **brute**: 2 → **1**、ウェーブ4の雑兵: 5 → **3**（鴉・群れの強化ぶんの帳尻合わせ。難度較正の主対象は鴉・群れ以外に限定する方針）
- 実測（`greedyStrategy` によるシミュレーション）: 素直な戦略での勝率は過半数以下（配分の余地が残っている）、かつ全敗ではない（理不尽ではない）。プリセット2種（速攻型・重厚型）の勝敗差は3ラン以内

## 9. 作らないもの（YAGNI）

- マップ追加・分岐経路・ボス（Yes 判定後）
- 物語・演出強化
- 魔力炉の暴走（既存設計書 §10 の将来案）
- デッキの保存・複数スロット（1つ組めれば判定できる）
- カードのレアリティ・アンロック進行

## 10. 既知のリスク

- **14種から20枚を選ぶ認知負荷**。反証条件に接続済み（億劫になるなら導線を見直す）
- **地上化と足止めの状態追加で `stepTick` が再び肥大化する**。PoC で一度分割した（`applyActions` / `moveEnemies` / `applyTraps` / `applyTowerShots` 等）ので、新機構もその粒度に収める
- **飛行判定が `spec.flying` の直接参照から関数経由に変わる**。既存の判定箇所（射撃・範囲巻き込み・罠・業火）をすべて置き換える必要があり、1箇所でも漏れると「地上化した敵に当たらない」または「飛行敵に当たる」が起きる。**漏れを検出するテストを機構ごとに用意する**
