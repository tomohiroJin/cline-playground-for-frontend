## 2. 診断 — 現状の構造

コードで確認した事実。

| 領域 | 現状 |
|---|---|
| マップ | **1種のみ**（`PLAINS_MAP`。9×7・2レーン） |
| ウェーブ | **4本の固定台本**（`PLAINS_WAVES` は定数。シードが効くのはデッキのシャッフルだけ＝**敵側はラン間で完全に同一**） |
| カード | 14種（同名3枚上限。ただし魔力炉のみ `maxCopies: DECK_SIZE`） |

### 2.1 「敵側がラン間で完全に同一」は判定を歪めていた

反復5 の判定記録 §4.6 が実測している——3ランは8分間の1セッションで、
**ウェーブ台本は3ランで完全に同一**（`wave_preview_shown` の tick も内容も一致）。
判定者の「慣れてきているので敵が弱く感じた」は、
**同じ台本を8分で3回続けた直後の発言**である。

### 2.2 「デッキ20枚が毎ラン完全消費される」が骨格を決めている

判定記録 §3.4 の実測——3ランとも出した＋手動の捨札＋溢れ ＝ **20枚ちょうど**。
山札は tick 680 で尽き、決着は 1146〜1162。
**供給が尽きてから 466〜482 tick の猶予がある。**

その結果、勝った2ランは**ラン全体の20〜28%を入力ゼロ・被害ゼロで通過して勝っている**（§4.7）。

### 2.3 支配デッキが成立している（設計前提の破れ）

判定記録 §4.3 の実測。

| デッキ | greedy | offPathOnly |
|---|---|---|
| 塔だけ20枚（魔力炉5・弓兵3・篝火3・徹甲弩3・投石機3・弩砲3） | **20/20** | **12/20** |
| 速攻型プリセット | 13/20 | 1/20 |
| 重厚型プリセット | 8/20 | 0/20 |

`card-pool.ts` は「同名3枚上限と併せて単一の支配戦略が成立しない」と主張していたが、
**魔力炉だけ同名上限が無い**（`maxCopiesOf('reactor')` が `DECK_SIZE`）ため成立している。

## 4. 遠征の骨格

### 4.1 形

ローグライト。**3ステージ連続**。

- ライフは遠征を通じて**持ち越す**（ステージクリアで一部回復）
- 盤面の設置物はステージごとに**リセット**
- **負けたら遠征終了**。獲得したカードも失う
- ステージ間で**3択から1枚を獲得**（獲得は2回、デッキは 12 → 13 → 14）

```
構築（12枚） → 層1 → 獲得（3択） → 層2 → 獲得（3択） → 層3 → 遠征結果
                 ↓敗北            ↓敗北            ↓敗北
                              遠征終了（獲得も失う）
```

### 4.2 レイヤ

`CombatState` は**1ステージの戦闘**を表すものとして今のまま残し、その上に遠征の層を新設する。
`CombatState` を拡張して複数ステージを持たせる案は採らない
（`step-tick.ts` は既に990行あり、遠征の関心を混ぜると追跡不能になる）。

```
domain/expedition/
├── stage-definition.ts   StageDefinition（層・マップ・ウェーブ台本の組）
├── stage-pool.ts         6ステージ（層1〜3 × 各2）
├── stage-draw.ts         シードから各層1つを選ぶ（決定的）
├── acquisition.ts        獲得候補3枚の抽選と、選択の適用
└── expedition-state.ts   ExpeditionState と遷移

application/use-cases/
├── start-expedition.ts
├── advance-stage.ts
└── acquire-card.ts
```

`domain/expedition/` は `domain/board`・`domain/combat`・`domain/cards` を参照するが、
**逆向きの参照は作らない**（`CombatState` は遠征を知らない）。

### 4.3 状態

```ts
export type StageTier = 1 | 2 | 3;

export interface StageDefinition {
  id: string;
  name: string;
  tier: StageTier;
  map: StageMap;
  waves: readonly WaveDefinition[];
}

export type ExpeditionPhase = 'stage' | 'offer' | 'ended';

export interface ExpeditionState {
  seed: number;
  stages: readonly StageDefinition[];   // 抽選済みの3ステージ（層1→2→3）
  stageIndex: number;
  deckCards: readonly string[];         // 遠征を通じて育つ（初期12 → 14）
  life: number;                         // 遠征を通じて持ち越す
  offer: readonly string[];             // 獲得の3択。空なら提示なし
  acquired: readonly string[];
  phase: ExpeditionPhase;
  outcome: 'running' | 'cleared' | 'failed';
}
```

`createCombatState(deck, waves)` を `createCombatState(deck, waves, initialLife)` に変え、
遠征から持ち越したライフで開始する。**ステージクリア時の回復量は初期値 +3 とし、較正で動かす**（§8）。
初期ライフは現行の `LIFE_INITIAL = 12` を出発点にする。どちらも段階D の較正対象である。

### 4.4 決定性を壊さない（**必須条件**）

反復5 の判定を救ったのは「`seed` ＋ `deckCards` ＋ `card_played` だけでランを完全再生できる」性質である。
初版判定記録の因果の主張は、この再生によって覆された。**遠征でもこれを維持する。**

遠征シード1つから `SeededRandom` を1本作り、**固定の順序**で消費する:

```
ステージ抽選(3回) → ステージ1のシャッフル → 獲得1の3択抽選
                 → ステージ2のシャッフル → 獲得2の3択抽選
                 → ステージ3のシャッフル
```

**プレイヤーが3択のどれを選ぶかは乱数を消費しない。**
よって `seed` ＋ 各獲得の選択 ＋ 操作列で遠征全体が再生できる。

**DoD に「遠征の完全再生テスト」を入れる。**

### 4.5 デッキ12枚が、支配デッキ問題を構造的に解く（§2.3 への回答）

`card-pool.ts` の docstring が、魔力炉を無制限にした理由を明記している:

> 20枚中3枚(15%)ではマナ基盤が確立する前にランが進んでしまっていた

**12枚デッキなら3枚は25%である。** よって `maxCopies: DECK_SIZE` の例外を外し、
魔力炉も `MAX_COPIES = 3` に揃える。塔だけデッキは「魔力炉3＋攻撃塔5種×3」で最大18枚となり、
**12枚枠では成立しない**（魔力炉3を入れると攻撃塔は9枚＝3種だけ）。

**ただし「解けた」とは主張しない。** 較正ハーネスの `offPathOnly` で
12枚デッキ空間の支配戦略を探索し、実測で確かめる（§8 の不変条件4）。

### 4.6 獲得が必ず見られることの保証

初期12枚・ドロー間隔40 tick なら山札は `40 × (12 − 初期手札3) = 360 tick` で尽きる。
1ステージを 420〜560 tick に設計するので、**プレイヤーは毎ステージ、デッキのほぼ全枚数を引く。**

つまり **獲得した1枚は次のステージでほぼ確実に手札へ来る。**
「機能は画面で自己紹介させる」（反復4 の教訓）を、UI の説明文ではなく**構造**で満たす。

判定項目2（獲得札が使われたか）が床に張り付いた場合、
原因を「引けなかった」ではなく「選ばれた／使われなかった」に絞り込める。

副次的に、反復5 で数値に残った**無操作の尾（ラン全体の20〜28%）**も短くなるはずである。
山札枯渇から決着までの窓が 466〜482 tick → **60〜120 tick** に縮むため。

| 層 | ステージ長 | デッキ | 枯渇 tick | 窓 | 窓の比率 |
|---|---|---|---|---|---|
| 1 | 420 | 12枚 | `40 × (12−3) = 360` | 60 | 14.3% |
| 2 | 500 | 13枚 | `40 × (13−3) = 400` | 100 | 20.0% |
| 3 | 560 | 14枚 | `40 × (14−3) = 440` | 120 | 21.4% |

判定項目5 で測る。

## 5. コンテンツ

### 5.1 盤面サイズは 9×7 で固定し、経路の形で差を作る

マップの多様性を**盤面の寸法**ではなく**レーン数・経路形状・高台・滞留**で作る。

理由: `layout-constants.ts` と「最小幅360px の実機確認」（持ち越し2回・未検証）に
新しい未検証項目を積み増さないため。寸法まで動かすと、判定で出る不満が
「マップの違い」なのか「表示崩れ」なのか**切り分けられなくなる**。

### 5.2 6ステージ（層ごとに2つ、要求する軸が違う）

| 層 | ステージ | 長さ | 経路 | 要求する軸 |
|---|---|---|---|---|
| 1 | **隘路** | 約420 tick / 2ウェーブ | 1レーンの直線 | ブロックと単体処理 |
| 1 | **涸れ沢** | 約420 tick / 2ウェーブ | 2レーン・どちらも短い | 配分（左右に割る判断） |
| 2 | **石切場** | 約500 tick / 3ウェーブ | 2レーン・高台多め | 群れ（範囲 **または** 貫通） |
| 2 | **鴉の谷** | 約500 tick / 3ウェーブ | 2レーン・滞留2 | 対空 ＋ ブロック |
| 3 | **城下** | 約560 tick / 3ウェーブ | **3レーン** | 配分 ＋ 摩耗 ＋ 対空。**盾衛**が出る |
| 3 | **灰の丘** | 約560 tick / 3ウェーブ | 2レーン・長距離 | 持久 ＋ 優先撃破 ＋ 群れ。**癒し手**が出る |

層ごとに1つを抽選するので **8通りの遠征**が成立する。
層で難度を保証するため、**抽選が難度カーブを壊さない。**

既存の `PLAINS_MAP` は**層2「鴉の谷」の原型**として作り直す
（現行の4ウェーブから鴉・重装を軸に3ウェーブへ再構成）。

### 5.3 新敵2種

| id | 名前 | 新機構 | 要求するもの |
|---|---|---|---|
| `warden` | **盾衛** | **装甲**: 受けるダメージから一定値を引く（最低0） | 数の手数ではなく**重い一撃**。弓兵(4)は装甲5に通らず、投石機(18)・徹甲弩(14)・弩砲(9)が要る |
| `mender` | **癒し手** | **回復**: 一定間隔で周囲の敵のHPを回復（`maxHp` を超えない） | **優先撃破**。放置すると前列が落ちない |

`EnemySpec` に `armor?: number` と `heal?: { amount; intervalTicks; radius }` を足す。

**盾衛は支配デッキへの構造的な回答でもある。** §4.5 のデッキ縮小と合わせて、
弓兵を並べるだけの戦略が層3 で通らなくなる。

**回復の処理順は tick 内で固定する。** 既存の順序に組み込み、`stepTick` の決定性を壊さない。
決定性は §4.4 の再生可能性の前提なので、これは**実装の必須条件**である。

### 5.4 新カード5種 — 3種を獲得専用にする

| id | 名前 | コスト | 効果 | 入手 |
|---|---|---|---|---|
| `sniper-nest` | **狙撃櫓** | 4 | 射程3.5・単体28ダメージ・間隔45 | **獲得専用** |
| `repair-hammer` | **修復槌** | 2 | 隣接する守り手を60tick ごとに HP+6 回復（オーラ） | **獲得専用** |
| `war-banner` | **鼓舞旗** | 3 | 隣接する守り手の攻撃間隔 −20%（オーラ） | **獲得専用** |
| `frost-trap` | 氷結罠 | 2 | 踏んだ地上敵を80tick 完全停止・3回 | 構築可 |
| `scatter-turret` | 散弾櫓 | 3 | 射程1.4・**射程内の最大3体**に7ダメージ・間隔14 | 構築可 |

数値はすべて**較正で動かす対象**である（§8）。

**獲得専用の実装**: `CardDefinition` に `acquireOnly?: boolean` を足し、
`deck-builder` の選択肢と `PRESET_DECKS` から除外する。獲得の抽選プールには含める。
同名上限（`MAX_COPIES = 3`）は獲得でも守り、既に上限まで持つ札は提示しない。

- **獲得専用3種が、獲得の自己紹介になる。** 構築画面で見たことのない札が3択に出るので、
  「これは獲得でしか手に入らない」が説明文なしで伝わる
- **散弾櫓は4本目の攻撃軸**（単体／範囲／貫通／**多目標**）
- **修復槌は反復5 の敗因への回答**。摩耗（敵の射程攻撃）で守り手が壊れることに対し、
  初めて対抗手段が入る

オーラは既に篝火（攻撃力）・鍛冶場（射程）があり、鼓舞旗（間隔）・修復槌（回復）で4種になる。
**「オーラの実効値がチップに出ない」（持ち越し2回）はここで無視できなくなるので、この反復で閉じる。**

### 5.5 敵の射程を可視化する（持ち越し1回・§6.3 の教訓）

反復5 の唯一の敗北の原因は「対空2基が北の地上敵の射程内にあり、鴉の襲来中に壊された」ことだった。
判定記録の結論:

> **摩耗を入れるなら、摩耗の可視化（射程リング）を同じ反復で出す。別々の反復に分けたことが、今回の唯一の敗北の原因である。**

反復6 は盾衛（射程持ち）を追加するので、**可視化は同反復で必須**である。

実装: **カード選択中、盤面に「敵の攻撃射程が届きうる経路外セル」を警告色で示す。**
射程を持つ敵が通るレーンセルから `attackRange` 以内の経路外セルは、
マップとウェーブが決まれば確定するので**静的に事前計算**でき、tick ごとの再計算は不要。

同時に、選択中のカード自身の射程も出す（既存の `RangeOverlay` の拡張）。

### 5.6 能力表示（`InspectPanel`）の決着（持ち越し2回）

`inspectOpens` は2反復連続でゼロ。原因は判定記録 §4.2 で**仕様と確定**している
（`useAshenRampartGame.ts:460` — カード選択中は `clickCell` に抜けるため開けない）。
申し送りは「畳むか導線を変えるかを**決める**」だった。

**決定: 畳まず、導線を §5.5 の射程オーバーレイへ寄せる。**

- 「置く前に知りたい」の本体は §5.5 で満たす（カード自身の射程 ＋ 敵の射程が、選択中に同時に見える）
- 設置済みの守り手の性能は `InspectPanel` を開かずとも常設チップに出す（§5.4 のオーラ実効値と同じ作業）
- `InspectPanel` 自体は残すが、**判定項目からは外す**（3回目の持ち越しにしない）

### 5.7 プリセットデッキの作り直し

`PRESET_DECKS`（速攻型・重厚型）は20枚構成なので、**12枚版へ再構成**する。

プリセットが弱いと「引き運ではなくプリセットの弱さで連敗する」ため、
較正で踏破率の差を実測して決める（§8 の不変条件5）。

**注意: 配列の並び順にも意味がある**（`createDeck` のシャッフルは入力配列の順序に依存する）。
較正の測定は宣言順そのままで行い、順序を変えたら `balance.test.ts` を必ず再実行する。

## 6. 作らないもの（YAGNI）

| 項目 | 理由 | 持ち越し回数 |
|---|---|---|
| メタ進行（遠征をまたぐ解放・永続強化） | 永続化・解放管理・進行画面が乗り、反復6 の規模が倍になる | 0（新規） |
| ステージ台本のシード生成（手続き生成） | 較正ハーネスの前提が揺れる。§5.2 の抽選で多様性は足りる | 0（新規） |
| 盤面サイズの可変化 | §5.1。表示崩れと多様性が切り分けられなくなる | 0（新規） |
| ストーリー・シナリオ | 反復3 #3 から継続。コンテンツの器ができてからのほうが載せやすい | **3回目** |
| 敵に向かっていくカード（出撃ユニット） | 反復3 #5 から継続。新しい移動体の概念が要る | **3回目** |
| 最小幅360px の実機確認 | 反復4 §7.3 から継続。§5.1 で盤面寸法を固定したので緊急度は上がっていない | **3回目** |
| 手札の幅を削る手順の実地検証 | 反復4 §7.3 から継続 | **3回目** |

**3回持ち越した項目が最上位の不満になった前例がある**（反復1〜3 のデザイン全面見直し）。
上表の**3回目が4件ある**ことを、反復7 の設計時に必ず読むこと。

## 7. 計測と判定

### 7.1 測れないことを先に宣言する（反復5 §5.5 の教訓）

較正ハーネス（`greedyStrategy`）の癖は既知である——ほぼ経路上に置き、札を抱えない。
**さらに反復6 では「獲得を選ぶ」概念が原理的に存在しない。**

| 測る対象 | 測定器 | 測れるか |
|---|---|---|
| 各ステージ層が**どの軸を要求するか** | 較正ハーネス | **測れる**（対照デッキで20シード） |
| 難度が層で単調に上がっているか | 較正ハーネス | **測れる**（層ごとの勝率） |
| **獲得が判断になったか** | 較正ハーネス | **測れない**。実プレイのログ＋主観のみ |
| **違いに合わせて手を変えたか** | 較正ハーネス | **測れない**。同上 |

**ハーネスで測れないものに、ハーネスの不変条件を立てない。**

### 7.2 baseline

反復5 の3ラン（判定記録 §1.2・§4.7・§4.8）。
ただし**構造が変わるため、直接比較できるのは項目5・項目6 だけ**である。

| 項目 | 反復5 の実測 |
|---|---|
| 無操作の尾 | 235 / 321 / 284 tick（ラン全体の 20.3% / 28.0% / 24.4%） |
| マナ余剰（tick 680 以降の `card_played.mana` 平均） | 8.2 / 13.0 / 9.0 |
| 最後の1手の残マナ | 10 / 15 / 10 |
| 獲得に関する数値 | **存在しない**（機構が無いため baseline なし） |

### 7.3 事前登録する8項目

**判定項目の番号は必ず「反復6の判定項目N」と反復名込みで書くこと。**
番号は反復ごとに振り直されるが、ログのフィールドは積み上がって残るため、
番号だけを書くと別の反復の項目と衝突する（反復5 で実際に起きた）。

実プレイは **3遠征**（各3ステージ、合計最大9ステージ）。

| # | 項目 | **測る瞬間** | 指標 | 事前予測 |
|---|---|---|---|---|
| 1 | 獲得の提示が遠征ごとに違うか（**機構の前提確認**） | `card_offered` の各回（遠征あたり2回） | 3遠征6回で提示された札の異なり数 | **10種以上**（§7.3.2） |
| 2 | **獲得した札が実際に使われたか** | 獲得**後**のステージの `card_played` | 獲得札のうち以後1回以上出された割合 | 6回中4回以上 |
| 3 | **ステージ間で手が変わったか** | 各 `card_played` 時（同じ札の `card_drawn` との差） | 同一遠征内で複数ステージに登場した札の「**引いてから出すまでの遅延**」の、ステージ間の差（中央値） | **段階D の較正で baseline を実測し、閾値を確定して本設計書へ追記する**（§7.3.1） |
| 4 | 難度が層で上がっているか | 各ステージ決着時 | ステージごとのライフ減少量 | 層1 < 層2 < 層3 が3遠征中2遠征以上 |
| 5 | 無操作の尾（反復5 から継続） | 各ステージの `endTick − lastPlayTick` | **ステージ長に対する比率**（絶対 tick ではない） | 全ステージ平均が **15% 未満**（baseline 20〜28%。§7.3.3） |
| 6 | **マナの余剰**（反復5 で測るべきだったのに測らなかった） | 各ステージの `card_played.mana` 平均 ／ 最後の1手の残マナ | 同左 | 最後の1手の残マナが baseline（10/15/10）より小さい |
| 7 | 遠征の踏破 | 遠征終了時 | 3遠征中、3ステージ踏破は何回か | 3遠征中1〜2回 |
| 8 | 主観 | 遠征終了後 | §7.4 の**事前登録した文面**で問う | — |

**項目7 の予測が「1〜2回」なのは、ローグライトとして全勝も全敗も較正の失敗だからである。**
3遠征とも踏破なら易しすぎ、0回なら難しすぎ。

#### 7.3.1 項目3 はなぜ「配置」でも「札の種類」でもなく「遅延」なのか

素朴な候補を2つとも棄却した。**どちらも、手を変えたこと以外のものを測ってしまう。**

| 候補 | なぜ棄却したか |
|---|---|
| **隣接ステージ間の配置セルの重なり率** | **マップの形が違えば自明に低くなる。** 層1「隘路」は1レーン、層2「石切場」は2レーン、層3「城下」は3レーンで、置ける場所そのものが違う。測れるのは「地形が違うこと」であって「手を変えたこと」ではない |
| **出した札の種類の集合の重なり率** | **自明に高くなる。** §4.6 のとおりプレイヤーは毎ステージ12〜14枚のデッキをほぼ全部引き、ほぼ全部出す。集合は毎ステージほぼ同一になる |

**残るのは「同じ札を、いつ出したか」である。**

`card_drawn` と `card_played` の tick 差（＝**引いてから出すまでの遅延**）は、
**ドロー順の違いに影響されない**（各札を、その札が手札に来た瞬間から測るため）。
適応はここに出る——対空札を「鴉の谷」では即出しし、「石切場」では温存する、という形で。

**測る瞬間の設計**（反復5 §3.4 の教訓）: ステージ開始からの経過ではなく、
**その札が手札に来た瞬間からの経過**を測る。前者はドロー順を測ってしまう。

**閾値を今ここに書かない理由**: 遅延の baseline がまだ存在しない（獲得も遠征も新規機構であり、
反復5 のログからは導けない）。反復5 は計画に根拠のない閾値（`>= 12/20`）を書いて実測11 で外した。
**段階D の較正（`greedyStrategy` で8通り×20シード）で遅延の分布を実測し、
閾値を確定してから本節へ追記する。** 追記は**実プレイ判定の前**に行う——
これを守らなければ事前登録ではなくなる。

**交絡の残り**: 遅延は「迷い」だけでなく「マナ不足で出せなかった」でも伸びる。
そのため項目3 は単独では読まず、**項目6（マナ余剰）と対で読む**（§7.6）。

#### 7.3.2 項目1 の「10種以上」の根拠

獲得の抽選プールは19種（既存14 ＋ 新規5）。3遠征 × 2回 = 6回の提示で **18枚**が提示される。
19種から18回引けば、異なり数の期待値は約 `19 × (1 − (18/19)^18) ≈ 11.8` 種になる
（同名上限と既所持による除外があるため実際はやや下がる）。

**10種は「抽選が機能していれば容易に超える」水準として置いた下限である。**
下回るなら抽選か除外規則にバグがあり、**項目2 以降は評価できない**（§7.6 の対の設計）。
これは達成度ではなく**機構の前提確認**であり、超えても反復6 の成果ではない。

#### 7.3.3 項目5 の「15% 未満」の根拠

反復5 の実測から比率で導く。

| | 反復5 | 反復6 の設計値 |
|---|---|---|
| 山札枯渇から決着までの窓 | 466〜482 tick ／ ラン長の **約40%** | §4.6 のとおり **14.3〜21.4%** |
| 実際の無操作の尾 | 235〜321 tick ／ **20.3〜28.0%** | ← 予測する対象 |
| 尾 ÷ 窓 | **0.50〜0.70** | 同じ比率が保たれると仮定 |

窓が 14.3〜21.4% に縮み、尾÷窓 が反復5 と同じ 0.50〜0.70 なら、尾は **7.2〜15.0%** に収まる。
**15% はその上端である。** これを超えるなら、尾は窓の縮小では説明できず、
別の原因（ステージ後半に出す札が無い、マナが枯れている）を疑う。

**注意: これは構造から出る予測であり、成果ではない。** ステージが短くなれば尾も短くなるのは
半ば自明なので、**項目5 単独では出口条件に使わない**（反証条件4 も主観との連言で組んである）。

### 7.4 主観は文面ごと事前登録し、中立に問う

反復5 は「事前に決めた切り分けを判定者に問う」と判定記録に書いたが、
**設計書に切り分けは一行も事前登録されていなかった**（判定記録 §1.7）。
数値を見た後に切り分けを思いつき、事前に決めたと書いた。**これは数値の誤りより重い。**

**以下の文面をそのまま使う。言い換えない。**

1. 「今回の3ステージは、それぞれ違う戦いでしたか／同じでしたか／どちらとも言えませんか」
2. 「カードを選ぶ場面は、遠征にどう影響しましたか。影響が無かったならそう答えてください」
3. 「前回と比べて、面白くなりましたか／変わりませんか／悪くなりましたか」

**切り分けも事前登録する:**

- **項目2 が予測を下回った場合**、問い4「獲得で選んだ札を、その後の戦いで使いましたか。
  使わなかったならなぜですか」で「使えない札だった」と「獲得の存在に気づかなかった」を切り分ける
- **項目4 が単調でなかった場合**、問い5「3つのステージのうち、いちばん苦しかったのはどれですか」で
  難度の体感順を取る（数値の順と一致するか）

**主観の回答は必ずログの記録経路に載せる。**
反復5 は判定を確定させた発言と次の方向を決めた発言の両方が
口頭＝検証不能な経路で入っていた（判定記録 §2）。

### 7.5 反証条件（すべて連言。単独指標に載せない）

反復5 は項目3 単独なら誤った No を出していた。「かつ」で書いていたため助かった（判定記録 §3.4）。

| # | 条件 | 判定 |
|---|---|---|
| 1 | 項目3 が3遠征とも閾値を下回る（遅延がステージ間で変わらない） **かつ** 主観1 が「同じ戦いだった」 | **No**（ステージの多様性が不成立） |
| 2 | 項目1 は成立している **のに** 項目2 が6回中2回以下 **かつ** 主観2 が「影響しなかった」 | **No**（獲得が判断になっていない） |
| 3 | 項目4 が3遠征とも単調でない **かつ** 主観3 または問い5 に難度への不満が出る | **No**（難度カーブが不成立） |
| 4 | 項目5 が baseline（20〜28%）から下がっていない **かつ** 主観に「配備が終わると暇」が出る | **No**（§4.6 の構造的な主張が外れている） |
| 5 | 3遠征とも**層1で敗北** | **評価不能**（較正の失敗。No ではない） |
| 6 | 3遠征とも踏破 **かつ** 主観3 に「易しい」が出る | **評価不能**（較正の失敗。No ではない） |

### 7.6 対の設計

- **項目1 と項目2 は対で読む。** 項目1 が満たされないなら項目2 は評価できない
  （提示が毎回同じなら、選ばれないのは提示の問題）
- **項目3 と主観1 は対で読む。** 遅延が変わっていても本人が「同じ戦い」と感じたなら、
  変わったのは出す順序であって戦いではない
- **項目3 と項目6 は対で読む。** 遅延はマナ不足でも伸びる（§7.3.1 の交絡）。
  遅延が伸びた区間でマナが余っていれば「温存＝判断」、枯れていれば「出せなかった＝制約」である。
  **この切り分けを飛ばして項目3 だけで判断しない**
- **項目5 と項目6 は対で読む。** 尾が縮んでもマナが余ったままなら、
  縮んだのはステージが短くなったからで、経済が変わったわけではない

### 7.7 床に張り付くリスクの事前検討

| 項目 | 床に張り付く条件 | そのときどう読むか |
|---|---|---|
| 2 | 獲得札が全て使われない | §7.4 の問い4 で切り分ける。**指標の失敗ではなく機構の失敗**として読む |
| 3 | 遅延が全ステージで 0 に張り付く（引いた札を即出しし続ける） | **これは床ではなく所見である。** マナが余っているのに即出しなら「判断が生まれていない」＝反証条件1 の入力。マナが枯れているなら「出せる札から出すしかない」＝経済側の問題として反復7 へ送る。**項目6 で切り分ける** |
| 5 | ステージが短いので尾も短い（自明） | **比率で測る**（絶対 tick ではなく、ステージ長に対する割合） |

### 7.8 出口条件と、満たさないときの帰結

**出口条件（連言）:**

> 反証条件のいずれにも当たらず、**項目2 と項目3 が床から離れ**、主観3問が肯定。

**満たさない場合の帰結（反復5 の設計書に無かったもの）:**

> **反復6 は No として記録し、次の反復は新しい問いへ進まない。
> 同じ問いのまま、判定記録が特定した箇所だけを直して再判定する。**

反復5 は合格条件だけを定義したため、違反を正直に記載してそのまま次段階へ進んだ。
**正直さが手続きの代替物として消費される構造**を、ここで塞ぐ。

### 7.9 継続観察（判定項目にはしない）

判定記録 §5.2 から引き継ぐ。

- **山札枯渇時の手札の中身とマナ余剰**（枚数だけでは足りない）
- **経路への関与率**（守り手だけの `placedOnPath` とは別に、罠を含めた比率）
- **隣接ステージ間の配置セルの重なり率**（§7.3.1 で判定項目から棄却したが、記録は続ける。
  マップの形が違えば自明に低くなるので、**単独で達成の証拠に使わない**）
- **鴉の撃破位置**（反復5 は baseline を全面的に下回っていた）
- **北レーンのマーカー重なり**（反復5 は観察が成立していない＝**未観測**。継続）

**観察対象の時間帯にプレイヤーの入力が無いなら、それは「実害なし」ではなく「未観測」である。**

## 8. 較正

### 8.1 現行の不変条件5本は全面やり直し

`balance.test.ts` は「単一ステージ・20枚デッキ」前提なので、そのままでは使えない。

| # | 不変条件 | 測り方 |
|---|---|---|
| 1 | **各ステージが宣言した軸を実際に要求する** | ステージごとに、その軸を抜いた対照デッキで20シード。勝率が落ちること |
| 2 | **層の難度が単調** | 同一デッキで 層1 > 層2 > 層3 の勝率 |
| 3 | **遠征の踏破率が目標帯に入る** | 8通りの遠征 × 20シード |
| 4 | **支配戦略が無い** | 12枚デッキ空間で `offPathOnly` が層3 を抜けないこと（§4.5 の主張の検証） |
| 5 | **プリセット間の偏りが閾値以内** | 速攻型・重厚型（12枚版）の踏破率の差 |

**閾値は実測してから決める。** 計画に根拠のない数値を書くこと
（反復5 で `>= 12/20` と書いて実測11 で外した）を繰り返さない。

### 8.2 測定器の新しい癖を、41通り回す前に確かめる（**段階A の出口ゲート**）

`greedyStrategy` には**獲得を選ぶ概念がない**。遠征を回すには獲得戦略を足す必要があるが、
**どんな獲得戦略も人間とは違う癖を持つ。**

反復5 は `deployThenIdleStrategy` に41通りの掃引を費やし、最後に**指標そのものが無効**と判明した
（20シード中11シードで両戦略のランが完全に一致していた）。
教訓は「**2つの戦略が実際に違う行動を取る余地があるかを先に実測せよ**」である。

**実装の最初のタスクとして、次の1本だけを走らせる:**

> `noAcquire`（12枚のまま3ステージ）と `greedyAcquire`（3択から最も高コストを取る）の
> **遠征踏破率に差が出るか**

- **差が出れば**: 獲得は較正上も効いている。以降の較正を進める
- **差が出なければ**: 獲得は測定器レベルでゼロであり、**§4.6 の前提が崩れている**。
  その場合は較正を続けず、**設計（獲得の枚数・デッキサイズ・獲得プールの強度）へ戻る**

### 8.3 諦めたことの記録は残す

反復5 の `deployThenIdleStrategy` は「較正レバーの墓場」として docstring に実測を保存してある。
`enemies.ts` の `attackRange` にも同じ趣旨の記録がある。**どちらも削除しない。**

反復6 で新しい不変条件を立てるときは、
**その指標が目的の行為を測れるかを測定器の癖と突き合わせて先に確かめること。**

## 10. テスト方針

### 10.1 計画に書くテストは、実装コードより厳しく検算する

反復5 は修正9ラウンドのうち、実装者の誤りより**計画に書いたテストの欠陥のほうが多かった**:

- 「最も近い守り手を選ぶ」テストの比較対象が射程外＝最近接の分岐が一度も通らない
- 「魔力炉は攻撃されない」テストが `units: []` ＝変更を revert しても通る
- 射程の境界が 1.0 対 5.0 で緩すぎ（射程1.5 の `<`/`<=` を検出できない）

**「境界」「最近接」「〜されない」を主張するテストは、実際の定数
（装甲5、射程3.5、`HAND_LIMIT` 5、`MAX_COPIES` 3、`DECK_SIZE` 12）と突き合わせ、
主張する分岐が本当に通る入力かを確かめる。**

### 10.2 ドメイン

- `domain/expedition/` の全ファイルにテストを置く（層の抽選が決定的であること、
  獲得が同名上限を守ること、ライフが持ち越されること、敗北で遠征が終わること）
- **遠征の完全再生テスト**（§4.4）: 同一シード＋同一の獲得選択＋同一操作列で、
  3ステージの決着 tick・勝敗・`unit_lost` の座標まで一致すること
- 装甲: 装甲値**ちょうど**のダメージが0になること、装甲値+1 が1通ること（境界）
- 回復: `maxHp` を超えないこと、撃破済みには効かないこと、tick 内の処理順が固定であること

### 10.3 レビュー

- **レビューには「実装を壊してテストが赤くなるか」（変異）を必ず要求する。**
  反復5 では毎回これを指示し全件で実効性が確認できた。変異なしのレビューでは
  4件の空虚なテストが素通りしていた
- **レビューの指摘が実装側か計画側かを見極める。** 計画側なら計画を先に直してから
  実装者に戻す（同じ欠陥が再導出されない）
- **並行検証は worktree で分離する。** 反復5 は4名を同一作業ツリーで並行させ、
  未追跡ファイルがビルドを壊して1名が実機確認できなかった
- **全エージェント終了後の `git status` / `git diff` の完全なクリーンを、PR 前の必須ゲートにする**

### 10.4 完了条件（DoD）

`npm run ci`（`lint:ci` → `typecheck` → `test:coverage` → `build`）が緑。

**`lint:ci` を明記する。** 反復5 は完了条件に書き忘れ、
未使用 import が型チェックもテストも素通りした。

**加えて、新しい操作・機能には「画面のどこで自己紹介するか」を DoD に含める**（反復4 の教訓）。
反復6 で該当するのは獲得画面・遠征バー・射程オーバーレイ・オーラ実効値チップ。
**獲得については §4.6 で構造的に満たしているが、操作説明にも1行入れる。**

## 11. 既知のリスク

| リスク | 対処 |
|---|---|
| **較正が最大の不確実性**（6ステージ×対照デッキ×20シード ＋ 遠征単位） | 閾値は実測後に決める。段階D に集約 |
| **獲得が測定器で測れない可能性** | §8.2 の早期ゲートで、段階A の時点で潰す |
| **1判定単位が10分強に伸びる**（遠征1回 約3.5分 × 3遠征） | 判定者に事前共有。層1を短く（420 tick）してある |
| **実装量が反復5 の3〜4倍** | §12 の4段階に分ける |
| 装甲がカードの軸を壊す（弓兵が死に札になる） | 装甲を持つのは層3 の盾衛だけ。§8.1 の不変条件1 で「弓兵だけでは層3 が抜けない」ことと、「層1・層2 では弓兵が有効」であることを両方検査する |
| 回復が決定性を壊す（処理順の曖昧さ） | §5.3。tick 内の処理順を固定し、§10.2 の完全再生テストで検査 |
| 3レーンのステージで `enemy-stack` のマーカー重なりが悪化 | 反復5 から**未観測のまま持ち越している**項目（§7.9）。層3「城下」で目視確認を段階C の DoD に入れる |

## 13. 教訓の適用

### 13.1 前反復から引き継ぐもの

- **敵対的検証**（実装にも、**判定記録にも**）
- **後回しの回数を数える**（§6。3回目が4件ある）
- **判定は「言われなかったこと」で読む。** ただし**言われなかったが数値に出ているもの**を
  同じ強さで扱う（反復5 §1.1・§4.7）
- **指標は「いつ測るか」を設計する**（§7.3 の「測る瞬間」列）
- **反証条件は単独の指標に載せない**（§7.5）
- **測定器の癖と突き合わせて、指標が目的を測れるかを先に確かめる**（§8.2）
- **計画に書いたテストは実装より厳しく検算する**（§10.1）
- **機能は画面で自己紹介させる**（§4.6・§10.4）

### 13.2 本反復で新たに立てるもの

- **出口条件を満たさないときの帰結を、設計書に書く**（§7.8）。
  反復5 にはこの規定が無く、違反を正直に記載してそのまま次へ進んだ
- **主観の切り分けを、問いの文面ごと事前登録する**（§7.4）。
  反復5 は事前登録せずに「事前に決めた」と判定記録に書いた
- **主観の回答をログの記録経路に載せる**（§9）。
  反復5 は判定を確定させた発言が口頭＝検証不能な経路で入っていた
- **選択を記録するときは、選ばなかった候補も残す**（§9）。
  選択の情報量は「何を捨てたか」の側にある
- **遠征の完全再生可能性を DoD にする**（§4.4・§10.2）。
  反復5 の因果検証は再生可能性があったから成立した

**実装完了は判定ではない。** DoD（`npm run ci` 緑）と CoS（実プレイの記録）は別物である。
