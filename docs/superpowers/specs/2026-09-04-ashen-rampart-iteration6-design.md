### 2.5 実測から確定したこと

**(a) マナは詰まない。だが層3 で余剰が戻る。**
12枚デッキは 11.3/12 出せている（「3分の1が出せない」という反証者の推定は外れ）。
ただし手札の最安札すら払えない tick が 488中402（**82%**）で、マナが律速であること自体は正しい。
**そして層3 では最終残マナが 12.3 に戻る**——反復5 の余剰問題（10/15/10）の再現である。

**(b) 徴発は骨格を壊す。** 枯渇 360 → 276、出せた枚数 11.3 → 10.1、尾 9.9% → 20.8%。
**枯渇 tick の式 `40 × (枚数 − 3)` は徴発を含まないデッキでのみ正しい。**

**(c) カウントダウン込みの実決着 tick は台本長から大きく伸びる。**
最終ウェーブ260 の台本で決着488。窓 ＝ 488 − 360 ＝ **128 tick ＝ 26.2%**。

**(d) デッキ枚数とステージ長は独立に決められない。**
12枚 / 反復5台本（長い）は **3/20**。「デッキ12枚」と「短いステージ」はセットでしか意味を持たない。

**(e) 支配デッキは層3 でのみ消える。層1・層2 では経路外のみが 20/20・18/20 で成立する。**

**これが段階0 の最大の収穫である。** 初版 §5.2 は層1 に「ブロックと単体処理」、
層2 に「群れ」「対空＋ブロック」を要求軸として宣言していたが、
**易しく作った層1・層2 ではその要求がどれも成立していなかった。**

**「易しい層」と「軸を要求する層」は両立しない。** 易しい層は「何を置いても勝てる」＝
支配戦略が成立する場所になる。**難度カーブを層の易しさで作ると、較正の不変条件1 が空虚に緑になる**——
反復5 で「空虚なテストが4件素通りした」のと同じ形を、較正の側で作ることになる。

## 4. 遠征の骨格

### 4.1 形

ローグライト。**3ステージ連続**。

- ライフは遠征を通じて**持ち越す**（ステージクリアで +3 回復。初期12。どちらも較正対象）
- 盤面の設置物はステージごとに**リセット**
- **負けたら遠征終了**。獲得したカードも失う
- ステージ間で**3択から1枚を獲得**（獲得は2回、デッキは 12 → 13 → 14）

### 4.2 レイヤ

`CombatState` は**1ステージの戦闘**を表すものとして今のまま残し、その上に遠征の層を新設する。

```
domain/expedition/
├── stage-definition.ts   StageDefinition（層・マップ・ウェーブ台本・要求軸）
├── stage-pool.ts         6ステージ（層1〜3 × 各2）
├── stage-draw.ts         派生シードから各層1つを選ぶ（決定的）
├── acquisition.ts        獲得候補3枚の抽選と、選択の適用
└── expedition-state.ts   ExpeditionState と遷移
```

`domain/expedition/` は `domain/board`・`domain/combat`・`domain/cards` を参照するが、
**逆向きの参照は作らない**（`CombatState` は遠征を知らない）。

### 4.3 状態と、2種類のデッキ検証

```ts
export type StageTier = 1 | 2 | 3;

/** デッキ述語で表せる要求軸だけを列挙する（§8.1 の不変条件1 の対象） */
export type DemandAxis = 'anti-air' | 'mass-answer' | 'heavy-hit' | 'block';

export interface StageDefinition {
  id: string;
  name: string;
  tier: StageTier;
  map: StageMap;
  waves: readonly WaveDefinition[];
  /** このステージが要求する軸。層1=1本、層2=2本、層3=3本 */
  demands: readonly DemandAxis[];
}

export interface ExpeditionState {
  seed: number;
  stages: readonly StageDefinition[];
  stageIndex: number;
  deckCards: readonly string[];   // 12 → 14 に育つ
  life: number;                   // 遠征を通じて持ち越す
  offer: readonly string[];
  acquired: readonly string[];
  phase: 'stage' | 'offer' | 'ended';
  outcome: 'running' | 'cleared' | 'failed';
}
```

**⚠️ 致命的欠陥の修正（初版はここで必ず落ちた）。**
`start-run.ts:43` が `validateDeck` を呼び、`deck-builder.ts:37` は
`cards.length !== DECK_SIZE` なら例外を投げる。**獲得後の13枚では層2 の開始時に必ず落ちる。**

**構築時の規則と実行時の不変条件を分離する:**

| 関数 | 用途 | 検査 |
|---|---|---|
| `validateDeck` | 構築画面・`PRESET_DECKS` | 枚数**ちょうど** `DECK_SIZE` ／ 同名上限 ／ 既知のカード ／ **`acquireOnly` の札を含まない** |
| `validateRuntimeDeck` | ステージ開始 | 枚数 `DECK_SIZE` 以上 `DECK_SIZE + 2` 以下 ／ 同名上限 ／ 既知のカード |

**`acquireOnly` の検査を `validateDeck` 側に入れる。** UI で隠すだけでは
`startRunWithDeck` に狙撃櫓3枚のデッキを渡せてしまう（`deck-builder.ts` の docstring 自身が
「UI 側でだけ検証すると『テストは通るが UI で組めないデッキ』が生まれる」と戒めている）。

### 4.4 決定性 — 単一ストリームをやめ、目的ごとの派生シードにする

反復5 の判定を救ったのは「`seed` ＋ `deckCards` ＋ `card_played` でランを完全再生できる」性質である。

**初版の「1本のストリームを固定順序で消費する」は2つの理由で誤りだった。**

1. `noAcquire` は3択抽選を消費しないため、**以降のシャッフルが全部ずれる**（§8.2 のゲートが壊れる）
2. 3択の抽選が「同名上限まで持つ札を除外」するなら、**棄却回数がプレイヤーの選択に依存し、消費数が可変になる**

**目的ごとに独立した派生シードを使う:**

```
SeededRandom(hash(seed, 'stage-draw'))
SeededRandom(hash(seed, 'shuffle', stageIndex))
SeededRandom(hash(seed, 'offer', offerIndex))
```

これで再生可能性は保たれたまま、**アーム間でシャッフルを共有できる**。

**乱数オブジェクトを React の state / ref に置かない。** `src/index.tsx:23` は `StrictMode` で、
`useState` の初期化子は二重に呼ばれうる。現在は毎回 `new SeededRandom(runSeed)` を作るため
冪等で無害だが、RNG を `useRef` に持たせて複数ステージにまたがらせた瞬間に決定性が壊れる。
派生シード方式なら React 側は何も保持しなくてよい。

**再生に必要なログが現状は足りない**（§9.2 で追加する）:

| 欠落 | 影響 |
|---|---|
| `chooseLevy` がログを一切記録しない（`useAshenRampartGame.ts:420-430`） | **徴発の選択が再生不能** |
| `reactivated` に `emberIndex` が無い | 燠火が2基以上あると再生が分岐する |
| `card_discarded_manual` に `handIndex` が無い | 同名札が複数あると手札配列が再現できない |

**反復5 で再生が成立したのは、判定3ランで徴発も燠火も実質使われなかった偶然である。**
遠征では札の総数が減るぶん徴発の相対価値が上がり、この偶然は続かない。

### 4.5 デッキ12枚が支配デッキに与える影響（初版の論証を撤回し、実測に置き換える）

**初版の論証は誤りだった**（§0.1）。魔力炉の密度は 25% で変わらず、
魔力炉3＋攻撃塔3種×3 の12枚は合法に組める。

**実測（§2.4）が示したのは別のことである:**

- 層3 では塔だけ12枚が greedy 5/20・経路外のみ 3/20 まで落ちる
- **しかし層1・層2 では経路外のみが 20/20・18/20 で成立する**

**したがって支配デッキを封じるのは枚数ではなく「層が軸を要求すること」である。**
§5.2 の層構成（A案）はこの実測に基づいて作り直した。

魔力炉の `maxCopies: DECK_SIZE` は撤廃して `MAX_COPIES = 3` に揃えるが、
**これは支配デッキ対策ではなく「12枚中3枚＝25% で確実に引ける」という
初版の docstring の理由がそのまま成立するからである**（20枚中3枚＝15% では不足していた）。

### 4.6 獲得が引かれることの保証（徴発を勘定に入れて書き直す）

| 条件 | 枯渇 tick | 出せた枚数 |
|---|---|---|
| 12枚・徴発なし | **360**（`40 × (12−3)` と一致） | 11.3/12 |
| 12枚・徴発1枚 | **276** | 10.1/12 |

**決定: 徴発を12枚デッキの構築プールと獲得プールの両方から外す。**

理由は3つある。

1. **§4.6 の構造的保証（獲得札は必ず引かれる）を、徴発1枚が崩す。** 実測で出せた枚数が
   11.3 → 10.1 に落ち、尾が 9.9% → 20.8% に倍増する
2. **徴発が3枚めくって1枚選ぶ動詞は、獲得（3択から1枚）とまったく同じである。**
   「獲得専用札が獲得の自己紹介になる」（§5.4）という主張は、プレイヤーが既に
   同型の3択 UI を見ていることを勘定に入れていない
3. **徴発で捨てられた2枚はイベントを一切残さない。** 獲得札が徴発で消えた場合、
   ログ上「引けなかった」ことが原理的に分からず、§7.7 の切り分けが成立しない

**徴発はカード定義としては残す**（削除しない）。20枚時代のデッキを再現する較正のために要る。
反復7 で「徴発を12枚経済へ再設計する」を持ち越し1回目として §6 に記録する。

これで **獲得した1枚は次のステージでほぼ確実に手札へ来る。**
判定項目2 が床に張り付いた場合、原因を「引けなかった」ではなく
「選ばれた／使われなかった／払えなかった」に絞り込める（§7.7）。

### 4.7 画面の流れ

```
構築（12枚） → 層1 → 獲得（3択） → 層2 → 獲得（3択） → 層3 → 遠征結果
                 ↓敗北            ↓敗北            ↓敗北
                              遠征終了（獲得も失う）
```

遠征の進行（現在どのステージか・持ち越しライフ・獲得済みの札）を常設のバーに出す。

#### 5.4.1 装甲の実装制約（初版が見落とした致命的欠陥）

**ダメージを `hpById` に書き込む箇所は5つあり、共通の適用関数が存在しない**
（`step-tick.ts` の罠628・射撃693・範囲763・貫通816・業火841）。

- 装甲は**1ヒットごと**に引く。`resolveDamage` に1回だけ入れると
  **同 tick の複数ヒットで装甲が1回しか効かない**
- **さらに深刻**: `sourceById.set` は**ダメージ量に関係なく実行される**（罠だけが `if (spec.damage > 0)` を持つ）。
  装甲4 の盾衛に弓兵（4）が撃つと、**0ダメージなのに撃破源が弓兵へ書き換わる。**
  `combat-state.ts:76` の契約「最後に**削った**者に帰属する」が破れ、
  `run-summary.ts` の `defeatsByUnit` と集計が静かに嘘になる

**段階B の先頭タスク**として、共通関数を1つ作り5箇所を置き換える:

```ts
applyDamage(hpById, sourceById, enemy, rawDamage, source)
// 内部で dealt = Math.max(0, rawDamage - armor) を計算し、
// dealt > 0 のときだけ sourceById.set する
```

#### 5.4.2 回復の処理順（tick 内蘇生を構造的に消す）

`ActiveEnemy.alive` は **`resolveDamage` まで確定しない。**
罠・射撃・業火は `hpById` を負値まで削るだけで `alive` は `true` のままである。
回復を後段に置いて `alive` だけで対象を絞ると、
**その tick に致死ダメージを受けた敵を 0 超へ戻して蘇生させる。**

**決定: 敵の回復は罠より前（`hpById` を種まきした直後）に置く。**
これで「回復は削られる前に効く」という一義的な意味になり、蘇生経路が構造的に消える。

**守り手の回復（修復槌）は `applyEnemyAttacks` の直前に置く。**
`applyEnemyAttacks` は同じ関数の中で `unit-lost` を積み `hp > 0` の守り手だけを返すため、
**後段に置くとその tick に壊れた守り手はもう配列に居らず救えない。**

### 5.7 敵の射程の可視化 — 視覚チャンネルの競合を先に解く

**カード選択中、盤面に「敵の攻撃射程が届きうる経路外セル」を示す。**
射程を持つ敵が通るレーンセルから `attackRange` 以内の経路外セルは、
マップとウェーブが決まれば確定するので**静的に事前計算**できる（この主張は検証で確認された）。

**初版が見落としていた2つの実装制約:**

1. **`RangeOverlay` は `plate.pos` を中心に描く。カード選択中には「そこ」が無い。**
   ホバーで代替すると、**最小幅360px＝タッチ環境には hover が無く、判定者の実機で一度も出ない。**
   → カード自身の射程は「置けるセルのハイライト自体を、射程が経路に届くセルに絞る」形で表現する（位置を要さない）
2. **警告色で塗る対象は「射程が届きうる経路外セル」＝そのまま守り手を置けるセルである。**
   `BoardGrid.tsx:60` は置けるセルへ既に `outline` を出しており、
   **同じセルの同じ視覚スロットを2つの意味が奪い合う**（`MAX_CELL_MARKS = 3` にも抵触）
   → 敵の射程警告は **outline ではなくセル背景の色調**で出し、役割を分ける

### 5.9 3レーン（層3「城下」）の表示側

### 5.10 プリセットデッキの作り直し

#### 7.3.1 項目1 を実プレイから外し、ユニットテストへ移す

| **4回** | 9.45 | **51.1%** |

#### 7.3.2 項目2b — 獲得が判断だったかを直接測る

**初版の項目2（獲得札が以後1回以上出された割合）はトートロジーだった。**
§4.6 が「毎ステージほぼ全枚数を引き、ほぼ全部出す」と構造で保証している以上、
**機構が動きさえすれば必ず当たる。** 実測でも 11.3/12 が出ている。

**§5.3 で次ステージの要求軸が開示されているので、「要求に応える札を選んだか」が測れる。**

- 分母: 6回（可変）の獲得のうち、**次ステージの要求軸を満たす札が3択に含まれていた回数**
- 分子: そのうち、実際にその札を選んだ回数
- **選ばない自由がある**（他の2枚を選べる）ので、トートロジーではない
- `card_acquired.offered[3]` が**選ばなかった2枚を残す**ので、判定記録で検算できる

**予測 0.6 の根拠**: 3択のうち要求軸を満たす札が1枚なら無作為は 0.33。
2枚なら 0.67。提示の構成は抽選なので、**無作為の期待値は 0.33〜0.67 の間**。
0.6 は「無作為より明確に上」を意味する下限として置く。
**段階D で、実際の抽選分布から無作為期待値を実測し、この節へ追記する**（§7.8 の手続きに従う）。

#### 7.3.3 項目3 — 鳩の巣原理を欠陥ではなく測定資源に転用する

**初版の「引いてから出すまでの遅延」は棄却する。** 検証で交絡が6経路見つかり、
そのうち3つは原理的に潰せない:

| 交絡 | なぜ潰せないか |
|---|---|
| **魔力炉の配置クールダウン60** | 12枚中3枚。**コスト0なのでマナでは切り分けられない** |
| **徴発・初期手札3枚に `card_drawn` が無い** | 12枚の25%に遅延が定義できない（徴発は §4.6 で外したが初期手札は残る） |
| **決着時に手札に残った札が母集団から落ちる** | **抱えた札ほど中央値から消える＝反復5 §3.4 と同型の穴に逆向きで落ちる** |

さらに「遅延はドロー順に影響されない」という初版の中心的正当化が誤りだった——
**マナ蓄積が時間の関数である以上、遅延は到着時刻＝ドロー順の関数である。**
実測でもマナ待ちの tick が 82% を占める。

**代わりに、検証が「欠陥」として指摘した性質を測定資源に使う。**

各層は2択、遠征は3回。**鳩の巣原理により、どの層でも同じステージが2回以上出ることが確定する。**
検証はこれを「同一台本の再演が確定する＝交絡」と指摘したが、
**地形が同一のペアが必ず手に入るということでもある。**

**指標の完全な定義:**

1. **配置セル集合** `P(stage, expedition)` ＝ そのステージで記録された `card_played` のうち
   `x, y` を伴うものの `(x, y)` の集合（重複除去。罠・魔力炉を含む）
2. **再演ペア** ＝ 同じ `stageId` が2つの異なる遠征で出た組。3遠征なら層ごとに1組以上（層3 は到達した遠征のみ）
3. **`J_human`** ＝ `|P₁ ∩ P₂| / |P₁ ∪ P₂|`
4. **`J_greedy`（ペアごとの反実仮想）** ＝ 同じ `stageId` を、**そのペアの実際の2つのデッキ**
   （初期12枚＋その時点の獲得札）で `greedyStrategy` に解かせた配置の Jaccard
5. **判定** ＝ `J_human < J_greedy` が、成立したペアの**過半**

**なぜこの形か:**

- **地形交絡がゼロ。** 同一ステージなので、置ける場所も経路も完全に同じ
- **デッキ変化の交絡が除かれる。** `J_greedy` は「適応ゼロで、デッキの違いだけで説明される変化量」であり、
  人間がそれを下回れば**デッキでは説明できない変化＝適応**である
- **`greedyStrategy` を閾値の源にしていない。** 初版は「測れないと宣言した測定器から閾値を取る」自己矛盾を犯していた。
  ここでは greedy は**閾値ではなく下限（適応ゼロの基準）**として使い、比較は差分で行う
- **曖昧語が無い。** 「床から離れ」「低い」のような未定義語を使わず、すべて演算で定義した

**ペアが1組も成立しない場合**（例: 3遠征とも層1 で敗北し、層1 のペアはあるが層2・層3 が無い）
——層1 のペアだけで判定する。**層1 のペアすら無いことは鳩の巣原理により起こらない。**

#### 7.3.4 項目5 の「15% 未満」の根拠（実測から導出）

§2.4 の greedy 実測と、反復5 で得られた人間/greedy 比から導く。

| | greedy 実測（§2.4） | 人間/greedy 比 | 人間の予測 |
|---|---|---|---|
| 層1 | 9.9% | 0.53〜0.73 | 5.2〜7.2% |
| 層2 | 15.2% | 同 | 8.1〜11.1% |
| 層3 | **34.0%** | 同 | **18.0〜24.8%** |
| 平均 | 19.7% | 同 | **10.4〜14.4%** |

**15% はこの範囲の上端である。**

**⚠️ 層3 単独では baseline（20.3〜28.0%）と重なる。** 層3 は決着 720 tick と長く、
枯渇 360 からの窓が広い。**層3 の尾は反復6 でも解消しない。**
これを §7.9 の帰結に含め、**反復7 の課題として先に宣言する**（後から「想定内だった」と言わないため）。

#### 7.3.5 項目6 を比率にする理由と、層3 の余剰

実測（§2.4）で最終残マナは 層1 3.4 / 層2 4.7 / **層3 12.3**。
**層3 では反復5 の余剰問題（10/15/10）が再現している。**

絶対値で「baseline より小さい」とすると層1・層2 では自動達成、層3 では未達になる。
**比率（残マナ ÷ 総マナ収入）で測る**: 層1 3.4/14.8 = 0.23、層2 4.7/17.4 = 0.27、層3 12.3/26.1 = 0.47。

**予測は層1・層2 のみに置く（0.25 未満）。層3 は継続観察とし、余剰が残ることを先に認める。**

#### 7.3.6 項目7 を「踏破」から「層3 到達」へ変える

**初版の「3遠征中1〜2回踏破」は、真の踏破率が20%〜80%のどこにあっても
半分近く合格する**（n=3 の二項分布）。較正の失敗を検出できない。

**さらに重要な理由がある。** 初版は新敵2種を層3 専用に置きながら、
「3遠征中1〜2回踏破」と予測していた。**この反復の目玉である敵2種が、
判定セッションで一度も画面に出ない可能性を構造的に放置していた**（致命的指摘）。

**決定:**
- **癒し手を層2「鴉の谷」にも1体出す**（軸にはならない予告個体）
- **層3 の両ステージに盾衛と癒し手を置く**（層3 に到達すれば必ず両方見る）
- **項目7 の指標を「層3 への到達率」にし、予測を 2/3 以上に置く**
- **踏破率は §8.1 の不変条件3（8通り×20シード＝160遠征）で測り、実プレイでは測らない**

### 7.4 主観 — 中立な文面と、肯定/否定のコード化を事前登録する

### 7.5 反証条件 — 客観の失敗を主観で救わせない

**初版の連言は反証回避の装置になっていた**（Codex が1本ずつ判定し、4本を「不当」と結論）。

| # | 条件 | 判定 |

### 7.8 閾値の後出しを禁じる手続き

**閾値そのものではなく、算出アルゴリズムを先に登録する**（Codex の指摘）。
現時点で値が未確定なのは **項目2b の無作為期待値**だけである。

**登録する算出手続き:**

1. **使用データ**: 段階D の較正で生成した8通り×20シード＝160遠征の `card_offered` 相当の抽選結果
2. **算出式**: 「次ステージの要求軸を満たす札が3択に含まれた提示」について、
   その3枚のうち要求軸を満たす札の枚数 `k` の分布を取り、無作為期待値 ＝ `E[k/3]`
3. **除外規則**: 提示が起きなかった遠征（層2 で敗北）は除外。丸めは小数第2位で四捨五入
4. **追記のタイミング**: **実プレイ判定を開始する前**に、本設計書へ**別コミット**で追記する
5. **追記後の変更を禁じる**: 追記コミットの SHA を判定記録に記載する

**この5点を守れないなら、項目2b は閾値を持たない所見に格下げし、F1 から外す。**

### 8.2.2 【撤回済み】`G1` は通ったが、「獲得が遠征を強くする」ことは支持されていない

**合格条件（§8.2）は満たされた。** `demandAwareAcquire`（17）と `randomAcquire`（11）に差があり、

マナが律速である（段階0 の実測で 82% の tick が「手札の最安札すら払えない」）ため、
軸に合わない札は純粋な希釈になる。**取る／取らないに重みがあることは、
ローグライトとしてはむしろ望ましい形である**——獲得が単純に加算的なら「何でも取ればいい」になり、
選択が判断にならない。

**しかし、次の主張は支持されていない。判定記録に書いてはならない:**

> ❌ 「獲得によって遠征が強くなる」

`demandAwareAcquire` は `noAcquire` に**並んだだけで、上回っていない**。
これを書けば、根拠のない因果の主張になる（反復5 の初版判定記録が犯した型）。

**支持されているのは次だけである:**

> ✅ 「獲得の選び方が遠征の結果を動かす。よく選べば取らないのと同等、雑に選べば取らないより悪い」

**帰結:**

1. **判定項目2b（獲得が判断だったか）の枠組みは有効。** むしろ「選び方に結果が付いてくる」ことが実測で裏づいた
2. **段階D の較正で「獲得プールの強度」を見直す候補にする。** 現状では最善手が現状維持と等価で、
   獲得が上振れを生んでいない。獲得専用札（狙撃櫓・修復槌・鼓舞旗）が入る段階B で再測定する
3. **この留保を判定記録の §1.1 の照合対象に含める**（§1.1 の不満リストと同じ扱いで、
   「言われなかったが数値に出ているもの」として）

### 8.2.3 【一部撤回】`reachedTier3` は腕の弁別には鋭敏でない

4腕とも 31〜34/40（77.5〜85%）で、踏破率ほどの差が出ていない。

**ただし判定項目7 の目的は腕の弁別ではない。** 「判定者が層3 に到達して新敵（盾衛・癒し手）を見るか」の
確認であり、その目的には適う。**33/40 ＝ 82.5% は §8.1 `C3` で宣言した帯 60〜85% の中にある。**

踏破率も `demandAware`／`noAcquire` の 42.5% が宣言帯 30〜60% の中にある
（`random` の 27.5% はわずかに下）。**暫定ステージの時点で帯にほぼ収まっているのは僥倖であり、
段階B で本番ステージに置き換えたら測り直すこと。**

### 8.2.4 撤回の理由と、判定を「判定不能」に戻す決定（2026-09-06）

4視点の敵対的検証（手続き／統計的検出力／因果と交絡／見落とし）にかけた。
**§8.2.1〜8.2.3 の主張はほぼすべて覆った。**

#### (a) 決定的な理由 — 事前登録した測定方法を実行していない

§8.2 の事前登録は3条ある。**そのうち第2条を、測定は満たしていない。**

> 2. **差を勝率ではなく反実仮想で測る。** 反復5 で確立した手法をそのまま使う——
>    **同一シード・同一操作列を再生し、獲得札だけを抜いて結果が変わるか**を見る

`expedition-gate.test.ts` は4戦略を独立に実行して**勝率を比べた**だけである。
**条文が「勝率ではなく」と明示的に否定した方法そのものを使った。**
獲得戦略が違えば greedy の後続操作も変わるので、観測された差は
「獲得札だけを抜いた反実仮想差」ではない。

**しかも §8.2.1 で「合格条件は満たされた」と書いたとき、この第2条を引いていない。**
引いたのは第1条（差が出るか）だけである。
**反復5 §1.6 の「有利な条文だけを引き、失敗を宣言する条文を沈黙で飛ばす」と同型の再発である。**

**したがって `G1` は通過でも不通過でもなく、判定不能である。**

#### (b) 統計 — n=40 に判断の資格が無く、中心的な主張は標本誤差だった

| 腕 | n=40（撤回した表） | **n=600（プール・2つの独立なシード帯）** | 95%CI |
|---|---|---|---|
| `noAcquire` | 17/40 = 42.5% | **203/600 = 33.8%** | [30.2, 37.7] |
| `randomAcquire` | 11/40 = 27.5% | 179/600 = 29.8% | [26.3, 33.6] |
| `cheapestAcquire` | 12/40 = 30.0% | 185/600 = 30.8% | [27.3, 34.6] |
| `demandAwareAcquire` | 17/40 = 42.5% | **236/600 = 39.3%** | [35.5, 43.3] |

- **n=40 の検出力は 8.1%**（真の効果量からのモンテカルロ）。有意水準5%の偽陽性率とほぼ区別できない。
  **この標本サイズは「差がある」とも「差がない」とも言う資格を持たない**
- **`demandAware` は `noAcquire` に並んでいない。** 対応のある McNemar 検定で

- **「17対17」は同着ではない。** 4件ずつの入れ替わりが相殺しただけで、

- **`randomAcquire` の 11/40 は rng ストリーム1本のくじ。** ストリームを変えて12本走らせると
  10〜16（平均12.67）で、`demandAware` との差が p<0.05 になるのは **2/12 のみ**。
  **ゲートが通ったのは当たりストリームを引いたからである**
- プリセット別では swift と heavy で符号が逆（n=40）。平均が両者を潰していた

#### (c) 因果 — 差の説明が「軸適合」である根拠が無い

- **暫定台本6ステージ中4つで、宣言した要求軸が実際には要求されていない。**
  `offPathOnlyStrategy`（一切ブロックしない）と `noPureGroundAttackStrategy` が
  層1・層2 の4ステージで **15/15 完勝**した。`stage-pool.ts` の docstring が
  「要求軸は暫定であり台本が本当に要求するかは未検査」と警告していたとおりである
- **`demandAwareAcquire` の優位は「軸適合」より「取る札が強い／高コスト」で説明がつく。**
  獲得の平均コストは `demandAware` 2.32 対 `cheapest` 1.27。
  `demandAware` は投石機9・徹甲弩9・火砲台7 を優先し、`cheapest` は弓兵14・鍛冶場10 に偏る
- **「軸適合＝良い」は成り立たない。** 石壁（block 軸）を常に取る腕は **11/40** で、
  `cheapest`(12) や `random`(11) より良くならない。効いているのは
  「状況に応じた選択」対「固定選択」の差のほうかもしれない
- **基底シャッフルの共有は正しく機能している**（ground truth 再計算で全シード・全ステージ一致）。
  §8.2 第1条は満たされている

#### (d) §7.1 の自己違反

§7.1 は「**獲得が判断になったか**は較正ハーネスでは**測れない**。実プレイのログ＋主観のみ」と
事前に宣言している。**にもかかわらず §8.2.2 の帰結1 は、greedy の4腕測定から

**測れないと自分で宣言した構成概念を、通過後に測れたことにしていた。**
§7.1 はまさにこれを防ぐために書いた節である。**帰結1 を撤回する。**

#### (e) §7.10 の必須欄が埋まっていない

§7.10 は `G1` について「原文・入力ログ・計算結果・判定・総合判定への効果」と
「データ完全性・指標妥当性・交絡・反対解釈」を必須とし、**空欄なら判定不能**としている。
§8.2.1〜8.2.3 はどれも埋めていない。**この条文だけでも判定不能である。**

#### (f) 判定と、次にやること

**判定: 判定不能（Unknown）。通過でも不通過でもない。**

**段階B へは進まない。** 次の順序で `G1` をやり直す。

1. **Task 15（遠征の完全再生）を先に完成させる。** 反実仮想の測定にはその機構が要る。
   §8.2 第2条が要求しているのはまさにこれである
2. **`G1` を反実仮想で測り直す。** 同一シード・同一操作列を再生し、
   **獲得札だけを抜いて**結果が変わるかを見る
3. **判定の演算を先に事前登録する。** 「差」の最小効果量・符号・標本サイズ・
   同率時の帰結・多重比較の扱いを、測る前に別コミットで固定する。
   **n は検出力80%以上を確保できる規模にする**（今回の実測から、
   `noAcquire` 対 `demandAware` なら N≈500 で85%）
4. **暫定台本が要求軸を実際に要求しているかを先に確かめる**（§8.2.4(c)）。
   要求していない軸に対する `demandAwareAcquire` の選択は、結果と無関係である
5. **`randomAcquire` は複数ストリームの平均と分散で報告する。** 単一ストリームの値を表に載せない

**この (f) を実行するまで、`G1` は判定不能のままとする。**

#### (g) やり直しの前に知っておくべき2件（Task 15 のレビューで判明・2026-09-06）

**1. `offerIndex` の交絡は直したが、現存するどの獲得戦略もそれを踏まない。**

`advance-stage.ts` の `offerIndex` を `acquired.length` から `stageIndex - 1` へ直した
（`noAcquire` の腕で同じ3択が2回提示されていた）。**しかし現存する戦略はすべて二値である**——
`noAcquire` は常に断り、`randomAcquireOf` / `cheapestAcquire` / `demandAwareAcquire` は常に受ける
（`offer.length === 0` の実質到達不能な場合を除く）。**提示の内容を見て断る戦略が1つも無い。**

したがって:

- **常に受ける腕**では `acquired.length` と `stageIndex - 1` が**全提示点で一致する**（乖離しえない）
- **常に断る腕**では、提示の内容が自分の軌跡に影響しない

**つまり修正前後で測定値が変わらなかったのは「たまたま」ではなく構造的必然である。**
`12/20` も `18/20` も、**現存する戦略の組み合わせでは変わりようがなかった。**

**帰結: この修正は「単体では正しいと証明されたが、実際の測定で効くことはまだ示されていない」。**
やり直しで同じ二値戦略だけを使えば、また「差が見えない」結果になる。
**それは交絡が無害だったことを意味しない。** 提示の内容に応じて断る戦略を1つ足すか、
反実仮想（下記2）で測るかしなければ、この修正の効果は観測されない。

**2. 「獲得札だけを抜く」ヘルパはまだ存在しない。**

§8.2 第2条が要求する反実仮想は、いまの部品で**原理的には表現できる**——
実ランの `acquired` を記録し、**1箇所だけ `undefined` を返す** `AcquireStrategy` の閉包を作れば、
その提示点までの提示内容は実ランと一致する（上記1の修正のおかげで、
以前は先に乖離したランでは一致しなかった）。

**しかしその「1つだけ抜く」ヘルパはまだ書かれていない。** Task 15 が作ったのは
「全選択を記録して丸ごと再生する」形だけである。**やり直しの最初の作業はこれを書くことである。**

**3. 提示そのものが獲得の有無で変わる経路が残っている（段階A の最終レビューで判明）。**

`buildOffer` の候補は `deckCards`（＝基底12枚 ＋ **獲得札**）の所持数で絞られる
（`acquisition.ts` の同名上限フィルタ）。**獲得した札が同名上限に達すると候補配列が1本短くなり、
同じ派生シードでも `splice` の当たる位置が変わって提示の中身が変わる。**

実測（本番と同じ式を独立に再現）: **seed 1〜20 の 60通りのうち14通りで、
2回目の提示が獲得の有無で変わった。** 順序だけでなく中身が違う例もある。

**これは撤回の原因とまったく同型である**——「事前登録した比較可能性を、測定器の別経路が壊している」。
`expedition-state.ts` の docstring は「獲得を含めた配列をシャッフルすると比較できなくなる」ので
基底を分けたと書いているが、**抽選側には同じ分離が入っていない**（`initialDeckCards` ではなく
`deckCards` を渡している）。

**決定: 反実仮想は「最後の獲得」だけを抜く形に限定する。ゲーム規則は変えない。**

理由——遠征の獲得は2回である。**2回目（最後）の獲得を抜けば、それ以前はすべて同一である:**

| | 実ラン | 2回目を抜いた再生 |
|---|---|---|
| 提示1 | 同一 | 同一 |
| ステージ2 | 同一 | 同一 |
| 提示2 | **同一**（デッキはどちらも 12＋1枚） | **同一** |
| ステージ3 | その1枚が有る | その1枚が**無い** |

**提示2 より後に提示は無いので、下流の乖離が生じない。** これは §8.2 第2条が要求する
「獲得札だけを抜いて結果が変わるか」を、交絡なしに満たす。

**1回目の獲得を抜く形は使わない。** 抜くと2回目の提示が変わりうるため（上記の14/60）。

**候補フィルタを `initialDeckCards` 基準に変える案は採らない。** 手持ちが3枚ある札を
4枚目として提示することになり、同名上限という規則そのものを壊す。
**測定の都合でゲーム規則を曲げてはならない。**

**やり直しで測るのは「最後の1枚が結果を変えるか」であり、
「獲得という機構全体の効果」ではない。** 後者を測るには腕どうしの比較が要り、
それは提示が腕依存になるため交絡する。**この限界を判定記録に明記すること。**

#### 8.2.5 この撤回から得た教訓

- **測定方法そのものを、条文ごと照合してから測る。** 今回は「差が出るか」という
  結論の条文だけを見て、「どう測るか」の条文を飛ばした
- **標本サイズを先に決める。** 検出力8.1% の測定に判断させてはならない。
  「n=40 で走る」は実行時間から逆算した都合であって、判断の要求から出た数ではなかった
- **同着を「効果なし」と読まない。** 対応のある設計では、総数の一致は
  入れ替わりの相殺でも起きる。**必ず分割表（b, c, 不一致数）で報告する**
- **乱数を使う腕は、単一ストリームの結果を表に載せない**
- **「測れない」と宣言した構成概念は、都合よく測れたことにしない**（§7.1 の自己違反）

### 8.2.6 `G1'`（やり直し）の事前登録 — 測る前に固定する

**これは事前登録である。ここに書いた演算・標本サイズ・判定条件を、測定の後に変えてはならない。**
変えるなら、それは新しい事前登録であり、**別のデータで測り直す**。

撤回の直接の原因は「合格条件が『差が出る』としか書かれておらず、
差の演算・最小効果量・標本サイズ・同率時の扱いが未定義だったため、
観測を見た後に読み方を作れたこと」である（§8.2.4）。ここでそれを塞ぐ。

#### (a) 2つの問いを分けて測る

反実仮想を**最後の獲得**に限定したこと（§8.2.4(g)-3）により、
下流に提示が無くなるので、**2つの問いが両方とも交絡なしに測れる。**

| | 問い | 比較 |
|---|---|---|
| **`G1a`（機構）** | 最後に獲得した1枚は、結果を変えるか | 実ラン 対 **最後の獲得だけを抜いた**再生 |
| **`G1b`（選び方）** | 最後の提示で**どの札を取るか**が、結果を変えるか | 最後の提示で **`demandAware` が選ぶ札** 対 **同じ提示の中で最もスコアの低い札** |

**`G1b` が主要対比である。** 事前登録した判定項目2b が問うのは「選び方」であり、
`G1a`（機構の有無）ではないからである。

**`G1b` は交絡しない。** 最後の提示までの操作列・デッキ・提示内容が両腕で完全に同一であり、
違うのは「その提示から何を取ったか」だけである。以後に提示は無い。

#### (b) 主要対比は1本。残りは探索的

**事前登録する主要対比は `G1b` の1本のみ。** `G1a` と、プリセット別の層別は**探索的**とし、
**多重比較の補正なしに解釈しない。** 撤回前は6組の対比較から最小の p だけを見ていた。

#### (c) 指標

**主指標は `outcome === 'cleared'`（踏破したか）の二値。**

`stagesCleared`（0〜3）と `reachedTier3`（≥2）は**同じ順序変数の粗視化**であり、
独立な証拠ではない（`reachedTier3 = stagesCleared ≥ 2`、`cleared = stagesCleared = 3`）。
**3つを別々の証拠として数えない。** 補助として `stagesCleared` の対応差を報告するが、判定には使わない。

**`reachedTier3` は腕の弁別に使わない。** 最後の獲得を抜く操作はステージ3 にしか効かず、
`reachedTier3` はステージ1・2 の結果なので**構造上まったく動かない。**

#### (d) 統計手続き

- **対応のある設計**（同一シード・同一プリセット・同一操作列）なので、**McNemar 正確検定**を使う
- **必ず分割表で報告する**: 両方踏破 / 実ランのみ踏破（b）/ 再生のみ踏破（c）/ 両方失敗、および不一致数 `b+c`
- **総数の比較を判定に使わない。** 撤回前の「17対17」は4件ずつの入れ替わりの相殺だった（§8.2.4(b)）
- 両側検定、α = 0.05

#### (e) 標本サイズ — 検出力から決める

**N = 500 遠征（250シード × プリセット2種）。**

根拠: 撤回時の実測（n=600）から真の効果量を推定し、McNemar 正確検定の検出力を
モンテカルロで計算した結果が次である。

| N | 検出力 |
|---|---|
| 40（撤回した測定） | **8.1%** |
| 120 | 26.6% |
| 300 | 62.2% |
| **500** | **85.4%** |
| 800 | 96.8% |

**N=40 の検出力 8.1% は有意水準5%の偽陽性率とほとんど区別できない。**
「差がある」とも「差がない」とも言う資格が無かった。

**N は実行時間の都合で決めない。** 500遠征で約5分（実測 40遠征21秒からの外挿）。
CI には常駐させず、**やり直しの測定は手動実行とする**（§8.3 の60秒予算を守るため）。

#### (f) 最小効果量

**p < 0.05 だけでは通さない。** 不一致ペアが少なすぎると、有意でも実質的な意味がない。

**通過には次の両方を要求する:**

1. **McNemar 正確検定で両側 p < 0.05**
2. **不一致ペア数 `b + c` ≥ 25**（N=500 の 5%）

#### (g) 前提条文の検査 — 1つでも未達なら通過を禁止する

**撤回の原因の1つは、前提条文（基底順の共有・反実仮想の実施）を引かずに
結論の条文だけを引いたことである**（§8.2.4(a)）。**測定の前に次を検査し、
判定票に Pass / Fail / Unknown を記入する。**

| ID | 前提 | 検査方法 |
|---|---|---|
| `P1` | 両腕の基底12枚のシャッフルが全ステージで同一 | ground truth（`shuffle(initialDeckCards, derivedSeed(seed,'shuffle',stageIndex))`）を独立に計算して照合 |
| `P2` | **最後の提示の内容が両腕で同一** | 両腕の `card_offered` 相当を突き合わせる |

**`P1`〜`P4` のいずれかが Fail なら、結果の解釈をしない（Unknown）。**

#### (h) 判定の演算と帰結

```
P1..P4 がすべて Pass でなければ          → Unknown
p < 0.05 かつ b+c >= 25                  → Pass
p >= 0.05 かつ b+c >= 25                 → Fail（選び方は較正上効いていない）
b+c < 25                                 → Unknown（効果を検出する材料が足りない）
```

**Pass の場合**: 段階B へ進む。**ただし主張できるのは
「較正ハーネス上で、最後の提示の選び方が結果差を生む」ことだけである。**

**Fail の場合**: 段階B へ進まない。§4.6（獲得は必ず引かれる）と判定項目2b の前提が崩れているので、
**獲得の枚数・獲得プールの強度・要求軸の開示のいずれかを設計から見直す。**
**判定条件そのものを変えて再度 `G1` と称して通してはならない。**
変更後は**別のシード帯**で測り直す。

**Unknown の場合**: 通過でも不通過でもない。**前提の Fail を直すか、N を増やすかしてから測り直す。**

#### (α) `isClean=true` の組には、構造的に無情報なものが混ざる

**踏破の可否を主指標にする以上、`actual.stagesCleared < 2` の組は必ず一致する。**

理由: 最後の獲得はステージ3 の直前に起きる。実ランがステージ2 までに敗北していれば、
その獲得は**ステージ2 に**効く。しかし腕が `cleared`（3ステージ踏破）になるには
そのステージに勝たねばならず、勝てば提示が1回増えて `noExtraOffers` に落とされる。
**つまり `isClean` を通った `stagesCleared < 2` の組は、両腕とも必ず `cleared` にならない。**

実測: 該当54組の不一致は **0件**。

#### (β) したがって検出力は「生の N」ではなく「有効 N」で読む

| | 定義 |
|---|---|
| **生の N** | `isClean` を通った組の数 |
| **有効 N** | そのうち `actual.stagesCleared >= 2` の組の数 |

**§8.2.6(e) の検出力表は有効 N に対して読む。** `greedyStrategy` × プリセット2種なら
有効率はおよそ 90%（N=500 → 有効 450、検出力はおよそ 85% → 82%。**80% は維持する**）。
弱い盤面戦略では有効率が 44% まで落ちうるが、`G1'` は `greedyStrategy` で測るので該当しない。

**測定は生の N と有効 N の両方を報告する。** 片方だけでは検出力を確かめられない。

#### (γ) 通過要件（§8.2.6(f)）は変更しない

`p < 0.05` と `b + c >= 25` はどちらも**不一致ペアの数**に対する条件であり、
無情報な組は「両方失敗」のセルに入るだけで `b` にも `c` にも寄与しない。
**したがって ballast は通過要件を甘くも辛くもしない。閾値は動かさない。**

**動かすのは「N が足りているか」の読み方だけである。**

#### 反対解釈

**1. コストの交絡（最も重い）**

2つの腕は**軸適合だけでなくコストの向きも逆である。**

```ts
demandAwareAcquire: score 降順 || cost 昇順   // 同点なら最安
worstDemandAcquire: score 昇順 || cost 降順   // 同点なら最高
```

**提示3枚の軸スコアが全て同じとき、2つの腕は「最安の札」対「最も高い札」を取る。**
これは軸適合の対比ではなく**純粋なコストの対比**である。

**したがって観測された差は「要求に合う札を取ったから」ではなく「安い札を取ったから」かもしれない。**
この測定はその2つを区別できない。**`worstDemandAcquire` を設計したとき、
`demandAware` の完全な裏返しにすることを優先し、コストの向きまで反転させてしまった。**

§8.2.7 が「宣言と実態が食い違う」ことを示している以上、**軸スコアはしばしば無意味であり、
その場合この対比はコスト対比そのものになる。** この解釈は本測定では棄却できない。

**2. 層別が正反対（heterogeneity）**

| | swift | heavy |
|---|---|---|
| `G1b`（主要対比） | p = **0.461** | p = **0.016** |
| `G1a`（探索的） | p = **0.014** | p = **0.229** |

**合算の有意性は `heavy` だけが担っており、`swift` 単独では差が無い。**
`G1a` では逆に `swift` だけが有意である。層別は探索的なので判定は動かさないが、
**「選び方が効く」という一般的性質なら、この非一貫性は説明を要する。**

除外率も大きく違う（`heavy` 20% / `swift` 4%）。

**3. 検出力が事前登録に届いていない**

有効 N=394 で検出力およそ 75〜78%。有意な結果なので Pass は揺らがないが、
**この標本で「効果がある」と言えても、効果量の推定は不安定である。**

### 8.2.9 `G1'` の Pass を撤回する（2026-09-06）

**§8.2.8 の判定 Pass を撤回する。** 発見は最終レビュー、検証はコントローラの実測。

#### (a) 何が起きたか — 除外が片方向だった

`isClean` による除外は `b`・`c` に中立だと §8.2.6+(δ) に書き、**「検算済み」と記した。
これは事実に反していた。**

実測（250シード × 2プリセット）:

```
採用組の分割表: b(実ランのみ)=48  c(反実仮想のみ)=28  p=0.028627
除外された組: 41
  そのうち actual 踏破  = 0   ← b には1件も加わらない
  そのうち swapped 踏破 = 6   ← c にだけ加わる
仮に除外分を戻したら: b=48 c=34  p=0.150675
```

**除外は構造的に `c` しか削らない。** 除外の発火条件が「**再生が実ランの負けたステージに
勝った**」だからである。再生が先へ進んだ組しか除外されないので、
除外集合の中で踏破しうるのは反実仮想の腕だけである。

**そして削られる向きは Pass に有利である。** 6件を戻すと p は 0.0286 → 0.1507 となり、
3件でも 0.0712 で不通過になる。**判定は除外の6件に依存していた。**

#### (b) より深い誤り — 処置後の変数で条件づけていた

数の偏りより重い。**`isClean` は「提示が増えたか」で組を選別しているが、
提示が増えたこと自体が、測っている選択の結果である。**

別の札を取った → ステージ2 に勝てた → 提示が1回増えた、という連鎖において、
**増えた提示は交絡ではなく媒介である。** それで絞り込むのは処置後の変数による
条件づけであり、選択バイアスを生む。**「効果があった組」を系統的に捨てていた。**

§8.2.4(g)-3 で「最後の獲得に限れば下流に乖離が生じない」と論じたとき、
私は**「最後の獲得」と「最後の提示機会」を同一視していた。**
ステージ2 で敗北した遠征では、実ランにとっての最後の獲得は
反実仮想にとっての最後ではない。ここが崩れていた。

#### (c) なぜ気づけなかったか

**「除外は中立」という主張を、私は自分で検算していない。**
Task 3 のレビューが出した分析を受け取り、**それを「検算済み」と書いた。**
レビューの分析は `stagesCleared < 2` の組が「構造的に一致する」と述べていたが、
**その組でも `swapped` 腕だけが踏破しうる**ことを見落としていた。

**受け取った分析に「検算済み」という語を付けたのは私である。**
確かめずに確かめたと書いた——**§8.2.4 で撤回した前回と同じ型の誤りである。**

#### (d) 判定の扱い

**`G1'` は判定不能（Unknown）とする。** Pass ではない。

**Fail でもない。** 除外を戻した p=0.1507 は「効果が無い」証拠ではなく、
**交絡した組を混ぜた数字**だからである。正しい母集団で測り直していない以上、
どちらとも言えない。

**段階B へは進まない。**

#### (e) 何を変えるか — 母集団を事前に決める

**除外で母集団を作るのをやめる。** 処置後の変数で絞る限り、同じ罠に落ちる。

**新しい母集団の定義（処置前の変数だけで決まる）:**

> **提示が2回起きた遠征のみを対象とする。**
> すなわち実ランがステージ1・2 の両方に勝った遠征。

この定義なら:

- 差し替える獲得は**ステージ2 の後の提示**に固定される
- ステージ1・2 の結果は、その獲得より**前**に決まっている（処置前）
- その獲得より後に提示は無いので、**下流の乖離が原理的に起きない**
- `isClean` による事後の絞り込みが**不要になる**

**§8.2.4(g)-3 が本来意図していたのはこれである。** 「最後の獲得」ではなく
「**最後の提示**」に固定すべきだった。

#### (f) やり直しの事前登録

- **`HAND_LIMIT = 5` は据え置きなのに、デッキは 12→13→14 と増える。**

  これが `I4` を「`lifeLostByLeak` のみ」で測る理由である（§7.3）
- PR #208 で足した `origin`（ドロー／徴発）は、徴発を外した反復6 では常に `'draw'` になる。

## 10. テスト方針

### 10.1 計画に書くテストは、実装コードより厳しく検算する

反復5 は修正9ラウンドのうち、実装者の誤りより**計画に書いたテストの欠陥のほうが多かった**。

**「境界」「最近接」「〜されない」を主張するテストは、実際の定数と突き合わせ、
主張する分岐が本当に通る入力かを確かめる**——装甲4、弓兵4、篝火 +25%、狙撃櫓の射程3.5、
`HAND_LIMIT` 5、`MAX_COPIES` 3、`DECK_SIZE` 12、`PLACE_COOLDOWN_TICKS` 60。

### 10.2 ドメイン

- `domain/expedition/` 全ファイル（層の抽選が決定的・獲得が同名上限を守る・
  ライフが持ち越される・敗北で遠征が終わる・**要求軸が構築画面へ渡る**）
- **装甲の境界**: 装甲4 に**ちょうど4** のダメージで **0**、**5** で **1**。
  **かつ「装甲ちょうどのダメージを与えた守り手は撃破源にならない」**（§5.4.1）
- **回復**: `maxHp` を超えない。**「同 tick に致死ダメージと回復が同時に起きても `defeat` が出る」**
  ——`alive: false` を使うテストだけでは tick 内蘇生を検出できない（§5.4.2）
- **守り手の回復**: 「その tick に壊れる守り手が、修復槌で救われる」（処理順が正しいときだけ通る）
- **`hitPattern` 共用体**: `hasMassAnswer` が `scatter` を拾うこと（§5.5.1）
- **遠征の完全再生テスト**: 同一シード＋同一の獲得選択＋**`reactivate` を含む**
  同一操作列で、3ステージの決着 tick・勝敗・`unit_lost` の座標まで一致すること
  （`choose-levy` は徴発が retired のため含めない）
- **抽選の一様性**（1000シード。§7.3.1）

### 10.3 既存テストの移行（`DECK_SIZE` 20→12・魔力炉の上限）

**赤になる箇所は特定済みである。段階B の独立タスクとして扱う。**

| ファイル | 箇所 |
|---|---|
| `deck-builder.test.ts` | 12-21・25・33・43-44・108-118、**120-122（`maxCopiesOf('reactor')` が `DECK_SIZE` を期待）** |
| `card-pool.test.ts` | 175-178（`unlimited` が `['reactor']` を期待）・186-188 |
| `start-run.test.ts` | 17 |
| `DeckBuilder.test.tsx` | 145（「20枚ちょうど」の文字列直書き） |

**`balance.test.ts` に前反復が仕込んだ申し送りがある**（PR #208 のテスト docstring）:

> **反復6 で支配デッキを解消したら、この行を通常の `it` へ戻すこと**

`it.failing('どのデッキでも…')` と `it('⚠️ 既知の欠陥: 塔だけの合法デッキが素直な戦略で全勝する')` の2本が、

### 10.4 較正の対照条件が静かに壊れる経路

`balance.test.ts:194` の `padToDeckSize` は最後に **`.slice(0, DECK_SIZE)`** する。
`FULL_DECK` を20枚リテラルのまま残して `DECK_SIZE` だけ12にすると、
`deckWithout(...)` は**先頭12枚を返し、徹甲弩・篝火などを黙って落とす。**
対照条件は緑のまま、**「全要求充足」の意味だけが変わる。**

**`describe('対照条件の作り方')` に、`padToDeckSize` を実際に通して
「入力に含まれていた札が1枚も減っていない」ことを検査する assertion を追加する。**

**⚠️ 初版はこれを `cards.length <= DECK_SIZE` と書いていたが、それは恒真式である**
（`kept ⊆ FULL_DECK` かつ `FULL_DECK.length === DECK_SIZE`）。**しかも `padToDeckSize` を
一度も呼ばない。** 段階A の実装時にレビューが検出した——検出したかった当の欠陥
（`slice` が黙って札を落とす）を、その検査は原理的に捉えられなかった。
生成器を実際に通し、入力の各札の枚数が出力で減っていないことを確かめること。

### 10.5 新敵・新カードの符号の一意性

`enemy-visual.test.ts:44` は `shape:sizePct` の一意性を `ENEMY_IDS.length` で強制し、
`EnemyShape` は**5値の union に5種が1対1で割り当て済み**。盾衛・癒し手には
**新しい形を2つ union と `getShapeClipPath` に足す**必要がある。

**`MAX_ENEMY_HP = 60` は HPバー幅の絶対スケールの基準である。**
盾衛を HP 60超で作ると重装と同じ幅になり、**「絶対スケール」の契約が黙って破れる。**
**盾衛の HP は 45 とし（§5.4）、60 を超えない。**

新カード5種も**形×サイズの一意性とグリフの一意性**を両方満たすこと。
`card-text.ts` の `MISSING_WEAKNESS_IDS` は文言漏れを起動時に検出する既存の防具として機能する。

### 10.6 レビュー

- **「実装を壊してテストが赤くなるか」（変異）を必ず要求する。**
  反復5 では毎回これを指示し全件で実効性が確認できた。変異なしのレビューでは
  4件の空虚なテストが素通りしていた
- **指摘が実装側か計画側かを見極める。** 計画側なら計画を先に直してから実装者に戻す
- **並行検証は worktree で分離する。** 反復5 は4名を同一作業ツリーで並行させ、
  未追跡ファイルがビルドを壊して1名が実機確認できなかった
- **全エージェント終了後の `git status` / `git diff` の完全なクリーンを、PR 前の必須ゲートにする**

`npm run ci`（**`lint:ci`** → `typecheck` → `test:coverage` → `build`）が緑。
