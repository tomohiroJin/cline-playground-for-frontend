### 2.5 実測から確定したこと

**(a) マナは詰まない。だが層3 で余剰が戻る。**
12枚デッキは 11.3/12 出せている（「3分の1が出せない」という反証者の推定は外れ）。
ただし手札の最安札すら払えない tick が 488中402（**82%**）で、マナが律速であること自体は正しい。
**そして層3 では最終残マナが 12.3 に戻る**——反復5 の余剰問題（10/15/10）の再現である。

**(b) 徴発は骨格を壊す。** 枯渇 360 → 276、出せた枚数 11.3 → 10.1、尾 9.9% → 20.8%。
**枯渇 tick の式 `40 × (枚数 − 3)` は徴発を含まないデッキでのみ正しい。**

**(c) カウントダウン込みの実決着 tick は台本長から大きく伸びる。**
最終ウェーブ260 の台本で決着488。窓 ＝ 488 − 360 ＝ **128 tick ＝ 26.2%**。

**(d) デッキ枚数とステージ長は独立に決められない。**
12枚 / 反復5台本（長い）は **3/20**。「デッキ12枚」と「短いステージ」はセットでしか意味を持たない。

**(e) 支配デッキは層3 でのみ消える。層1・層2 では経路外のみが 20/20・18/20 で成立する。**

**これが段階0 の最大の収穫である。** 初版 §5.2 は層1 に「ブロックと単体処理」、
層2 に「群れ」「対空＋ブロック」を要求軸として宣言していたが、
**易しく作った層1・層2 ではその要求がどれも成立していなかった。**

**「易しい層」と「軸を要求する層」は両立しない。** 易しい層は「何を置いても勝てる」＝
支配戦略が成立する場所になる。**難度カーブを層の易しさで作ると、較正の不変条件1 が空虚に緑になる**——
反復5 で「空虚なテストが4件素通りした」のと同じ形を、較正の側で作ることになる。

## 4. 遠征の骨格

### 4.1 形

ローグライト。**3ステージ連続**。

- ライフは遠征を通じて**持ち越す**（ステージクリアで +3 回復。初期12。どちらも較正対象）
- 盤面の設置物はステージごとに**リセット**
- **負けたら遠征終了**。獲得したカードも失う
- ステージ間で**3択から1枚を獲得**（獲得は2回、デッキは 12 → 13 → 14）

### 4.2 レイヤ

`CombatState` は**1ステージの戦闘**を表すものとして今のまま残し、その上に遠征の層を新設する。

```
domain/expedition/
├── stage-definition.ts   StageDefinition（層・マップ・ウェーブ台本・要求軸）
├── stage-pool.ts         6ステージ（層1〜3 × 各2）
├── stage-draw.ts         派生シードから各層1つを選ぶ（決定的）
├── acquisition.ts        獲得候補3枚の抽選と、選択の適用
└── expedition-state.ts   ExpeditionState と遷移
```

`domain/expedition/` は `domain/board`・`domain/combat`・`domain/cards` を参照するが、
**逆向きの参照は作らない**（`CombatState` は遠征を知らない）。

### 4.3 状態と、2種類のデッキ検証

```ts
export type StageTier = 1 | 2 | 3;

/** デッキ述語で表せる要求軸だけを列挙する（§8.1 の不変条件1 の対象） */
export type DemandAxis = 'anti-air' | 'mass-answer' | 'heavy-hit' | 'block';

export interface StageDefinition {
  id: string;
  name: string;
  tier: StageTier;
  map: StageMap;
  waves: readonly WaveDefinition[];
  /** このステージが要求する軸。層1=1本、層2=2本、層3=3本 */
  demands: readonly DemandAxis[];
}

export interface ExpeditionState {
  seed: number;
  stages: readonly StageDefinition[];
  stageIndex: number;
  deckCards: readonly string[];   // 12 → 14 に育つ
  life: number;                   // 遠征を通じて持ち越す
  offer: readonly string[];
  acquired: readonly string[];
  phase: 'stage' | 'offer' | 'ended';
  outcome: 'running' | 'cleared' | 'failed';
}
```

**⚠️ 致命的欠陥の修正（初版はここで必ず落ちた）。**
`start-run.ts:43` が `validateDeck` を呼び、`deck-builder.ts:37` は
`cards.length !== DECK_SIZE` なら例外を投げる。**獲得後の13枚では層2 の開始時に必ず落ちる。**

**構築時の規則と実行時の不変条件を分離する:**

| 関数 | 用途 | 検査 |
|---|---|---|
| `validateDeck` | 構築画面・`PRESET_DECKS` | 枚数**ちょうど** `DECK_SIZE` ／ 同名上限 ／ 既知のカード ／ **`acquireOnly` の札を含まない** |
| `validateRuntimeDeck` | ステージ開始 | 枚数 `DECK_SIZE` 以上 `DECK_SIZE + 2` 以下 ／ 同名上限 ／ 既知のカード |

**`acquireOnly` の検査を `validateDeck` 側に入れる。** UI で隠すだけでは
`startRunWithDeck` に狙撃櫓3枚のデッキを渡せてしまう（`deck-builder.ts` の docstring 自身が
「UI 側でだけ検証すると『テストは通るが UI で組めないデッキ』が生まれる」と戒めている）。

### 4.4 決定性 — 単一ストリームをやめ、目的ごとの派生シードにする

反復5 の判定を救ったのは「`seed` ＋ `deckCards` ＋ `card_played` でランを完全再生できる」性質である。

**初版の「1本のストリームを固定順序で消費する」は2つの理由で誤りだった。**

1. `noAcquire` は3択抽選を消費しないため、**以降のシャッフルが全部ずれる**（§8.2 のゲートが壊れる）
2. 3択の抽選が「同名上限まで持つ札を除外」するなら、**棄却回数がプレイヤーの選択に依存し、消費数が可変になる**

**目的ごとに独立した派生シードを使う:**

```
SeededRandom(hash(seed, 'stage-draw'))
SeededRandom(hash(seed, 'shuffle', stageIndex))
SeededRandom(hash(seed, 'offer', offerIndex))
```

これで再生可能性は保たれたまま、**アーム間でシャッフルを共有できる**。

**乱数オブジェクトを React の state / ref に置かない。** `src/index.tsx:23` は `StrictMode` で、
`useState` の初期化子は二重に呼ばれうる。現在は毎回 `new SeededRandom(runSeed)` を作るため
冪等で無害だが、RNG を `useRef` に持たせて複数ステージにまたがらせた瞬間に決定性が壊れる。
派生シード方式なら React 側は何も保持しなくてよい。

**再生に必要なログが現状は足りない**（§9.2 で追加する）:

| 欠落 | 影響 |
|---|---|
| `chooseLevy` がログを一切記録しない（`useAshenRampartGame.ts:420-430`） | **徴発の選択が再生不能** |
| `reactivated` に `emberIndex` が無い | 燠火が2基以上あると再生が分岐する |
| `card_discarded_manual` に `handIndex` が無い | 同名札が複数あると手札配列が再現できない |

**反復5 で再生が成立したのは、判定3ランで徴発も燠火も実質使われなかった偶然である。**
遠征では札の総数が減るぶん徴発の相対価値が上がり、この偶然は続かない。

### 4.5 デッキ12枚が支配デッキに与える影響（初版の論証を撤回し、実測に置き換える）

**初版の論証は誤りだった**（§0.1）。魔力炉の密度は 25% で変わらず、
魔力炉3＋攻撃塔3種×3 の12枚は合法に組める。

**実測（§2.4）が示したのは別のことである:**

- 層3 では塔だけ12枚が greedy 5/20・経路外のみ 3/20 まで落ちる
- **しかし層1・層2 では経路外のみが 20/20・18/20 で成立する**

**したがって支配デッキを封じるのは枚数ではなく「層が軸を要求すること」である。**
§5.2 の層構成（A案）はこの実測に基づいて作り直した。

魔力炉の `maxCopies: DECK_SIZE` は撤廃して `MAX_COPIES = 3` に揃えるが、
**これは支配デッキ対策ではなく「12枚中3枚＝25% で確実に引ける」という
初版の docstring の理由がそのまま成立するからである**（20枚中3枚＝15% では不足していた）。

### 4.6 獲得が引かれることの保証（徴発を勘定に入れて書き直す）

| 条件 | 枯渇 tick | 出せた枚数 |
|---|---|---|
| 12枚・徴発なし | **360**（`40 × (12−3)` と一致） | 11.3/12 |
| 12枚・徴発1枚 | **276** | 10.1/12 |

**決定: 徴発を12枚デッキの構築プールと獲得プールの両方から外す。**

理由は3つある。

1. **§4.6 の構造的保証（獲得札は必ず引かれる）を、徴発1枚が崩す。** 実測で出せた枚数が
   11.3 → 10.1 に落ち、尾が 9.9% → 20.8% に倍増する
2. **徴発が3枚めくって1枚選ぶ動詞は、獲得（3択から1枚）とまったく同じである。**
   「獲得専用札が獲得の自己紹介になる」（§5.4）という主張は、プレイヤーが既に
   同型の3択 UI を見ていることを勘定に入れていない
3. **徴発で捨てられた2枚はイベントを一切残さない。** 獲得札が徴発で消えた場合、
   ログ上「引けなかった」ことが原理的に分からず、§7.7 の切り分けが成立しない

**徴発はカード定義としては残す**（削除しない）。20枚時代のデッキを再現する較正のために要る。
反復7 で「徴発を12枚経済へ再設計する」を持ち越し1回目として §6 に記録する。

これで **獲得した1枚は次のステージでほぼ確実に手札へ来る。**
判定項目2 が床に張り付いた場合、原因を「引けなかった」ではなく
「選ばれた／使われなかった／払えなかった」に絞り込める（§7.7）。

### 4.7 画面の流れ

```
構築（12枚） → 層1 → 獲得（3択） → 層2 → 獲得（3択） → 層3 → 遠征結果
                 ↓敗北            ↓敗北            ↓敗北
                              遠征終了（獲得も失う）
```

遠征の進行（現在どのステージか・持ち越しライフ・獲得済みの札）を常設のバーに出す。

#### 5.4.1 装甲の実装制約（初版が見落とした致命的欠陥）

**ダメージを `hpById` に書き込む箇所は5つあり、共通の適用関数が存在しない**
（`step-tick.ts` の罠628・射撃693・範囲763・貫通816・業火841）。

- 装甲は**1ヒットごと**に引く。`resolveDamage` に1回だけ入れると
  **同 tick の複数ヒットで装甲が1回しか効かない**
- **さらに深刻**: `sourceById.set` は**ダメージ量に関係なく実行される**（罠だけが `if (spec.damage > 0)` を持つ）。
  装甲4 の盾衛に弓兵（4）が撃つと、**0ダメージなのに撃破源が弓兵へ書き換わる。**
  `combat-state.ts:76` の契約「最後に**削った**者に帰属する」が破れ、
  `run-summary.ts` の `defeatsByUnit` と集計が静かに嘘になる

**段階B の先頭タスク**として、共通関数を1つ作り5箇所を置き換える:

```ts
applyDamage(hpById, sourceById, enemy, rawDamage, source)
// 内部で dealt = Math.max(0, rawDamage - armor) を計算し、
// dealt > 0 のときだけ sourceById.set する
```

#### 5.4.2 回復の処理順（tick 内蘇生を構造的に消す）

`ActiveEnemy.alive` は **`resolveDamage` まで確定しない。**
罠・射撃・業火は `hpById` を負値まで削るだけで `alive` は `true` のままである。
回復を後段に置いて `alive` だけで対象を絞ると、
**その tick に致死ダメージを受けた敵を 0 超へ戻して蘇生させる。**

**決定: 敵の回復は罠より前（`hpById` を種まきした直後）に置く。**
これで「回復は削られる前に効く」という一義的な意味になり、蘇生経路が構造的に消える。

**守り手の回復（修復槌）は `applyEnemyAttacks` の直前に置く。**
`applyEnemyAttacks` は同じ関数の中で `unit-lost` を積み `hp > 0` の守り手だけを返すため、
**後段に置くとその tick に壊れた守り手はもう配列に居らず救えない。**

### 5.7 敵の射程の可視化 — 視覚チャンネルの競合を先に解く

**カード選択中、盤面に「敵の攻撃射程が届きうる経路外セル」を示す。**
射程を持つ敵が通るレーンセルから `attackRange` 以内の経路外セルは、
マップとウェーブが決まれば確定するので**静的に事前計算**できる（この主張は検証で確認された）。

**初版が見落としていた2つの実装制約:**

1. **`RangeOverlay` は `plate.pos` を中心に描く。カード選択中には「そこ」が無い。**
   ホバーで代替すると、**最小幅360px＝タッチ環境には hover が無く、判定者の実機で一度も出ない。**
   → カード自身の射程は「置けるセルのハイライト自体を、射程が経路に届くセルに絞る」形で表現する（位置を要さない）
2. **警告色で塗る対象は「射程が届きうる経路外セル」＝そのまま守り手を置けるセルである。**
   `BoardGrid.tsx:60` は置けるセルへ既に `outline` を出しており、
   **同じセルの同じ視覚スロットを2つの意味が奪い合う**（`MAX_CELL_MARKS = 3` にも抵触）
   → 敵の射程警告は **outline ではなくセル背景の色調**で出し、役割を分ける

### 5.9 3レーン（層3「城下」）の表示側

### 5.10 プリセットデッキの作り直し

#### 7.3.1 項目1 を実プレイから外し、ユニットテストへ移す

| **4回** | 9.45 | **51.1%** |

#### 7.3.2 項目2b — 獲得が判断だったかを直接測る

**初版の項目2（獲得札が以後1回以上出された割合）はトートロジーだった。**
§4.6 が「毎ステージほぼ全枚数を引き、ほぼ全部出す」と構造で保証している以上、
**機構が動きさえすれば必ず当たる。** 実測でも 11.3/12 が出ている。

**§5.3 で次ステージの要求軸が開示されているので、「要求に応える札を選んだか」が測れる。**

- 分母: 6回（可変）の獲得のうち、**次ステージの要求軸を満たす札が3択に含まれていた回数**
- 分子: そのうち、実際にその札を選んだ回数
- **選ばない自由がある**（他の2枚を選べる）ので、トートロジーではない
- `card_acquired.offered[3]` が**選ばなかった2枚を残す**ので、判定記録で検算できる

**予測 0.6 の根拠**: 3択のうち要求軸を満たす札が1枚なら無作為は 0.33。
2枚なら 0.67。提示の構成は抽選なので、**無作為の期待値は 0.33〜0.67 の間**。
0.6 は「無作為より明確に上」を意味する下限として置く。
**段階D で、実際の抽選分布から無作為期待値を実測し、この節へ追記する**（§7.8 の手続きに従う）。

#### 7.3.3 項目3 — 鳩の巣原理を欠陥ではなく測定資源に転用する

**初版の「引いてから出すまでの遅延」は棄却する。** 検証で交絡が6経路見つかり、
そのうち3つは原理的に潰せない:

| 交絡 | なぜ潰せないか |
|---|---|
| **魔力炉の配置クールダウン60** | 12枚中3枚。**コスト0なのでマナでは切り分けられない** |
| **徴発・初期手札3枚に `card_drawn` が無い** | 12枚の25%に遅延が定義できない（徴発は §4.6 で外したが初期手札は残る） |
| **決着時に手札に残った札が母集団から落ちる** | **抱えた札ほど中央値から消える＝反復5 §3.4 と同型の穴に逆向きで落ちる** |

さらに「遅延はドロー順に影響されない」という初版の中心的正当化が誤りだった——
**マナ蓄積が時間の関数である以上、遅延は到着時刻＝ドロー順の関数である。**
実測でもマナ待ちの tick が 82% を占める。

**代わりに、検証が「欠陥」として指摘した性質を測定資源に使う。**

各層は2択、遠征は3回。**鳩の巣原理により、どの層でも同じステージが2回以上出ることが確定する。**
検証はこれを「同一台本の再演が確定する＝交絡」と指摘したが、
**地形が同一のペアが必ず手に入るということでもある。**

**指標の完全な定義:**

1. **配置セル集合** `P(stage, expedition)` ＝ そのステージで記録された `card_played` のうち
   `x, y` を伴うものの `(x, y)` の集合（重複除去。罠・魔力炉を含む）
2. **再演ペア** ＝ 同じ `stageId` が2つの異なる遠征で出た組。3遠征なら層ごとに1組以上（層3 は到達した遠征のみ）
3. **`J_human`** ＝ `|P₁ ∩ P₂| / |P₁ ∪ P₂|`
4. **`J_greedy`（ペアごとの反実仮想）** ＝ 同じ `stageId` を、**そのペアの実際の2つのデッキ**
   （初期12枚＋その時点の獲得札）で `greedyStrategy` に解かせた配置の Jaccard
5. **判定** ＝ `J_human < J_greedy` が、成立したペアの**過半**

**なぜこの形か:**

- **地形交絡がゼロ。** 同一ステージなので、置ける場所も経路も完全に同じ
- **デッキ変化の交絡が除かれる。** `J_greedy` は「適応ゼロで、デッキの違いだけで説明される変化量」であり、
  人間がそれを下回れば**デッキでは説明できない変化＝適応**である
- **`greedyStrategy` を閾値の源にしていない。** 初版は「測れないと宣言した測定器から閾値を取る」自己矛盾を犯していた。
  ここでは greedy は**閾値ではなく下限（適応ゼロの基準）**として使い、比較は差分で行う
- **曖昧語が無い。** 「床から離れ」「低い」のような未定義語を使わず、すべて演算で定義した

**ペアが1組も成立しない場合**（例: 3遠征とも層1 で敗北し、層1 のペアはあるが層2・層3 が無い）
——層1 のペアだけで判定する。**層1 のペアすら無いことは鳩の巣原理により起こらない。**

#### 7.3.4 項目5 の「15% 未満」の根拠（実測から導出）

§2.4 の greedy 実測と、反復5 で得られた人間/greedy 比から導く。

| | greedy 実測（§2.4） | 人間/greedy 比 | 人間の予測 |
|---|---|---|---|
| 層1 | 9.9% | 0.53〜0.73 | 5.2〜7.2% |
| 層2 | 15.2% | 同 | 8.1〜11.1% |
| 層3 | **34.0%** | 同 | **18.0〜24.8%** |
| 平均 | 19.7% | 同 | **10.4〜14.4%** |

**15% はこの範囲の上端である。**

**⚠️ 層3 単独では baseline（20.3〜28.0%）と重なる。** 層3 は決着 720 tick と長く、
枯渇 360 からの窓が広い。**層3 の尾は反復6 でも解消しない。**
これを §7.9 の帰結に含め、**反復7 の課題として先に宣言する**（後から「想定内だった」と言わないため）。

#### 7.3.5 項目6 を比率にする理由と、層3 の余剰

実測（§2.4）で最終残マナは 層1 3.4 / 層2 4.7 / **層3 12.3**。
**層3 では反復5 の余剰問題（10/15/10）が再現している。**

絶対値で「baseline より小さい」とすると層1・層2 では自動達成、層3 では未達になる。
**比率（残マナ ÷ 総マナ収入）で測る**: 層1 3.4/14.8 = 0.23、層2 4.7/17.4 = 0.27、層3 12.3/26.1 = 0.47。

**予測は層1・層2 のみに置く（0.25 未満）。層3 は継続観察とし、余剰が残ることを先に認める。**

#### 7.3.6 項目7 を「踏破」から「層3 到達」へ変える

**初版の「3遠征中1〜2回踏破」は、真の踏破率が20%〜80%のどこにあっても
半分近く合格する**（n=3 の二項分布）。較正の失敗を検出できない。

**さらに重要な理由がある。** 初版は新敵2種を層3 専用に置きながら、
「3遠征中1〜2回踏破」と予測していた。**この反復の目玉である敵2種が、
判定セッションで一度も画面に出ない可能性を構造的に放置していた**（致命的指摘）。

**決定:**
- **癒し手を層2「鴉の谷」にも1体出す**（軸にはならない予告個体）
- **層3 の両ステージに盾衛と癒し手を置く**（層3 に到達すれば必ず両方見る）
- **項目7 の指標を「層3 への到達率」にし、予測を 2/3 以上に置く**
- **踏破率は §8.1 の不変条件3（8通り×20シード＝160遠征）で測り、実プレイでは測らない**

### 7.4 主観 — 中立な文面と、肯定/否定のコード化を事前登録する

### 7.5 反証条件 — 客観の失敗を主観で救わせない

**初版の連言は反証回避の装置になっていた**（Codex が1本ずつ判定し、4本を「不当」と結論）。

| # | 条件 | 判定 |

### 7.8 閾値の後出しを禁じる手続き

**閾値そのものではなく、算出アルゴリズムを先に登録する**（Codex の指摘）。
現時点で値が未確定なのは **項目2b の無作為期待値**だけである。

**登録する算出手続き:**

1. **使用データ**: 段階D の較正で生成した8通り×20シード＝160遠征の `card_offered` 相当の抽選結果
2. **算出式**: 「次ステージの要求軸を満たす札が3択に含まれた提示」について、
   その3枚のうち要求軸を満たす札の枚数 `k` の分布を取り、無作為期待値 ＝ `E[k/3]`
3. **除外規則**: 提示が起きなかった遠征（層2 で敗北）は除外。丸めは小数第2位で四捨五入
4. **追記のタイミング**: **実プレイ判定を開始する前**に、本設計書へ**別コミット**で追記する
5. **追記後の変更を禁じる**: 追記コミットの SHA を判定記録に記載する

**この5点を守れないなら、項目2b は閾値を持たない所見に格下げし、F1 から外す。**

### 8.2 段階A の出口ゲート `G1` — 反実仮想で測る（初版のゲートは反転していた）

**初版のゲートは「差が出れば合格」だったが、`createDeck` のシャッフルが
枚数で変わるため必ず差が出る。獲得が因果的に無力でも通った。**

**作り直す。**

1. **基底の並びを揃える。** §4.4 の派生シードにより、両アームで同じ12枚シャッフルを共有する。
   **獲得札はシャッフル後の山札の固定位置に挿入する**（末尾から3枚目など。位置は定数化）
2. **差を勝率ではなく反実仮想で測る。** 反復5 で確立した手法をそのまま使う——
   **同一シード・同一操作列を再生し、獲得札だけを抜いて結果が変わるか**を見る
3. **獲得戦略を1本にしない。** `noAcquire` / `randomAcquire` / `cheapestAcquire` /
   `demandAwareAcquire`（次ステージの要求軸を満たす札を選ぶ）を並べ、
   **獲得戦略の癖と獲得機構の効果を分離する**

**ゲートの判定:**

- **`demandAwareAcquire` と `randomAcquire` の踏破率に差が出る** → 獲得は「選び方」が効いている。較正を進める
- **差が出ない** → 獲得は較正上ゼロであり、**§4.6 と項目2b の前提が崩れている。**
  較正を続けず、**設計（獲得の枚数・獲得プールの強度・要求軸の開示）へ戻る**

**`greedyAcquire`（最も高コストを取る）は単独では使わない。**
マナが唯一の律速である greedy にとって**最も打てない札を選び続ける戦略**であり、差の符号が解釈できない。

#### 8.2.1 `G1` の実測と判断（段階A・2026-09-05）

`greedyStrategy` ・ シード1〜20 × プリセット2種 ＝ **各腕40遠征**。暫定ステージ（段階B で置き換える）で測定。

|---|---|---|---|---|
| `noAcquire` | **17/40** | 33/40 | 88 | 0 |
| `randomAcquire` | **11/40** | 31/40 | 80 | 69 |
| `cheapestAcquire` | 12/40 | 33/40 | 83 | 71 |
| `demandAwareAcquire` | **17/40** | 34/40 | 89 | 72 |

測定の健全性はレビューで独立に検証済み——4腕でシード・プリセット・盤面戦略が共通、
`randomAcquireOf` の rng は他腕を汚染できない（シャッフルと抽選は別々の派生シード）、

### 8.2.2 `G1` は通ったが、「獲得が遠征を強くする」ことは支持されていない

**合格条件（§8.2）は満たされた。** `demandAwareAcquire`（17）と `randomAcquire`（11）に差があり、
獲得内容も 18/20 の遠征で異なっている。**獲得の「選び方」は結果を動かしている。**

**しかし `noAcquire` が 17/40 で `demandAwareAcquire` と同着である。**

読み方はこうなる——**獲得は期待値を上げない。獲得が作るのは「下振れのある選択」である。**

| | 踏破 | 取らない場合との差 |
|---|---|---|
| よく選ぶ（demandAware） | 17 | **±0** |
| 適当に選ぶ（random） | 11 | **−6** |
| 安く選ぶ（cheapest） | 12 | **−5** |
| 取らない（noAcquire） | 17 | — |

**これは設計として擁護できる。** デッキが 12→13→14 と育つと1枚あたりの引き確率が薄まり、
マナが律速である（段階0 の実測で 82% の tick が「手札の最安札すら払えない」）ため、
軸に合わない札は純粋な希釈になる。**取る／取らないに重みがあることは、
ローグライトとしてはむしろ望ましい形である**——獲得が単純に加算的なら「何でも取ればいい」になり、
選択が判断にならない。

**しかし、次の主張は支持されていない。判定記録に書いてはならない:**

> ❌ 「獲得によって遠征が強くなる」

`demandAwareAcquire` は `noAcquire` に**並んだだけで、上回っていない**。
これを書けば、根拠のない因果の主張になる（反復5 の初版判定記録が犯した型）。

**支持されているのは次だけである:**

> ✅ 「獲得の選び方が遠征の結果を動かす。よく選べば取らないのと同等、雑に選べば取らないより悪い」

**帰結:**

1. **判定項目2b（獲得が判断だったか）の枠組みは有効。** むしろ「選び方に結果が付いてくる」ことが実測で裏づいた
2. **段階D の較正で「獲得プールの強度」を見直す候補にする。** 現状では最善手が現状維持と等価で、
   獲得が上振れを生んでいない。獲得専用札（狙撃櫓・修復槌・鼓舞旗）が入る段階B で再測定する
3. **この留保を判定記録の §1.1 の照合対象に含める**（§1.1 の不満リストと同じ扱いで、
   「言われなかったが数値に出ているもの」として）

### 8.2.3 `reachedTier3` は腕の弁別には鋭敏でない

4腕とも 31〜34/40（77.5〜85%）で、踏破率ほどの差が出ていない。

### 8.3 較正の実行時間に予算を置く

`balance.test.ts` の**現行の実測は98秒**（31テスト・20シード×約13スイープ）。

## 10. テスト方針

### 10.1 計画に書くテストは、実装コードより厳しく検算する

反復5 は修正9ラウンドのうち、実装者の誤りより**計画に書いたテストの欠陥のほうが多かった**。

**「境界」「最近接」「〜されない」を主張するテストは、実際の定数と突き合わせ、
主張する分岐が本当に通る入力かを確かめる**——装甲4、弓兵4、篝火 +25%、狙撃櫓の射程3.5、
`HAND_LIMIT` 5、`MAX_COPIES` 3、`DECK_SIZE` 12、`PLACE_COOLDOWN_TICKS` 60。

### 10.2 ドメイン

- `domain/expedition/` 全ファイル（層の抽選が決定的・獲得が同名上限を守る・
  ライフが持ち越される・敗北で遠征が終わる・**要求軸が構築画面へ渡る**）
- **装甲の境界**: 装甲4 に**ちょうど4** のダメージで **0**、**5** で **1**。
  **かつ「装甲ちょうどのダメージを与えた守り手は撃破源にならない」**（§5.4.1）
- **回復**: `maxHp` を超えない。**「同 tick に致死ダメージと回復が同時に起きても `defeat` が出る」**
  ——`alive: false` を使うテストだけでは tick 内蘇生を検出できない（§5.4.2）
- **守り手の回復**: 「その tick に壊れる守り手が、修復槌で救われる」（処理順が正しいときだけ通る）
- **`hitPattern` 共用体**: `hasMassAnswer` が `scatter` を拾うこと（§5.5.1）
- **遠征の完全再生テスト**: 同一シード＋同一の獲得選択＋**`choose-levy` と `reactivate` を含む**
  同一操作列で、3ステージの決着 tick・勝敗・`unit_lost` の座標まで一致すること
- **抽選の一様性**（1000シード。§7.3.1）

### 10.3 既存テストの移行（`DECK_SIZE` 20→12・魔力炉の上限）

**赤になる箇所は特定済みである。段階B の独立タスクとして扱う。**

### 10.4 較正の対照条件が静かに壊れる経路

`balance.test.ts:194` の `padToDeckSize` は最後に **`.slice(0, DECK_SIZE)`** する。
`FULL_DECK` を20枚リテラルのまま残して `DECK_SIZE` だけ12にすると、
`deckWithout(...)` は**先頭12枚を返し、徹甲弩・篝火などを黙って落とす。**
対照条件は緑のまま、**「全要求充足」の意味だけが変わる。**

**`describe('対照条件の作り方')` に、`padToDeckSize` を実際に通して
「入力に含まれていた札が1枚も減っていない」ことを検査する assertion を追加する。**

**⚠️ 初版はこれを `cards.length <= DECK_SIZE` と書いていたが、それは恒真式である**
（`kept ⊆ FULL_DECK` かつ `FULL_DECK.length === DECK_SIZE`）。**しかも `padToDeckSize` を
一度も呼ばない。** 段階A の実装時にレビューが検出した——検出したかった当の欠陥
（`slice` が黙って札を落とす）を、その検査は原理的に捉えられなかった。
生成器を実際に通し、入力の各札の枚数が出力で減っていないことを確かめること。

### 10.5 新敵・新カードの符号の一意性

`enemy-visual.test.ts:44` は `shape:sizePct` の一意性を `ENEMY_IDS.length` で強制し、
`EnemyShape` は**5値の union に5種が1対1で割り当て済み**。盾衛・癒し手には
**新しい形を2つ union と `getShapeClipPath` に足す**必要がある。

**`MAX_ENEMY_HP = 60` は HPバー幅の絶対スケールの基準である。**
盾衛を HP 60超で作ると重装と同じ幅になり、**「絶対スケール」の契約が黙って破れる。**
**盾衛の HP は 45 とし（§5.4）、60 を超えない。**

新カード5種も**形×サイズの一意性とグリフの一意性**を両方満たすこと。
`card-text.ts` の `MISSING_WEAKNESS_IDS` は文言漏れを起動時に検出する既存の防具として機能する。

### 10.6 レビュー

  反復5 では毎回これを指示し全件で実効性が確認できた。変異なしのレビューでは

- **並行検証は worktree で分離する。** 反復5 は4名を同一作業ツリーで並行させ、

- **全エージェント終了後の `git status` / `git diff` の完全なクリーンを、PR 前の必須ゲートにする**
