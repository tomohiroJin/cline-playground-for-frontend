# 灰燼の城壁 リアルタイム・デッキ PoC 設計書

> 2026-07-29 策定。既存の `src/features/ashen-rampart/` を**同名のまま作り直す** PoC。
> 前コンセプト（予告反証ゲーム化・Epic #188）は 2026-07-29 に No 判定で終了済み。

## 1. なぜ作り直すのか

前コンセプトは実プレイで棄却された。原因は Epic #188 のクローズコメントに記録済みだが、要点は2つ:

1. **弓兵の塔が数学的な支配戦略だった**。DPS/マナで弓兵 0.375 に対し火砲台 0.22。支援系（かがり火・鍛冶の加護）は隣接3基／塔4基で初めて元が取れるが、マナ4/ウェーブ・3ウェーブ最大6基という尺では到達不能
2. **敵にカウンター要求が無かった**。雑兵・俊足・重装は HP と速度が違うだけで、すべて「火力を増やす」という同一の答えで解けた

この2点は「フェーズ分離＋事前計算戦闘」という構造とは独立の欠陥であり、観戦体験を磨いても直らない。したがってコンセプトを入れ替える。

## 2. コンセプト＝反証可能な面白さの仮説

> **プレイヤーは有限の札を「今切るか、この先のために温存するか」で配分し、切り時の判断が当たった／外れたことを実感して面白がる。**

ジャンルの組み合わせ（MTG × RTS × TD）は仮説ではなく手段である。前回の設計書はここを取り違えて「ジャンルと世界観の列挙」をコンセプト節に書き、「なぜ面白いのか」が不在のまま実装に進んだ。同じ形を繰り返さないため、判定対象は上記の一文に限定する。

**この仮説が成立するための必要条件**（いずれか欠けたら仮説は判定不能）:

- 札を**全部は出せない**こと（出せるなら配分は発生しない）
- 出す／出さないの選択が**排他的**であること（同時に両方できるなら選択ではない）
- 出さなかったことに**代償**があること（無料なら温存は決断ではない）

設計はこの3条件を機構として保証する（§4）。

## 3. スコープ＝最小垂直スライス

**1マップ・4ウェーブ・カード8種・敵5種**。全要素を入れるが各1つずつに絞る。

| 入れる | 入れない（理由） |
|---|---|
| リアルタイム進行・自動ドロー・手札上限 | デッキ構築 UI（プリセット選択で代替。構築はリアルタイム層の面白さを何も教えない） |
| コストのカード化（魔力炉） | 早送り・スキップ・リプレイ（リアルタイムでは観戦が存在しない） |
| 配置スロット有限・同名上限 | ウェーブ報酬・フェーズ分離 |
| カウンター要求3軸（各敵1種） | 複数マップ・ボス |
| 再起動ギミック（カード1枚） | 魔力炉の暴走（§10 将来案） |
| 次ウェーブの予告 | 物語・演出強化 |
| **一時停止**（§9.6） | 早送り・スキップ（別問題として削除） |
| **画面設計一式**（§9） | 複数解像度の作り込み |

削る基準は「**これが無いと仮説を判定できないか**」の一点。飛行敵が1種いれば「対空を温存する理由」は成立し、3種いても判定の質は上がらない。

## 4. 資源とテンポ

1 tick = 100ms（既存踏襲）。ラン長は約 **950 tick（95秒）**。

| 項目 | 値 |
|---|---|
| デッキ上限 | **20枚** |
| 同名上限 | **3枚** |
| 手札上限 | **5枚** |
| 初期手札 | **3枚** |
| ドロー間隔 | **40 tick（4秒）に1枚** |
| 手札溢れ時 | 上限に達している場合、そのドローは**墓地へ直行**（プレイヤーは選択しない）。失った札は §9.5 で可視化する |
| 配置クールダウン | **60 tick（6秒）に1回** |
| 初期マナ | **2** |
| マナ自然回復 | **なし** |
| 魔力炉の生成 | **60 tick（6秒）ごとに +1マナ** |
| ライフ | **10**（敵1体の漏れで −1、0で敗北） |
| 敗北条件 | ライフ 0 |
| 勝利条件 | 4ウェーブの敵をすべて処理しきる |
| デッキ切れ | **敗北ではない**。以後ドローが止まるだけで、**手札に残った札は引き続き配置できる**。手札も尽きたら盤面と再起動で戦う |
| 再発動（燠火） | **マナも配置クールダウンも消費しない**（クリックのみ）。終盤に操作対象を残すための措置 |

### 4.1 3つの必要条件が機構でどう保証されるか

**全部は出せない**: 950 tick で引ける枚数は 20（デッキ全部）、配置できる回数は 950 ÷ 60 = **15回**。差の5枚は必ず出せずに終わる。

**排他的**: 配置クールダウン中は他の札を出せない。「弓兵か弩砲か」は同時に選べない。

**代償**: 出さなかった札は手札を占め、上限に達すれば以後のドローが墓地へ直行する。温存は無料ではない。

### 4.2 マナ経済の検算

15回の配置のうち魔力炉に何回使うかがランの骨格になる。魔力炉以外の平均コストは約 2.1（弓兵2・弩砲3・火砲台3・棘罠1・時泥2・業火2・篝火2）。

| 魔力炉 | 生成マナ（初期2込み） | 残り13〜14回に必要なマナ | 判定 |
|---|---|---|---|
| 1基（tick 60 設置） | 16 | 約 29 | **足りない** |
| 2基（tick 60・120） | 29 | 約 27 | **拮抗** |
| 3基（tick 60・120・180） | 41 | 約 25 | 余るが、スロットと配置回数を1つ余計に失う |

平均コストの安いデッキなら1〜2基で回り、高いデッキなら3基要る。**デッキ構成によって最適な魔力炉数が動く**ため、プリセットの差別化軸になる。

### 4.3 スロットの収支

現行マップの設置スロットは **12**。罠は経路セルに置くためスロットを消費しない。

魔力炉2基なら塔に使えるのは10スロット。15回の配置は「魔力炉2 + 塔10 + 罠/呪文3」でちょうど埋まる。**スロット・配置回数・マナの3つが同時に拘束条件になる**ように数値を合わせてある。

> これらの数値（ドロー40 / 配置60 / 魔力炉60 / ライフ10）が主要な調整つまみである。実プレイで最初に疑うべき対象。

ウェーブは重なりうる（リアルタイム連続進行）。次ウェーブの構成は予告として常時表示する。

**この敵数は概算に基づく出発点である。** 当初案（総HP 736）は防衛力に対して約2倍過剰だった。概算の根拠:

- 標準的な建て方（tick 900 までに塔10基）の塔存在時間は約 3800 tick
- 実効射撃率を 50% と仮定すると 1900 tick × 0.75 DPS ≒ **1400 ダメージ**
- 実効射撃率 50% は旧実装の実測（弓兵1基で W2 敗北・3基で漏れ0）と整合する

防衛力が敵総HPを大きく上回ると、**15回の配置枠を使い切る必然性が消え、配分の圧力そのものが働かない**。したがって難度は快適さの問題ではなく、仮説が成立するための条件である。

**それでもこの数値は仮説にすぎない。** §7 の自動検算テストを先に用意し、そこで較正してから実プレイに入る。手で当てにいかない。

## 7. 支配戦略チェック

**前回はこの検算をせずに実装し、3回の実プレイと3つの Epic を費やして初めて欠陥を知った。** 今回は設計段階で通す。

DPS/マナは 弓兵 0.375 > 弩砲 0.277 > 火砲台 0.223 で、**弓兵が最効率である点は前回と同じ**。それでも潰れない理由:

1. **同名上限 3枚**により弓兵は最大3基。合計 2.25 DPS が天井になる
2. **弓兵は飛行に当たらない**。鴉が出た時点で弓兵の枚数は無意味になり、弩砲を温存していたかが問われる
3. **鴉は経路中盤から出現する**ため、弓兵を入口寄りに固める最適配置も同時に崩れる
4. **群れは範囲を要求する**。単体攻撃の合計 DPS が足りていても処理が間に合わない

採用した原則は「**最高効率のカードには必ず効かない相手を作る**」である。効率を平準化してどれも似た性能にすると、選ぶ理由そのものが消える。**効率差は残し、適用範囲で差をつける。**

### 全カードが原則を満たすことの確認

原則を宣言することと、全要素に適用することは別作業である。初稿では業火だけが例外になっていた（全敵・射程無制限・再発動無料で、カウンター要求をすべて迂回できた）。全カードについて「効かない相手」を明示する:

| カード | 効かない相手 |
|---|---|
| 弓兵の塔 | 飛行 |
| 弩砲 | なし（代わりに DPS/マナが最低クラス） |
| 火砲台 | 飛行・単体高HP（範囲は重装に非効率） |
| 棘罠 | 飛行・使い切り後 |
| 業火／燠火 | **飛行**・設置セルから半径2の外 |
| 時泥 | ダメージを与えない（単体では勝てない） |
| 篝火 | 単体では0ダメージ |
| 魔力炉 | 単体では0ダメージ |

弩砲だけが「効かない相手なし」だが、DPS/マナ 0.277 と効率で劣後させることで釣り合いを取っている。**汎用性と効率のどちらかは必ず犠牲にする**という形で原則を統一した。

### 自動検算をテストとして常設する

`stepTick` が純粋関数であるため、UI 抜きでランを丸ごと回すテストが書ける。以下を CI で常時検証する:

- 単一カードだけのデッキ（弓兵20枚相当・同名上限を無視した仮想デッキ）では**勝てない**こと
- 用意した各プリセットデッキで勝率が偏りすぎないこと

これは「支配戦略が生まれていないか」の回帰テストであり、バランス調整のたびに自動で再検証される。

## 8. アーキテクチャ

### 8.1 中核の作り替え

```
現状: simulateWave(board, wave, modifiers) → CombatResult{ ticks[] }
      └ 内部で MAX_TICKS までループ。「配置は1ウェーブ不変」が前提

新規: stepTick(state, actions, rng) → state
      └ 1 tick だけ前進する純粋関数。決定性は維持
```

`CombatState` が敵・塔・罠・マナ・手札・デッキ・墓地・経過 tick を一括で保持する。リアルタイムではこれらが相互に影響するため、分割すると追跡が難しくなる。

乱数（ドロー）は既存パターンを踏襲し、`domain` は `RandomFn = () => number` のみを受け取る。`RandomPort` は `application/ports` に置く。シード固定により決定性を保ち、リプレイと事故の事後判別を可能にする。

### 8.2 時間を進めるのは presentation だけ

`setInterval(100ms)` で `stepTick` を呼ぶ薄い層のみを presentation に置き、**ロジックは一切持たせない**。

これは既存の地雷マップにある教訓（`src/features/air-hockey/` は Canvas/requestAnimationFrame にロジックを持たせたためテストが困難）の回避策である。

### 8.3 既存からの再利用

| 再利用するもの | 内容 |
|---|---|
| `domain/board/stage-map.ts` / `board-state.ts` | 盤面・経路・設置スロット・地形（高台・滞留） |
| `domain/combat/simulate-wave.ts` の 1tick 計算部 | ターゲティング・射程判定・ダメージ・範囲・罠・オーラ合成 |
| `presentation/enemy-visual.ts` / `EnemyMarker` / `EnemyLegend` / `cell-descriptor.ts` | PR #180 の可読性資産（敵の描き分け・凡例・HPバーの絶対スケール） |
| `application/ports/play-log-port.ts` / `infrastructure/play-log/` | 行動ログ基盤（スキーマを v2 に更新。§11 参照） |

### 8.4 削除するもの

`simulateWave` のバッチループと `CombatResult.ticks[]`、リプレイ再生、`BattleControls`（早送り・スキップ）、`RewardPanel`、`WavePreview` の予告パズル用途、フェーズ分離（`RunPhase`）、`choose-reward.ts`、`start-wave.ts` の finishWave 系。

### 8.5 層構成

```
src/features/ashen-rampart/
├── domain/
│   ├── board/          # 盤面（再利用）
│   ├── cards/          # カード定義・デッキ・手札・墓地の規則
│   ├── combat/         # CombatState・stepTick・敵・ウェーブ
│   └── run/            # ラン状態（ライフ・勝敗）
├── application/
│   ├── ports/          # RandomPort・PlayLogPort
│   └── use-cases/      # start-run / play-card / reactivate
├── infrastructure/     # 乱数・行動ログ
└── presentation/       # ゲームループ・盤面・手札・状態表示・凡例（§9）
```

### 8.6 一時停止の置き場所

一時停止はゲームループの制御であり、ドメインの状態ではない。`setInterval` を止めるだけで `stepTick` は呼ばれなくなるため、**presentation の薄い層で完結する**（§8.2 の方針を崩さない）。

ログ記録は `application/use-cases` 経由で行う（副作用のオーケストレーションは use-case を通す規約に従う）。

## 9. 画面設計

初稿にはこの節が存在しなかった。前作 S1（#179）は**静止した盤面の可読性だけでスプリント1本を費やし、それでも合格に2周かかった**。リアルタイム化は可読性の難度を上げこそすれ下げないため、実装前に決めておく。

### 9.1 情報系統をグループ化して7以内に収める

設計が要求する情報は素で数えると9系統ある（手札／マナ／配置クールダウン／ドロー残／スロット空き／敵／予告／燠火の再起動可否／ライフ）。ミラーの法則（5〜7）を超えるため、**近接の法則でグループ化し、同時に読む「枠」を減らす**。

```
┌─ 上部固定（ラン状態）────────────────────────┐
│  ライフ  ウェーブ番号  次ウェーブ予告  ⏸一時停止 │
├─ 中央（盤面）─────────────────────────────┤
│                                              │
│   9×7 グリッド                                │
│   経路・設置スロット・地形・敵・塔・燠火        │
│                                              │
├─ 下部固定（手札と資源）──────────────────────┤
│  マナ  [統合タイマー]  手札5枚  墓地数         │
└──────────────────────────────────────────┘
```

- **スロットの空き状況は盤面そのもの**で表す（別表示を作らない）
- **燠火の再起動可否は盤面上のマーカー**で表す（別枠を作らない）
- **配置クールダウンとドロー残は1本の統合ゲージに統合**（下記 9.2）

結果、同時に走査する枠は「上部3・盤面1・下部3」の**7枠**に収まる。

### 9.2 統合タイマー（2本の非同期タイマー問題）

配置クールダウン（60 tick）とドロー（40 tick）は周期が異なり非同期に走る。別々のゲージにすると「次に何かできるのはいつか」を2箇所から読む必要が出る。

**1本のトラック上を2つのマーカーが進む形**にする。共通運命の法則により、2つの周期が1つの情報単位として認識される。

### 9.3 群れのスタック表示（描画密度の破綻を防ぐ）

§6 の較正でウェーブ3は群れ20体になった。間隔3 tick・速度0.12 なので**間隔は0.36セル**、経路11セルのうち **7.2セル分を群れだけで埋める**。1セルあたり約2.8体で、マーカーは重なり HP バーは読めない。

**同種かつ0.5セル以内の敵を1マーカーに集約し、体数バッジを付ける。**

- バッジ: マーカー右下に体数（例: `×7`）
- HPバー: スタック内の**合計残量比**を表示（個体別は表示しない）
- 集約は同種のみ。雑兵と群れは別マーカーのまま

これは表示上の集約であり、ドメインの敵は個体のまま扱う（`stepTick` は変更しない）。

> **教訓の記録**: この問題は、敵数を2倍に較正した §6 の修正が引き起こした。**数値設計と表示設計を別々に検証すると、片方の正しさが他方を壊す。** 以後、敵数を変更したら描画密度を再計算する。

### 9.4 配色（60-30-10 と警告色の分離）

既存実装は `#8b2635`（暗い赤）を全コンポーネントの主色として使っている。ゲームUI では**赤は危険・緊急に予約すべき色**であり、主色に使うと本当の危険を赤で伝えられない。前作は戦闘が事前計算で危険の即時通知が不要だったため顕在化しなかった。

| 役割 | 比率 | 色 | 用途 |
|---|---|---|---|
| ドミナント | 60% | 暗い灰（灰燼） `#1a1614` | 背景・盤面の地 |
| セカンダリ | 30% | 灰白 `#e8ded2` | テキスト・枠・パネル |
| アクセント（危険） | 10% | 赤 `#8b2635` | **ライフ低下・敵の接近・警告のみ** |
| アクセント（好機） | 10%内 | 琥珀 `#e8a33d` | **再起動可能・配置可能・要操作** |

赤をテーマから外すのではなく、**危険側に予約し直す**。ダークファンタジーの世界観は暗色ドミナントで担保する。

色だけに依存しないこと（色覚多様性）: 危険はテキスト（「残り2」）を、好機は形状（脈動する枠）を併用する。

### 9.5 フィードバック

| 事象 | 表現 |
|---|---|
| 手札溢れで札を失った | 失った札名を手札枠の上に **60 tick（0.6秒）表示**してから墓地へフェード。何を失ったかが見えないと理不尽として体感される |
| 燠火が再起動可能になった | マーカーが琥珀で脈動。加えて下部バーに可能な件数を表示 |
| 配置できない（マナ不足） | 手札カードを減光し、不足量を表示 |
| ライフが減った | 盤面外周が赤く一瞬明滅＋数値の変化 |

**燠火の再起動可能状態は消えない。** 押すまでクールダウンは進まないため、押し忘れても損失は「遅れた分」に留まり、常時監視を強制しない。リアルタイム中の監視対象を増やさないための措置。

### 9.6 一時停止

**スペースキーまたは ⏸ ボタンで一時停止できる。**

- 一時停止中は盤面・タイマーが停止し、手札とカード効果は**閲覧できるが配置はできない**
- 配置可能にすると熟考ゲームになりリアルタイム性が消えるため、**戦術的優位は与えない**
- 目的は認知負荷とアクセシビリティの緩和であり、観戦装置ではない（早送り・スキップを削除した判断とは別問題）

**一時停止の回数と累計時間をログに記録し、判定に使う**（§11 判定項目6）。9系統の情報を6秒サイクルで処理できているかの指標になる。

### 9.7 選択空間の削減とタッチ対応

手札5枚 × スロット12 = **60通り**の選択空間がある。カードを選択すると、**そのカードが置けるスロットだけを琥珀でハイライト**する（既存の射程オーバーレイの発展）。塔は設置スロット、罠は経路セル、即時呪文は盤面全体、と種別で対象が変わるため、実質的な選択肢は数個に落ちる。

タッチ対応: 最小対応幅 360px。9セル幅では1セル約36pxとなり 44×44px のタッチターゲットを満たさないため、**ハイライトされたスロットのみヒットエリアを44px以上に拡大する**（視覚サイズは変えない）。ハイライトで対象が絞られているため、拡大したヒットエリア同士は重ならない。

`prefers-reduced-motion` 指定時は、脈動・明滅を静的な枠線とアイコンに置き換える。

## 11. 判定の事前登録

前回の最大の失敗は「事前登録した項目を判定に使わなかった」ことである（S1 では行動記録を登録しながら CoS に含めず、ユーザーが一度も遊ばないままクローズした）。**ここに書く項目は全部判定に使う。**

**実施**: 同一プリセットデッキで **3ラン**。うち**2ランは同一シード**、1ランは別シードとする。同一シードのペアはドロー順が完全に一致するため、配置の違いを学習に帰属させられる（シードが全部違うと、配置の変化が学習か引き順かを切り分けられない）。

| # | 収集項目 | 何が分かるか |
|---|---|---|
| 1 | **札の手札滞留時間**（引いた tick → 出した tick）と、**最後まで出さなかった札** | 配分の決断が実際に発生したか。滞留がほぼ0なら「引いたら即出す」であり、温存は起きていない |
| 2 | 同一シードの2ラン間で**配置が変わったか**（ログ） | 学習が起きたか。ドロー順が同一なので、違いは判断の変化に帰属する |
| 3 | **予告を見た後に配置を変えたか**（予告表示 tick と直後の配置の突き合わせ） | 温存の理由③（先の脅威に備える）が働いているか。無関係なら予告はスコープから外せる |
| 4 | 勝敗理由の記述（`run_note`） | 「引きが悪かった」が支配的なら事故側の問題（§12） |
| 5 | ユーザーの主観判定（面白いか Yes/No） | 最終判定 |
| 6 | **一時停止の回数と累計時間** | 9系統の情報を6秒サイクルで処理できているか。多用されるなら情報量か時間設計が過大（§9.1） |

> **項目1の設計変更（初稿からの修正）**: 初稿は「手札溢れで何を捨てたか」を配分の指標にしていたが、§4 では溢れたドローが自動で墓地に行き**プレイヤーは何も選んでいない**ため、この記録には決断が1ビットも含まれない。滞留時間と未使用札に置き換えた。溢れの発生自体は別途カウントし、前提確認（溢れが起きているか）にのみ使う。

### 反証条件（先に定義する）

- 3ラン中2ラン以上で敗因が「引き」なら → **コスト札の事故込み採用を見直す**（初期手札5枚、初手に魔力炉確定、または資源デッキ分離へ）
- **マナ0かつ手札に魔力炉が無い「何もできない時間」が体感で目立つなら** → §12 の引き受けたリスク2を見直す（最低限の自然回復を入れる）
- 配置クールダウン中に何もすることがないなら → **テンポ設計を見直す**（クールダウン短縮、または再起動ギミックの増設）
- 手札溢れが一度も起きないなら → **ドロー速度と配置間隔の比を見直す**
- 札の滞留時間がほぼ0（引いたら即出す）なら → **温存に利益がない**ということ。仮説そのものを疑い、スロット希少性かコスト設計を見直す
- 15回の配置枠を使い切る前に勝ててしまうなら → **難度が低すぎて配分が発生していない**。§6 の較正をやり直す
- 一時停止が多用される（例: 1ランで10回以上、または累計がラン長の3割超）なら → **同時表示すべき情報量か時間設計が過大**。§9.1 のグループ化か §4 のテンポを見直す

### 出口条件

6項目すべてを記録したうえで:

- **Yes** → 次段階（デッキ構築 UI・マップ追加）へ
- **No** → どの反証条件に当たったかを記録して停止する

### ログスキーマ v2

反復0で作った `play-log` を流用し、以下を記録する。前スキーマ（v1）とは互換性がないため版数を上げ、`CURRENT_ITERATION` も更新する。

- `run_started`: シード・プリセットデッキ ID
- `card_drawn`: 引いた札と tick（判定項目1の滞留時間の起点）
- `card_played`: 札・配置先・その時点のマナ・tick（滞留時間の終点）
- `card_discarded_overflow`: 溢れで失った札と tick（前提確認用。決断の指標としては使わない）
- `run_ended` 時点の `hand_remaining`: 最後まで出さなかった札（判定項目1）
- `wave_preview_shown`: 予告を表示した tick と内容（判定項目3の起点）
- `reactivated`: 再起動した設置物と tick
- `paused` / `resumed`: 一時停止の開始・解除 tick（判定項目6）
- `wave_started` / `run_ended` / `run_note`: 反復0と同様

反復0の教訓により、**ここに列挙した項目はすべて §11 の判定に使う**。判定に使わない項目は記録しない。

## 12. 既知のリスクと引き受けた判断

**コスト札の事故を許容する判断はユーザーが明示的に行った。** 緩和は入れず、まず作って実際に判断する方針である。以下は「知らずに踏む」ことを防ぐための記録であって、設計変更の提案ではない。

### 12.1 この作品の「事故」は MTG の事故とは別物

初稿は MTG の土地過多・土地不足（構成の偏り）を引き合いに出したが、**その事故は本作では原理的に起きない**。デッキ20枚を 800 tick で全部引き切るため、**1ランで手に入る札の内容は毎回同じ**である。変動するのは**順番だけ**。

したがって実際のリスクは「魔力炉を引く順番が遅いこと」に集約される。

### 12.2 引き受けたリスク1: 6割のランが魔力炉なしで始まる

初期手札3枚・魔力炉2〜3枚/20枚のとき、初手に魔力炉が入る確率は **40%**。入らなかった場合、初設置は tick 280〜400 頃になり、生成マナは約10（§4.2 の必要量は約27）。**このランは判断と無関係に不利が確定する。**

- 判定への影響: 判定項目4（勝敗理由）で「引きが悪かった」が多発する可能性が高い
- 反証条件に接続済み: 3ラン中2ラン以上で敗因が引きなら、初期手札5枚・初手魔力炉確定・資源デッキ分離のいずれかへ

### 12.3 引き受けたリスク2: 完全な進行停止が起こりうる

マナが0で、かつ手札に魔力炉が無い状態では、次のドローを待つ以外に一切の操作がない。魔力炉のみがマナ源であることの帰結である。

- 判定への影響: 「何もできない時間」は退屈として体感されうる。前コンセプトで問題になった観戦の空白と体感が似る恐れがある
- 反証条件に接続済み: 体感で目立つなら最低限の自然回復を検討する

### 12.4 計測側の担保

戦闘は決定的でシードを記録するため、「事故で負けたのか判断で負けたのか」を事後にデータで切り分けられる。設計を変えずに判定の精度だけを守る措置であり、上記2つのリスクを許容できるのはこれがあるためである。

### 12.5 撤去・売却を入れない判断

設置物を撤去する手段は設けない。スロットが希少である以上、誤配置は永久に残り回復できない。

これは意図的である。**「このスロットをこの札で埋めていいのか」という緊張は、取り消せないからこそ生まれる。** 撤去を入れると配置は暫定的な行為になり、仮説の中心にある「配分の重み」が薄まる。

ただし §6 の較正で難度が上がるほど、序盤の1手の誤りがランを壊す度合いも上がる。実プレイで「取り返しがつかなすぎる」と感じた場合は、撤去（マナ返還なし・配置クールダウンを消費）の追加を次段階で検討する。

- マージ後に戻す必要が生じた場合も、git 履歴（PR #171 空間パズル / #180 可読性 / #190 計測基盤）から復元できる
- ゲーム一覧のエントリ・ルーティング・タイトルは変更しない
